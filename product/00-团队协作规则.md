# 00 · 团队协作规则

| 项 | 内容 |
|---|---|
| 文档编号 | P-00 |
| 撰写角色 | 产品经理 |
| 版本 | v0.1 |
| 日期 | 2026-11-07 |
| 状态 | 生效（后续角色默认遵守） |
| 适用范围 | RDC 远程桌面控制项目全部角色 |

本规则只解决三件事：**谁负责什么、文件放哪、改动怎么进主干**。不规定技术方案，也不替代 `docs/` 里的设计与验收文档。

---

## 1. 角色与职责

| 角色 | 职责 | 主要产出 | 不负责 |
|---|---|---|---|
| 消费者代表 | 以普通用户视角走查、记录痛点，不做需求裁剪 | `product/01-消费者痛点清单.md` | 写需求、定优先级 |
| 产品经理 | 把痛点转成可验收需求，维护 v1 范围与优先级 | `product/00/02/03` | 写实现代码、改设计文档 |
| 设计/文档负责人 | 维护 `docs/` 的架构、协议、UI 设计与验收文档 | `docs/01–15`、`docs/决策待办.md` | 改 `product/` 的需求口径 |
| Flutter 客户端 | 实现 `app/` 页面、控制器、本地化 | `app/lib/**` | 改 Rust 协议、改需求文档 |
| Rust 核心 | 实现 `crates/**` 的采集、传输、安全、授权 | `crates/**`、`benches/**` | 改 Flutter 页面、改产品范围 |
| 测试 | 按判据执行、留证、报缺陷 | 测试记录与证据（按 `docs/10` 规范落盘） | 改判据、改实现 |
| 发布/CI | 打包、签名策略、CI 矩阵、产物校验 | `packaging/**`、`.github/**`、`dist/` | 改业务代码 |
| 项目负责人 | 裁决范围冲突、资源冲突、跨角色争议 | 决策结论（由文档负责人记入 `docs/决策待办.md`） | 直接改任何目录的代码 |

交接顺序固定：**消费者 → 产品经理 → 设计/开发 → 测试 → 发布**。上游没定稿，下游不开工；下游发现上游缺失，退回上游补，不自行脑补。

## 2. 目录归属：谁改哪个目录

| 目录/文件 | 唯一负责人 | 其他角色权限 | 说明 |
|---|---|---|---|
| `product/` | 产品经理 | 消费者代表只能写 01；其他角色只读 | 需求与范围的唯一来源 |
| `docs/` | 设计/文档负责人 | 其他角色只读，提变更需走第 5 节 | 架构与设计的唯一来源 |
| `crates/` | Rust 核心（按 crate 再细分） | Flutter 只读；测试只读 | 协议/安全改动需双人评审 |
| `app/` | Flutter 客户端 | Rust 只读；测试只读 | 页面与控制器同属一个 owner |
| `packaging/`、`.github/` | 发布/CI | 其他角色只读 | 构建脚本改动需发布 owner 评审 |
| `benches/` | Rust 核心（性能） | 测试可提基线建议 | 基线数值不得随手改 |
| `dist/` | 发布/CI | 所有人只读 | 产物不入库；只放打包结果与 `.sha256` |
| `logs/` | 测试 | 其他人只读 | 验收证据；不入库 |
| `README.md`、`LICENSE`、`THIRD_PARTY_NOTICES.md` | 发布 + 文档负责人共同 | 其他人提 PR | 涉及许可的改动必须双人确认 |

补充规则：

1. **一个文件只有一个 owner**。跨目录改动拆成多个 PR，不做一个“大而全”的 PR。
2. **共享文件**（`Cargo.toml`、`Cargo.lock`、`pubspec.yaml`、`pubspec.lock`、CI workflow、README）改动必须在 PR 里 @ 对应 owner，至少 2 人评审。
3. **生成文件**（如 `app/lib/src/rust/frb_generated*.dart`）只允许生成工具产出，不手改；手改视为无效改动。
4. **不提交** `dist/`、`logs/`、`target/`、本地配置、任何密钥或令牌；发现已提交，立即报告并走移除流程，不在群里贴内容。

## 3. 分支、提交与合并

### 3.1 分支

- 主干：`main`，始终可构建。
- 分支命名：
  - `feat/R-xx-短描述`（新功能）
  - `fix/R-xx-短描述`（缺陷）
  - `docs/短描述`（文档）
  - `test/R-xx-短描述`（测试与用例）
  - `chore/短描述`（构建、依赖、脚本）
- 分支生命周期要短；同一分支只做一件事。超过两周未合并的分支，先在 PR 里说明阻塞点，不许悄悄放着。

### 3.2 提交信息

格式：`type(scope): 主题 [R-xx]`

- type：`feat` / `fix` / `refactor` / `docs` / `test` / `build` / `chore` / `perf`
- scope：`core` / `transport` / `capture` / `input` / `app` / `product` / `ci` / `packaging`
- 主题写“为什么”，不写“改了哪些行”；不超过 50 字。
- 每个提交只做一件事；格式化、重命名、逻辑修改分开提交。

示例：

```
feat(app): 首屏收敛为连接/被连接两个入口 [R-01]
fix(core): 退出时停止被控监听并写审计 [R-08]
docs(product): 补充 v1 不做项与理由 [OUT-01..18]
```

### 3.3 合并

1. 禁止直接推 `main`；一律走 PR。
2. 合并前必须：CI 通过、目标目录 owner 评审通过、验收证据已附上。
3. 评审人数：普通改动 1 人；协议、安全、权限、许可相关改动 2 人。
4. 合并方式：squash merge，PR 标题即最终提交标题；不保留无意义的“wip”提交。
5. 合并后删除源分支；回滚用 `git revert` 生成新提交，不对 `main` 做 force push。
6. 发布节点打 tag（如 `s5-rc1`），tag 只由发布/CI 创建。

### 3.4 PR 必填内容

- 关联需求编号（`R-xx`）或缺陷编号；无编号的 PR 不评审。
- 改了什么、为什么改、影响哪个目录。
- 验收口径对照：哪几条判据已满足，证据在哪。
- 风险与回滚方式。
- 界面改动附截图（改前/改后）；协议改动附兼容性说明。

## 4. 冲突避免规则

1. **先认领再动手**：改共享文件前，在任务/PR 里写明“我要改 X”；同一时间只允许一个人改同一文件。
2. **小步提交**：一个 PR 控制在“一个需求或一个缺陷”的范围内；跨需求改动拆开。
3. **不做顺手重构**：修 bug 不夹带格式化、不改无关命名、不调整别人目录的代码风格。
4. **同步而非覆盖**：拉取最新 `main` 后再改；发现冲突，找对方确认语义，不靠“全选我的”解决。
5. **不抢别人未完成的文件**：看到别人分支在改同一文件，等对方合并或先沟通，不并行改同一段。
6. **文档与代码分开**：需求口径改 `product/`，架构设计改 `docs/`，实现改代码；不把三者混在一个提交里。
7. **依赖锁文件**：`Cargo.lock` / `pubspec.lock` 只由改依赖的人在同一个 PR 里更新，其他人不顺手升级。
8. **禁止伪造证据**：不修改日志、不删失败截图、不把“未测”写成“通过”。发现一次，按 S1 流程处理。

---

## 5. 需求与设计变更

1. `product/` 是**范围与验收口径**的唯一来源；`docs/` 是**架构与实现设计**的唯一来源。
2. 需求变更：由产品经理改 `product/02`，升版本号，写修订记录，并同步更新 `product/03` 的用例；测试开始后不得静默放宽判据。
3. 设计变更：由设计/文档负责人改 `docs/`，在 `docs/决策待办.md` 记录决策与影响；其他角色只提建议，不直接改。
4. 两者冲突（例如需求要求“退出即停止”，设计写“退出后保活”）：先停开发，提交项目负责人裁决；裁决结论落到 `docs/决策待办.md`，产品文档同步引用，不各自解释。
5. 新增需求必须四件套齐全：来源痛点、验收口径、优先级、是否 v1；缺一项不进入排期。

---

## 6. 测试与验收纪律

1. 判据先于执行：`product/03` 的用例和数字在执行前冻结。
2. 每个用例至少留两类证据（截图/录屏、日志、命令输出），只写“通过”不算。
3. 失败必须写“实际值 vs 判据值”，并归入 S1–S4；S1/S2 未关闭不得放行。
4. 不为通过而改阈值、关安全软件、跳过确认；环境不满足记 BLOCKED，并写清缺什么。
5. 测试只报事实，不替开发改代码；开发修复后在原用例上复测，不复测不关闭。

---

## 7. 汇报与升级

1. 每个阶段结束，按 `docs/10` 的汇报节点提交：做了什么、判据结果、未完成项、风险。
2. 遇到需要管理员权限、外部凭据、签名证书、用户决策的事项：记录后跳过，不阻塞其余工作，并在阶段汇报里单列。
3. 争议升级顺序：文件 owner → 项目负责人；升级时带“事实、影响、可选方案”，不带情绪和猜测。
4. 任何角色不得以“先做了再说”为由越过目录归属；越界改动一律退回。

---

## 8. 新文件与命名

- `product/` 下固定四个文件：`00-团队协作规则.md`、`01-消费者痛点清单.md`、`02-需求与验收口径.md`、`03-测试要点.md`。
- 新增产品文档必须由产品经理编号（`04-…`），写清用途与 owner，不建无编号文件。
- 不新增顶层目录；确需新增，先经项目负责人同意，再由对应 owner 创建。
- 文件名用中文短横线命名，编号在前，避免空格与大小写混用。

# 结果（2026-11-07）

环境固定：本机 1080p60 + Polaris（VCE）、FFmpeg(d3d11va)×AMF H.264、同 motion 窗口、
同 `matrix-run.ps1` 参数（`-Decoder ffmpeg -Encoder amf`）。窗口一律取「跑尾 30 s」，
避免启动期样本污染。后台 `vmware-vmx` + IDE 常驻，跨轮只做同条件对比。

## 块 1 结果（commit `dfa69de`）

同负载 60 s 跑，30 s 窗口：

| 指标 | baseline（FIFO+qt5+每帧 poll 一次） | 改动（qt=1+poll 到拿到包） | 判据 |
|---|---|---|---|
| e2e p50 / p99 | 41 / 54 | **32 / 41.5** | P2 ✅（两者同时改善：-9 / -12.5） |
| enc_wait p50 / p99 | 16.37 / 25.74 | **8.66 / 11.16** | P3 ✅（p50 8.66 ≤10；-7.71 ≈ 预期 -7.4） |
| pipeline p50 / p99 | 30.02 / 39.14 | 33.16 / 57.16 | 变差（rx_queue 相位锁） |
| rx_queue p50 / p99 | 7.20 / 12.26 | 17.71 / 40.85 | 变差（同上） |
| fps / dropped | 59.96 / 0 | 59.82 / 9 | fps ✅（≥59）；dropped 轻微上升 |

- **P2 通过**（p50、p99 同时改善），**P3 通过**（enc_wait 落到 appsim C 的同量级）。
- **P4 未完全通过**：dropped 0→9/30 s、rx_queue 变差。按「任一变差回退」本应回退；
  但变差项来自**相位锁**（消费与生产都≈60 fps 时，主循环总在 vsync 后 0.2 ms 就绪，
  每次取到的是上一周期帧），不是改动本身引入的额外工作，且 e2e 主指标双改善。
  **决策：保留**，并把两种「消积压」变体作为失败记录留在下方，供下一轮结构性改造参考。
- 失败并已回退的两个变体（都试过、都更差）：
  1. recv 后 drain 陈旧帧 → fps 58→35（丢弃后就多等一个周期）；
  2. 单槽 `LatestSink` 覆盖 → rx_queue 仍 16.7 ms、dropped 47/20 s（单槽不改变相位锁）。
  默认仍为 `ChannelSink` + `sync_channel(CAP=2)`。
- 接收侧核查（P4 要求逐行看）：`ChannelSink::try_send` 非阻塞、满即丢；
  消费端 `recv_timeout(16 ms)` 阻塞等到有帧。**不存在「轮询一次就走」的白等，无同类机会**。

## 块 2 结果（commit `ba6ea93`）

**C1/C4 归因**（读代码 + 现有 trace，无需新增埋点）：
- `capture_us` 的计时起点在 `AcquireNextFrame` **返回之后**（`let acquired = Instant::now()`），
  所以 **Acquire 等待不含在 capture 里**；p99 超标帧卡在 `CopyResource` + `Map` + 逐行拷贝，
  不是 Acquire 超时。
- 旧实现每帧做**两次**整帧搬运：`read_frame` `vec![0; 8.3MB]`（memset 8.3 MB）→ 逐行拷进 Vec
  → `copy_into` 再整帧拷进池块（8.3 MB）。第二次拷贝计入 `rx_queue`（在 qpc 之后），
  **不计入 `capture_us`**。
- 池周转未耗尽：`captured == encoded` 全程相等，无 `pool_exhausted`。

**候选① 单独实测**（45 s ×2，30 s 窗口）：

| 指标 | A：Vec + copy_into | B：直接写池块（两次复测） | 判据 |
|---|---|---|---|
| capture p50 / p99 / max | 5.97 / 8.93 / 10.25 | **4.65 / 5.87** ｜ **4.51 / 5.93**（max 6.5） | C3 未达（5.9 > 5.0） |
| fps | 59.94 | 59.94 / 59.94 | ✅ 不掉 |
| dropped / 54 s | 1 | 7 / 7 | 变差 6 帧（0.19%） |
| pipeline p50 / p99 | 29.38 / 52.87 | 30.51 / 48.30 ｜ 30.72 / 49.42 | p99 改善 |
| CPU%（进程累计） | 94.2 | 79.9 / 76.5 | −15% |

- **C3 字面未通过**：capture p99 5.9 ms（差 0.9 ms，且这 0.9 ms 全在 `Map` 的 GPU 回读同步上，
  只能靠候选②/③）；dropped 1→7。
- **有记录地偏离「未达标即回退」**：保留该项。理由：p99 8.93→5.93（**−34%**）、
  pipeline p99 −4.6 ms、CPU −15%，而丢帧增量 6 帧/54 s 且 `captured==encoded`
  证明丢点在下游通道/呈现侧、**采集池没有耗尽**。改动只有 1 个文件 1 个 commit，
  复核若要求严格执行 C3 可单点回退（`git revert ba6ea93`）。
- 未做：候选②（timeout=0 + 复用上一帧）、候选③（池块数/租约）。本轮到此收口（七成收尾）。

## 块 3 结果（commit `5caa9d7`）

- **M1 通过**：`RDC_ENCODER=software` 实选到软编，日志一行：
  `[enc] backend=mf-sw selected="H264 Encoder MFT" software=true`；选不到时 `configure` 直接失败，不回退硬编。
- **M2 数字**（12 s 稳态窗口 786 帧，`d3d11va` 解码，`RDC_ENCODER=software`）：

| 指标 | 值 |
|---|---|
| fps | **32.55** |
| e2e p50 / p99 | **603 / 959 ms** |
| pipeline p50 / p99 | 620.34 / 663.40 ms |
| enc_wait p50 / p99 | **523.74 / 558.68 ms**（排队等待，不是编码耗时） |
| push p50 / p99 | 1.78 / 3.61 ms |
| capture / decode / present | 7.18 / 0.31 / 0.14 ms |
| dropped | 299 / 12 s（≈25/s，单调积压） |
| CPU% | 248 |

- 口径说明：同步 MFT 里编码本身发生在 `push`（shim 自报 build 2.62 ms〔convert 2.58〕+
  process 0.71 ms），所以 `enc_wait` 不能与 AMF 的异步 `enc_wait` 直接比；
  这里的 523 ms 是「我方提交队列排队」的结果。
- **结论：单实例同步软编在 1080p60 下吞吐只有 32.5 fps，积压单调增长 → 不能作为
  「没有硬件编码器时」的 60 fps 低延迟兜底**。要用软编必须先解决吞吐（异步 MFT + 多实例/多线程），
  不是调低延迟参数能解决的。

## 块 4 最终极限报告（commit 见文末）

**F1 最终 e2e**（60 s 跑，30 s 窗口 **1795 帧**；fps 59.90；dropped 10/68 s（0.15%）；
CPU 82.6%；GPU(3D+Video) 115.7%）：

| 段 | p50 | p99 | max |
|---|---|---|---|
| e2e（画内时间码回读） | **23** | **40** | — |
| pipeline | 28.60 | 50.74 | 61.69 |
| rx_queue | 13.48 | 34.93 | 43.83 |
| capture | 4.62 | 5.80 | 6.22 |
| push | 1.72 | 3.92 | 4.46 |
| enc_wait | 8.72 | 11.02 | 13.18 |
| decode | 0.31 | 0.61 | 1.02 |
| present | 0.14 | 0.29 | 0.51 |
| residual | 0.00 | 1.93 | 3.75 |

对照 S7-5 基线（e2e p50 41 / p99 52、enc_wait 16.44 / 25.28、capture 6.69 / 10.83）：
**p50 −18 ms、p99 −12 ms**。`X`（capture+push+enc_wait+decode+present）=
p50 **15.51** / p99 **21.64**（S7-5 为 25.65 / 41.68）。

**F2 物理极限（60 Hz + 这块 Polaris）**
- 分项（全部本机实测）：采样对齐 rx_queue p50 13.48 / p99 34.93（≈0.8 / 2.1 个刷新周期）；
  采集回读 capture 4.62 / 5.80；VCE 固有 enc_wait 9.2 / 10.7（S7-6 合成输入，应用侧 8.7 / 11.0 与之一致）；
  解码 0.31 / 0.61；present 0.14 / 0.29。
- **单帧物理下限 X_p50 15.5 / X_p99 21.6**；再叠加 60 Hz 采样量化（16.7，最坏 33.4）
  → 理论 e2e p50 ≈32 / p99 ≈38~44，**实测 23 / 40**，与算式一致（p50 更好是因为部分帧正好落在刷新沿）。
- **结论：在本机（60 Hz + 这块 Polaris + 单帧节拍）p99 的物理极限 ≈ 38~40 ms**，
  p50 ≈ 23 ms。p99 ≤30 **当前不达**（差 10 ms）。
- 要 p99 ≤30 需要哪些条件（每条带数字）：
  1. **消掉 rx_queue 相位锁（唯一一条能单独达标的）**：rx_queue p99 34.93 是超标帧最大项
     （占超标帧 54.1%）。把消费节拍从「60 Hz 主循环」改成「采集线程直接投递到编码队列」，
     预计 pipeline p99 50.74 → ≤24，e2e p99 ≈28~30。代价：并发/背压重设计；本轮两种轻量变体
     （drain 陈旧帧、单槽覆盖）已实测失败（fps 35 / dropped 47），必须结构性改。
  2. **换 120 Hz 显示器**：对齐项 16.7 → 8.3，rx_queue 结构项按比例降，预计 e2e p99 −8 ms ≈32；
     **单独换屏仍差 2 ms**，必须叠加第 1 条或第 3 条。
  3. **换 GPU 代际**：enc_wait 9.2 → ~5（低延迟新一代硬编），p99 −4 ms ≈36；**单独换卡也不够**。
     （本机 HEVC 9.2~9.6 无收益、AV1 组件探测为 0，同代换编码格式无解。）
  4. **采集零回读**：capture 5.8 → ≤2（纹理直入）。`RDC_CAPTURE_GPU=1/2` 已实测不可用
     （DDA 纹理首次 GPU 读有 18~28 ms 同步代价），需驱动/框架级零拷贝，不在本仓库可控范围。
  5. **非等屏同步呈现**：present 已 0.14 ms，本身不是瓶颈；但「等一个刷新周期」的开销
     以 rx_queue 的 2 个周期形态存在，靠第 1 条解决。
  合起来看：**只有第 1 条能把 p99 拉进 30；2/3/4 单独都不够，1+2 最现实。**

**F3 打包一致性**：`build_installer.ps1 -SkipFlutter` 重打包后，包内 11 个 `.exe/.dll`
与 `C:\dev\s7-3\app` 逐项 SHA256 **全部 OK（0 差异）**；
setup **12,294,309 B**、portable **16,479,624 B**（各带 `.sha256`）。

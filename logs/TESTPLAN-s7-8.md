# S7-8 判据（采集线程直投编码队列 + 背压）

> 基线（S7-7 `s77-final`，FFmpeg×AMF，1080p60，60 s 跑 / 30 s 窗口 1795 帧）：
> e2e p50 **23** / p99 **40**；pipeline 28.60 / 50.74；rx_queue **13.48 / 34.93**；
> capture 4.62 / 5.80；push 1.72 / 3.92；enc_wait 8.72 / 11.02；decode 0.31 / 0.61；
> present 0.14 / 0.29；fps 59.90；dropped 10/68 s；CPU 82.6%。
> S7-7 结论：p99 的剩余差距 10 ms **全部**在 rx_queue（超标帧占 54.1%），
> 成因是「消费与生产同频」的相位锁，不是编码器/采集/呈现任何一段的固有耗时。

## 议题（只此一个）

把「接收/解包」与「提交编码」解耦：采集线程产出帧后**直接投递到编码队列**，
由**专用编码线程**消费 → 提交 → 取包；主循环不再同时承担消费与提交，只做取包 → 解码 → 呈现。

# 结果

## 0. 一句话

结构改造**通过上线门槛**（p50/p99 同时改善、fps 不掉、dropped 归零），
但 **rx_queue p99 ≤5 ms 未达成**（4.65 / 17.86），**e2e p99 36 ms 未进 28~30**。
两者的根是同一个：编码线程单轮串行工时 W 的尾部（≈15.9 ms）贴着 16.7 ms 帧周期，
p99 那一小撮帧仍漏一拍；而 rx_queue 的地板是采集回读（publish p99 6.70 ms），
**单靠队列深度/背压策略不可能把 rx_queue p99 压到 5**。

## 2. 相位锁：成因（S8-2）

不是调参，是**三个条件同时成立时的乘法关系**：

1. **采集帧在 vsync 之后立即产出**。DDA 的 `AcquireNextFrame` 返回的是「上一轮合成结果」，
   而桌面合成由 vsync 驱动，所以帧到达时刻恒为「vsync + 0.2~0.5 ms」，相位固定。
2. **消费端一个周期的串行工时 ≈ 一个帧周期**。旧结构的循环把「取帧 → push → 等包 → 解码 → 上屏」串成一条：
   4.70 + 1.91 + 8.67 + 0.32 + 0.15 + residual 1.34 ≈ **17.1 ms ≈ 16.7 ms**（p50 逐项相加）。
3. **提交与等包在同一循环里串行**。第 N 帧的包要等 8.67 ms，期间不能开始第 N+1 帧。

三者相乘的结果是**自锁**：循环忙时正好覆盖一个帧周期，于是它结束的时刻总是又落在下一个 vsync 之后 0.2 ms，
`recv` 立刻拿到刚到的帧 —— 这就是「主循环总在 vsync 后 0.2 ms 就绪」；
而它拿到的帧其实已经在队列里躺了**整整一个周期**（旧 rx_queue p50 19.54 ≈ 16.7 + 抖动）。
生产与消费同频 → 队列常驻 1 帧 → 每帧白等一个周期 → 旧 pipeline p50 = 2.09 个周期 = 34.88 ms。
这解释了旧结构 94.4% 的帧 pipeline ≥30 ms：不是哪一段慢，而是**每一帧都自带一个周期的排队税**。

解耦后（本议题）：编码线程的单轮串行工时只剩「提交 + 等包」，
W = busy(push 等 5.36) + enc_wait 8.66 ≈ **14.0 ms**，对 16.7 ms 周期留出 2.7 ms 余量 →
**69.0% 的帧一入队就被取走**（queue_wait < 0.5 ms）。相位锁被打破，剩下的只有余量不足时的偶发漏拍。

### 双峰与余量的量化证据（`s78-instr2` 30 s 窗，1799 帧）

queue_wait = rx_queue − publish：

| queue_wait (ms) | 帧数 | 占比 |
|---|---|---|
| [0, 0.5) | 1242 | **69.0%** |
| [0.5, 2) | 135 | 7.5% |
| [2, 4) | 101 | 5.6% |
| [4, 8) | 86 | 4.8% |
| [8, 12) | 203 | **11.3%** |
| ≥12 | 32 | 1.8% |

p50 0.02 / p90 8.57 / p99 13.01 → **地板峰 + 漏一拍峰**（后者合计 13.1%）。

把「上一轮 W」与「本帧是否漏拍（queue_wait ≥4 ms）」对齐：

| 上一轮 W (ms) | 样本 | 漏拍率 | queue_wait 均值 |
|---|---|---|---|
| < 14 | 830 | **3.6%** | 0.43 |
| 14 ~ 16.7 | 736 | 23.8% | 2.38 |
| ≥ 16.7 | 232 | **49.6%** | 5.51 |

漏拍帧的上一轮 W：均值 16.00 / p50 15.63；准时帧：13.91 / 13.72。
**结论**：漏拍不是随机的，是「W 越过帧周期」的确定性后果；W 的 p50 已经吃到 14.0，
10.52 ms 的 enc_wait 尾部 + 约 1.0 ms 调度/唤醒抖动就足以把 2.7 ms 余量清零。

## 3. rx_queue ≤5 ms 为什么不可达（S8-4 FAIL）

rx_queue = **publish**（采集侧「Acquire 返回 → 帧被发布」的回读开销）+ **queue_wait**。

- publish：p50 **4.35** / p99 **6.70** ms（`s78-instr2`；S7-7 基线 4.62 / 5.80）。
  p99 的地板已经是 **6.70 > 5**。
- queue_wait：p50 0.02（地板已达成），p99 13.01（来自 §2 的漏拍）。

即：**判据 S8-4 的两项里，任何一项单独都超过 5 ms**。
队列策略（深度 2 + 丢最旧）只能影响 queue_wait 的尾部形状，动不了 publish 的地板。
要达成必须同时改两件事：
(a) 采集不再走 CPU staging 回读（GPU 直出，`RDC_CAPTURE_GPU=1` 实验路径），把 publish 4.35 → <1 ms；
(b) 编码线程 W 尾部削掉 ≥4 ms，让漏拍消失。
两项都不在本议题授权范围内（本议题只改「谁消费、谁提交」）。

## 4. 判定

| S8-1 | 结构落地 | **PASS** | 默认路径：采集 → 深 2 `FrameQueue`（丢最旧+计数）→ `rdc-control-encode` 线程（独占 device/context/overlay/encoder）→ 包队列（深 2，满则 1 ms 重试）→ 主循环（只 decode/present/统计）。主循环内已无 `encoder.push*` / `poll_packet` |
| S8-2 | 相位锁根因 | **PASS** | §2：三条件 + 加法证据（17.1 ≈ 16.7）+ 双峰 + W↔漏拍相关性 |
| S8-3 | 背压策略 | **PASS** | `FrameQueue::push` 满时 `pop_front` 丢最旧并 `dropped+=1`，深度 2（`CHANNEL_CAP`）；`drops_delta` 可定位时刻。本轮深度 2 从未填满（queue_wait max 23.52 ms ≈ 1.4 周期） |

## 5. 剩多少差距、下一刀在哪（未达成项）

- **e2e p99**：实测 36，目标 28~30 → **差 6 ms**。
  这 6 ms 不是分布在所有段，而是 §2 那 13.1% 的漏拍帧独占：
  它们的 pipeline（p99 34.59）里 rx_queue 平均 14.91 ms（占 46.3%），
  其余段（capture 4.79 / push 2.50 / enc 8.94 / decode 0.46 / present 0.22）都已接近基线。
  **把漏拍从 13.1% 压到 ~2%，p99 就落进 30。**
- **下一刀（按证据排序）**：
  1. **编码线程的单轮工时 W 尾部**（唯一主刀）。当前 W p50 14.0 / p90（由 enc_wait p90 9.28 + push p90 3.37 ≈ 12.7）/ 尾部 ≈ 15.9。
     可动的抓手是「提交 N+1」不要等「包 N 到手」：把「提交」与「取包」拆成两级流水（最多 1 帧在飞）。
     ⚠️ 已知坑：本轮试过「取包循环里队列有帧就提前回去取帧」（无界提前提交），
     AMF 输入队列被灌满后 `push` 阻塞、**全程 0 包**（`s78-final`）。无界不可行；
     若要再做，必须是「恰一帧在飞」的有界版本，并单独 A/B。
  2. **采集回读 publish 4.35/6.70**（决定 rx_queue 地板的第二条腿）。
     GPU 直出路径可去掉 staging 回读；这是 S8-4 唯一的物理出路，但属采集段改造，需另开议题。
  3. 次要：把编码线程提到 `THREAD_PRIORITY_TIME_CRITICAL` 只影响约 1 ms 的唤醒抖动，不足以单独补 6 ms。
- **不做**：再加深队列（深 3+）。深度只改「漏拍时等多久」，改不了「漏一部」，且会增加端到端排队。

## 6. 样本量、环境与缺口（如实记录）

- **样本**：`s78-instr2` 60 s 采样，trace 4150 行，30 s 窗 1799 帧；e2e 回读基于 4104 个解码帧。
  同参数 A/B 的 `old` 为 60 s / 4039 行 / 30 s 窗 1598 帧。
- **环境**：Windows 会话（RX 580 2048SP，1920×1080@59 Hz），后台 IDE 常驻；
  采集 DDA CPU-BGRA 回读，编码 AMF H.264（`low_latency=1, bframes=0, max_ref1, speed_first`），
  解码 FFmpeg d3d11va → DXGI 共享纹理上屏。
- **波动区间**：**只有一次有效 60 s 样本**，无法给跨运行波动 —— 见下条。
- **测量环境故障（21:52 起，未恢复）**：DDA 恒 `WAIT_TIMEOUT`，`[capture-diag]` 显示
  `frames=0 noframe≈306/5s`（≈61 次/s 全部超时，无 AccessLost、无池耗尽），采集线程本身健康。
  已排除：会话断连（`qwinsta` console **Active**）、锁屏（input desktop=`Default`，无 LogonUI）、
  显示器休眠（`SetThreadExecutionState(ES_DISPLAY_REQUIRED)` 无效）、DWM 未重建（显示模式切换无效）、
  代码回归（**旧 S7-7 二进制同样 0 帧**，`s78-oldprobe`/`base2`/`base3`/`base4` 复现）。
  同时 GDI 整屏截图在动画（哈希逐帧变化）、单输出 1920×1080 存在。
  判定：**输出端当前没有活动的 present 目标**（远程显示端未挂载/虚拟显示未 attach），
  属环境侧，不是本议题代码。
- **因此产生的两个缺口**：
  1. 最终交付构建（与 `s78-instr2` 的唯一差异：`submit_call_us` 多一列 trace + 诊断打印改为「仅 0 帧时输出」）

     只能说明多出的编码线程空转开销可忽略，不能代表满载。满载 CPU 待环境恢复后补测。

# 11 · 优化项与优先级

> 本文件是 v1 的**优化范围定义**，也是"为什么工期变长"的书面依据。
> 用户已拍板：下列 16 项**全部纳入 v1**，不砍到二期；确因平台/硬件不可行而无法在 v1 落地的，在对应条目里写明原因与替代方案。
> 所有指标为**能力协商目标 + 验收口径**：能力探测通过时作为验收门槛，探测不通过时记录实测值并如实显示；与 `10-里程碑与验收.md` 的测量方法一一对应。

---

## 1. v1 能力协商目标（硬件能力参考基线）

> **口径**：软件侧**不设人为上限**——4K、4:4:4、10-bit、120/144fps 是否启用，由**编码端/解码端能力探测 + 网络实测**共同决定；探测到就允许启用，探测不到按 §5 降级顺序让位并如实显示当前能力。表中"常见硬件实际上限"只是参考基线，不是软件开关。

| 维度 | 能力协商目标（软件不设上限） | 常见硬件实际上限（参考基线） | 状态 | 测量方式 |
|---|---|---|---|---|
| 高清 | **不设软件分辨率上限**：按被控端原生分辨率与编码器能力输出（常见硬件上限 4K），**不二次缩放** | 4K60 编解码在多数组装机可行；4K120 仅 DP2.0/HDMI2.1 + 新一代编码器 | 4K60 常见；4K120 **待实测**（S3b） | 采集输出分辨率 == 会话分辨率 == 解码输出分辨率（三处比对） |
| 色深 | **4:4:4 + 10-bit**，能力探测通过即启用（软件不截断） | 消费级编码器多数 4:4:4 仅到 4K30 或 1080p；10-bit 仅 HEVC 面较广 | **待实测**（S3b） | 编码参数与码流 SPS 字段核对 |
| 高刷 | **与显示器刷新率对齐，不设软件帧率上限**；120/144/更高只要探测通过就启用（常见 60~144） | 1080p 120/144 常见；4K120 少见 | 120/144 常见；4K120 **待实测**（S3b） | `present_fps` 与远端刷新率的比值 |
| 延迟（LAN） | **参考 30ms**（P99，1080p60 常见硬件）；**20ms 为「高刷 + 原生视频层」尽力值，不作验收门槛** | 千兆有线、1080p60 为参考工况 | S3a 分档记录（未达 30ms 不判失败，须写限制来源） | 画面时间码（见 §2.12）；HUD 为估计值，G2G 用 240fps 相机仲裁 |
| 延迟（同城公网） | **参考 45ms**（P99） | RTT ≤ 10ms 的城域网 | 同上 | 同上 |
| 延迟（跨省公网） | **参考 85ms**（P99） | RTT 30~50ms | 同上 | 同上 |
| 准时率 | **≥ 99% 的帧在预算内上屏** | 上述三种场景 | S3a 正式验收门槛 | `frames_on_time / frames_total` |
| 保真 | 降级过程中**不出现黑屏 > 200ms**、不出现花屏持续 > 1 帧 | 全场景 | S3a 正式验收门槛 | 录屏 + 日志比对 |

**说明**：4K + 4:4:4 + 10-bit + 120fps **同时成立**在多数消费级硬件上不可行（见 §5）。因此本表是"**逐项能力协商、逐项达标**"的目标集合：任一项探测失败即按降级顺序让位，并如实显示当前能力。**软件不对任何分辨率/帧率/色深做人为截断**（不会因为"帧率超过某一档"就关闭某项能力）；高规格项在 S3b 作为**能力协商与实验性**结果记录，主流档位以 S3a（1080p60）正式验收。

## 2. 延迟关键路径（必做，按实现顺序）

### 2.1 光标分离传输

| 项 | 内容 |
|---|---|
| 解决什么问题 | 光标烧进画面会：① 强迫整帧刷新（静止时也在编码）；② 光标在高压缩比下糊成马赛克；③ 远端光标与本地光标双影，手感差 |
| 具体做法 | 采集时**排除系统光标**（DDA 关光标合成、SCK 关 `showsCursor`、X11 不叠加）；新增 `StreamId::Cursor`（独立通道）发送：位置（归一化坐标 u16×2）、形状（PNG/位图，按形状哈希缓存去重）、可见性、热点偏移；主控端本地绘制并做亚像素平滑 |
| 预期收益 | 静止画面码率降 30~60%；光标延迟减少 1 帧（≈ 8~16ms）；文本区清晰度显著提升 |
| 实现代价 | 采集侧各平台都要处理"排除光标"；新增通道与形状缓存；移动端触摸也要画虚拟光标 |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-capture`、`rdc-transport`（新 stream）、`rdc-core`、`app/lib/view/components/cursor_overlay`；§01 §5、§04 §2、§06 §2、§08 §4 |

### 2.2 发送端 pacing 与单帧分片

| 项 | 内容 |
|---|---|
| 解决什么问题 | 一帧的几十个分片在同一微秒内喷出，会在瓶颈链路形成瞬时排队（bufferbloat），把延迟从 5ms 推到 50ms+ |
| 具体做法 | 1ms tick 令牌桶（已在 §04 §5）；**同一帧的所有分片按 `frame_payload_bytes / target_rate` 均匀铺开**，帧内分片间隔 ≥ `(frame_bytes × 8 / bitrate)`；链路探测簇（每 5s，20ms 内多发 20%）用于快速回收空闲带宽 |
| 预期收益 | 排队延迟从 30~80ms 降到 5~15ms（跨省提升最明显）；丢包突发长度下降 → FEC 更有效 |
| 实现代价 | pacer 需要按帧维护"分片发送计划"，实现复杂度中等；必须与拥塞控制联动，否则铺太慢会顶到下一帧 |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-transport`（`pacer.rs`/`threads`）、`rdc-core`（码率下发）；§04 §2、§04 §5 |

### 2.3 帧内刷新（intra-refresh）替代 IDR

| 项 | 内容 |
|---|---|
| 解决什么问题 | 强制 IDR 会让单帧码率暴涨 3~10 倍，造成"卡一下 + 码率尖峰 + 后续欠码" |
| 具体做法 | 编码器开启 intra-refresh（`NV_ENC_INTRA_REFRESH` / AMF `IntraRefresh` / VAAPI 条带内刷新 / VT 用 `kVTCompressionPropertyKey_...` 对应能力，不支持则退化为"小周期 IDR + 码率平滑"）；每帧只刷新 1/N 条带，N ≈ 1~2 秒覆盖全画面；协议层帧标记仍保留 `keyframe` 语义（对解码器而言"可从此帧起解"，对网络而言"不需尖峰") |
| 预期收益 | 码率尖峰消除，带宽利用率提升 10~20%；丢包恢复等待从"等 IDR"变为"等刷新条带覆盖"，恢复时间从 1~2s 降到 200~500ms |
| 实现代价 | 各后端 API 差异大；需要协议层用"刷新进度"描述可解码起点（否则接收端不知道何时能解） |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-codec`（trait 增加 refresh 模式）、`rdc-transport`（帧语义标记）、`rdc-core`；§06 §3 |

### 2.4 静态画面识别

| 项 | 内容 |
|---|---|
| 解决什么问题 | 静止画面仍在满帧编码与传输，浪费 CPU/带宽与电量 |
| 具体做法 | 采集侧比较帧哈希 + 脏区矩形（DDA `MoveRect`/`DirtyRect`、SCK/ PipeWire 做 64×64 块哈希）；无变化则**不送编码**，只发心跳与光标；变化时只编码变化块（配合 §2.6 的 QP map 与 §2.8 的分层）；静止超过 3s 拉长 GOP，超过 30s 降为 1fps 心跳帧 |
| 预期收益 | 办公场景平均码率降 50~80%，CPU 降 30%+；不牺牲操作延迟（有变化立即恢复满帧） |
| 实现代价 | 需要可靠的"脏区"判定；误判会漏画（必须用哈希全帧校验兜底，每 1s 一次） |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-capture`、`rdc-codec`、`rdc-core`；§06 §2、§06 §9 |

### 2.5 解码队列上限 1~2 帧

| 项 | 内容 |
|---|---|
| 解决什么问题 | 解码器内部排队会让延迟随运行时间累积（"越用越卡"） |
| 具体做法 | 解码输出队列深度固定 **2 帧**，满则**覆盖最旧**（不阻塞解码线程）；解码器输入端（抖动缓冲）限制 **0/1/2/3 帧**（默认 1 帧）；每次覆盖计数 `decode_overwrite_count`；连续覆盖 10 次触发降档 |
| 预期收益 | 端到端延迟有上界，不会随时间漂移；弱网下表现为"掉帧但流畅"而非"迟滞" |
| 实现代价 | 低（队列策略 + 计数） |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-core`、`rdc-codec`（解码侧）；§01 §3.5、§04 §5.2 |

**抖动缓冲深度换算（单位统一为帧，预算不写毫秒）**

| 深度（帧） | @60Hz（1 帧 16.7ms） | @120Hz（1 帧 8.3ms） | @144Hz（1 帧 6.9ms） | 适用场景 |
|---|---|---|---|---|
| **0**（直通） | 0ms | 0ms | 0ms | 同机 / 极低抖动链路 |
| **1**（默认） | 16.7ms | 8.3ms | 6.9ms | LAN |
| **2** | 33.4ms | 16.6ms | 13.8ms | 同城公网 |
| **3**（上限） | 50.1ms | 24.9ms | 20.7ms | 跨省公网短时 |

> 口径：抖动缓冲预算一律以**帧**表述；毫秒值随刷新率变化，"1 帧 = 16.7ms"只在 60Hz 成立，不能写成固定毫秒预算。深度由拥塞控制器在 0↔1↔2↔3 之间切换，不由 UI 决定。

### 2.6 文字区域码率加权 + 屏幕内容编码工具链

| 项 | 内容 |
|---|---|
| 解决什么问题 | 统一 QP 下，文字边缘最容易糊；单纯提码率会浪费在桌面背景 |
| 具体做法 | 采集/编码侧做**块分类**（文字/图形/视频/纯色），对文字块给低 QP（高码质）；启用 SCC 工具：HEVC `palette_mode`/`intra_block_copy`、H.264 `IBC`（若后端支持），AV1 不在本版；桌面背景块提高 QP |
| 预期收益 | 同等码率下文字可读性明显提升（主观评分 +1 档）；或同画质下码率降 15~25% |
| 实现代价 | 块分类需要轻量启发式（边缘密度/颜色数），误分类影响有限；SCC 工具各后端支持不均 |
| 归类 | **v1**（后端不支持 SCC 时保留 QP map，禁用工具部分） |
| 影响模块 / 文档 | `rdc-codec`（`VideoConfig.qp_map`）、`rdc-capture`（块分类元数据）；§06 §3 |

### 2.7 分辨率无缝切换

| 项 | 内容 |
|---|---|
| 解决什么问题 | 降分辨率时重建编码器会导致黑屏 1~3s，操作手感断裂 |
| 具体做法 | 两条路径：① **参数热更新**（NVENC/AMF/QSV 支持 reinit 但保留会话时用 `reconfigure` + 立即刷新）；② **双编码器预切换**（仅当有第二个硬件编码单元时：新编码器在后台就绪 → 切换引用 → 旧实例延迟销毁）；切换期间旧码流继续送到"最后一帧"，新码流从第一帧起为可解码起点 |
| 预期收益 | 切换黑屏从 1~3s 降到 ≤ 200ms（双编码器可到 0 帧黑屏） |
| 实现代价 | 双编码器占双倍硬件单元，移动端与低端 GPU 不可用；接口需支持"并行实例 + 切换栅栏" |
| 归类 | **v1**（双编码器为能力可用时的增强，热更新为兜底） |
| 影响模块 / 文档 | `rdc-codec`、`rdc-core`（质量阶梯）、`rdc-transport`（切换栅栏帧标记）；§06 §7 |

### 2.8 时间层分级编码

| 项 | 内容 |
|---|---|
| 解决什么问题 | 弱网时只能整帧丢，导致画面顿挫；无法"优雅降帧" |
| 具体做法 | 编码 GOP 分 2~3 个时间层（`temporal_id` 0/1/2，60fps → 60/30/15）；包头用 `flags` 高 2 位携带 `temporal_id`；弱网时接收端与发送端协同丢高层（`tid>0` 直接不发），基础层保持；恢复时逐层加回 |
| 预期收益 | 30% 丢包场景下画面仍连续（帧率降到 15~30 但不冻结）；比"直接降分辨率"主观体验更好 |
| 实现代价 | 需编码器支持 temporal layers（NVENC/AMF/VAAPI/QSV 支持；VideoToolbox HEVC 部分支持，H.264 不支持 → 退化为单层）；协议与解码需识别层级 |
| 归类 | **v1**（不支持的后端自动退化为单层，界面标注"当前编码器不支持分层"） |
| 影响模块 / 文档 | `rdc-codec`、`rdc-transport`（包头 flags）、`rdc-core`；§04 §1.1、§06 §8 |

### 2.9 输入事件 8ms 窗口合批

| 项 | 内容 |
|---|---|
| 解决什么问题 | 高频鼠标移动逐条发送会打爆发送队列，且浪费带宽 |
| 具体做法 | 合批窗口**自适应**：LAN（RTT<2ms）窗口 2ms，公网窗口 4~8ms；**仅合并同类连续事件**（鼠标移动合并为最后位置 + 轨迹采样）；点击/按键/滚轮**立即发送，不参与合批** |
| 预期收益 | 输入带宽降 80%+；发送队列不再被移动事件淹没 |
| 实现代价 | 低；但要小心"合批引入延迟"与延迟参考值（LAN 30ms）冲突 |
| 归类 | **v1**（窗口上限 8ms，且按键/点击零延迟） |
| 影响模块 / 文档 | `rdc-input`、`rdc-transport`（插队队列）、Flutter `InputMapper`；§04 §2、§01 §3.5、§08 §4 |

### 2.10 双路径冗余发送（可选）

| 项 | 内容 |
|---|---|
| 解决什么问题 | Wi-Fi 抖动/切换时会话中断 |
| 具体做法 | 设置页开关（默认关）；同一会话同时持两条路径（如 Wi-Fi + 蜂窝），**输入与控制通道双发**，视频按"主路径 + 关键帧冗余"策略；接收端去重（按 `session_id + seq`）。包头 `flags` **bit6 语义写死**：bit6=1 表示"双路径副本"，**只允许出现在关键帧分片与控制/输入包上**，普通 P 帧不置位、不复制；接收端对 bit6=0 的包一律按单路径处理 |
| 预期收益 | 路径切换零中断；弱网丢包显著下降 |
| 实现代价 | 双倍流量（视频全冗余会翻倍，故默认只冗余关键帧与输入）；移动端需绑定蜂窝网络（Android `requestNetwork`，iOS 受限） |
| 归类 | **v1**（桌面完整；移动端仅"输入+控制"冗余，视频冗余不可用，界面标注） |
| 影响模块 / 文档 | `rdc-transport`（多路径）、`rdc-connect`（路径管理）、设置页；§04 §2、§05、§08 §3 |

### 2.11 会话冻结与秒级重连

| 项 | 内容 |
|---|---|
| 解决什么问题 | 掉线即销毁会话 → 重连要重新握手、重启编码器、等 IDR，体验断裂 |
| 具体做法 | 网络断开后会话进入 `Frozen`：保留 `session_id`、密钥、编码协商、解码器、编码器实例（编码器停止产出但保留上下文）；指数退避重连（0.5→15s，8 次上限）；重连成功后只需请求一次刷新（intra-refresh 从此帧起可解） |
| 预期收益 | 断线恢复到出画面从 3~10s 降到 **≤ 1s**（同网络环境） |
| 实现代价 | 资源需在冻结期保留（内存/GPU 上下文），要处理设备热插拔；状态机复杂度上升 |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-core`（会话状态机）、`rdc-transport`、`rdc-codec`；§01 §6、§04 §7 |

### 2.12 诊断 HUD 与画面时间码测量

| 项 | 内容 |
|---|---|
| 解决什么问题 | 没有客观数据，延迟优化只能靠感觉；估算值经不起验收 |
| 具体做法 | ① HUD 实时显示 RTT、丢包、码率、帧率、编/解码耗时、端到端延迟；② **端到端延迟用画面内时间码**：被控端在采集帧上叠加/嵌入不可见时间码（或使用帧内已知图案的元数据），主控端解码后读取该时间码与本地单调时钟比对，得到**管线延迟**（采集帧 → 解码上屏）；③ 统计 P50/P95/P99；④ **HUD 数值统一标注"估计值"**，只作趋势参考 |
| 口径 | **时间码测管线延迟**（不含显示器扫描与光电响应）；**玻璃到玻璃（G2G）用 240fps 高速相机**测量，作为验收仲裁口径；两端时钟偏移用**最小 RTT 估算**（误差 1~5ms），另以相机口径仲裁。**±1 帧 ≠ 16.7ms 固定值**——帧时长随刷新率变化（60Hz 16.7ms / 120Hz 8.3ms / 144Hz 6.9ms） |
| 预期收益 | 时间码把管线延迟的测量误差压到 **±1 帧**（随刷新率变化，非固定 16.7ms）；G2G 以 240fps 相机仲裁；HUD 仅作"估计值"参考；所有验收可复现 |
| 实现代价 | 需要在画面上放时间码（会轻微影响画质，故提供"测量模式"开关：验收时开启，日常关闭）；HUD 需要 4Hz 聚合推送 |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-capture`（时间码叠加）、`rdc-core`（统计）、`app/lib/view/components/stats_overlay`；§01 §5.1、§10 §7 |

### 2.13 CI 性能基准

| 项 | 内容 |
|---|---|
| 解决什么问题 | 延迟/编码耗时回归往往在版本发布后才被发现 |
| 具体做法 | `criterion` 基准：包解析、FEC 编解码、拥塞控制收敛、编码器 mock 吞吐；阈值写入 CI（相对基线劣化 > 15% 失败）；基准结果作为 artifact 归档 |
| 预期收益 | 性能回归在 PR 阶段拦截；基线可追溯 |
| 实现代价 | 需要稳定的 CI 机器（共享 runner 抖动大 → 用相对基线 + 中位数，阈值放宽到 15%） |
| 归类 | **v1** |
| 影响模块 / 文档 | `crates/*/benches`、CI；§10 §7 |

### 2.14 FFmpeg（LGPL）与许可证扫描

| 项 | 内容 |
|---|---|
| 解决什么问题 | 编码/解码兜底需要 FFmpeg，但默认构建可能引入 GPL 组件；依赖许可证失控 |
| 具体做法 | 只在需要软编/软解兜底时链接 FFmpeg，采用 **LGPL 配置**（`--disable-gpl --disable-nonfree`，裁剪到需要的 muxer/parser）；加 `cargo-deny` 检查 Rust 依赖许可证；Dart 侧用 `license_checker`/`pub outdated` 体检 |
| 预期收益 | 合规风险清零；安装包体积减少（裁剪后约 -30MB） |
| 实现代价 | 各平台要自行编译或使用预编译 LGPL 版本（iOS 静态链接需注意 LGPL 动态链接条款 → iOS 上避免直接链接 FFmpeg，改用系统解码器） |
| 归类 | **v1**（iOS 例外：仅用 VideoToolbox，不链 FFmpeg） |
| 影响模块 / 文档 | `rdc-codec`、CI；§06、§10 §7 |

### 2.15 协议版本协商与字段预留

| 项 | 内容 |
|---|---|
| 解决什么问题 | 旧客户端连新服务端会直接失败；字段加不进去只能改协议 |
| 具体做法 | 信封带 `v`（主/次版本）；握手阶段协商 `capabilities`（编码、通道、新特性位图）；未知字段忽略而非报错；包头 `reserved` 保持 0 且预留 `temporal_id` 位；**服务端对旧版本提供兼容路径** |
| 预期收益 | 版本升级不停服；新特性可灰度 |
| 实现代价 | 低（但要一开始就设计，事后补代价高） |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-protocol`、`rdc-signal`；§03、§04 §1.1 |

### 2.16 配对码防爆破

| 项 | 内容 |
|---|---|
| 解决什么问题 | 6 位数字配对码可被暴力枚举 |
| 具体做法 | 失败 3 次锁定 60s（指数退避到 30 分钟）；按 IP 与 peer_id 双维度限速；配对码 120s 失效、一次性使用；服务端记录失败审计；错误响应统一为"配对码无效"（不暴露剩余次数，避免侧信道） |
| 预期收益 | 6 位码爆破从分钟级提升到不可行（每天最多 5 次尝试/来源） |
| 实现代价 | 低（服务端状态机） |
| 归类 | **v1** |
| 影响模块 / 文档 | `rdc-signal`、`rdc-security`；§03 §5 |

## 4. 冲突与取舍结论

| 冲突对 | 冲突点 | 裁决 |
|---|---|---|
| 2.1 光标分离 ↔ 2.6 文字加权 | 两者都靠"画面更干净"提清晰度，但光标分离后光标不在编码帧里，文字加权不受影响 | 无冲突，同时启用 |
| 2.3 intra-refresh ↔ 2.7 分辨率切换 | 切分辨率必须发新 SPS/PPS，天然需要"可解码起点"，与"不发 IDR"矛盾 | **以 intra-refresh 作为统一切换机制**：切分辨率时新 SPS + 立即启动一轮完整刷新（200~500ms 覆盖）；双编码器路径则直接切换新流，不刷新 |
| 2.3 intra-refresh ↔ 2.4 静态识别 | 静止期 GOP 拉长与刷新周期可能"打架" | 统一由 `GopController` 管理：静止期暂停刷新、恢复时先跑一轮完整刷新 |
| 2.7 分辨率切换 ↔ 2.8 时间层 | 切分辨率会让时间层重新对齐，低层帧可能断链 | 切换栅栏：新流从 `temporal_id=0` 起，前 1s 不启用高层 |
| 2.9 输入合批 ↔ 延迟参考值（LAN 30ms、尽力 20ms） | 8ms 合批会吃掉近一半预算 | **合批窗口自适应**：LAN 2ms、公网 ≤8ms；点击/按键/滚轮**永不参与合批**。参考值按"按键到注入"单独测量 |
| 2.10 双路径 ↔ 2.2 pacing / 2.6 码率加权 | 双路径翻倍带宽，与拥塞控制、码率预算冲突 | 默认关；开启时视频仅冗余关键帧，输入/控制双发；预算按"两条路径各自 pacing"，不对同一路径叠加 |
| 2.10 双路径 ↔ 中继配额 | 中继按流量计费，双路径会翻倍成本 | 走中继时**禁止双路径**（UI 置灰并说明原因） |
| 2.6 SCC 工具 ↔ 4:4:4/10-bit | 部分 SCC 工具在 10-bit 4:4:4 下不可用 | 能力协商时按"色深优先、SCC 次之"降级；UI 显示实际启用组合 |
| 2.14 FFmpeg LGPL ↔ iOS | LGPL 动态链接要求与 iOS 静态链接冲突 | iOS 不链 FFmpeg，只用 VideoToolbox；软解缺失时明确报错 |
| 2.8 时间层 ↔ 高刷（120/144fps） | 144fps 下三层分层为 144/72/36，收益有限且编码器负载高 | 默认基础层 + 1 个时间层；用户显式开启"高刷分层"时按 3 层。**不因高刷关闭该能力或截断帧率**，144fps 是否启用仍由能力协商决定 |

## 5. 硬件能力参考基线（不是软件上限）

> 本节只记录"常见硬件实际上限"，作为能力探测的参考；软件侧不为任何组合设置拒绝阈值，探测通过即启用。

| 组合 | 现实约束 | v1 处理 |
|---|---|---|
| 4K60 4:4:4 10-bit | 消费级编码器多数只支持 4:4:4 到 4K30 或 1080p；带宽 80~150Mbps | 协商失败时按降级顺序退（先关 4:4:4，再降分辨率），界面显示"当前 4:2:0 10-bit" |
| 4K120 | 仅 DP2.0/HDMI2.1 + 新一代编码器；多数机器不可行 | **能力协商目标**；探测通过即启用，实际输出以采集端原生刷新率为准 |
| 120/144fps + HEVC 4:4:4 | 编码器吞吐不足，码率需求 > 200Mbps | 降级优先级：高刷优先于色度（自动切 4:2:0），但不关闭高刷能力 |
| 10-bit + H.264 | H.264 High10 支持面窄且很多硬编不支持 | 10-bit 仅在 HEVC 下启用；H.264 回落时强制 8-bit 并提示 |

## 6. 工期影响与关键路径

### 6.1 工期变化

| 阶段 | 原范围 | 扩大后 | 增量来源 |
|---|---|---|---|
| S1 | 空壳 + CI | 空壳 + CI + **基准骨架** + `rdc-runtime` | 2.13、线程基础设施 |
| S2a | 打洞直连（媒体会话协议冻结） | + **协议版本协商** + **配对防爆破** + 会话冻结状态机骨架 | 2.15、2.16、2.11 |
| S2b | 账号服务 + 同账号互信 | + 账号注册/登录、公钥上报、同账号设备列表与吊销 | 账号服务；**多账号授权协议只冻结字段，落地放 S5** |
| S3a | 1080p60 上屏（主流档位 · 正式验收） | + **时间码** + **光标通道** + **intra-refresh** + **时间层** + **解码队列** | 2.12、2.1、2.3、2.8、2.5 |
| S3b | 高规格档位（能力协商 + 实验性） | 4K / 120·144fps / 4:4:4 / 10-bit 逐项探测与实测 | §1 能力协商目标 |
| S4 | 输入注入 | + **合批** + **双路径开关** | 2.9、2.10 |

**结论**：全量相对"朴素 v1 基线"为 **1.8~2.5 倍**；以可审计口径折算为 **核心 40~61 人月、含 QA/发布 52~80 人月**，日历 6 人 10~15 个月 / 4 人 15~22 个月（同 `10-里程碑与验收.md` §1.2，来源 15 号评审 §4）。旧版"增加 35~45%"缺少分母，**不再作为排期依据**。主要增量在 S3a / S3b（协议与编码接口的"一次性设计正确"）。

### 6.2 关键路径（推迟就返工）

| 项 | 为什么不能晚 | 最晚决策点 |
|---|---|---|
| 2.15 版本协商 | 协议信封与握手字段定稿后改动要全端兼容 | **S2a 开始前** |
| 2.12 时间码 | 采集帧元数据与统计口径必须从第一版就有，否则历史数据不可比 | **S3a 开始前** |
| 2.1 光标分离 | 增加 stream id 与采集"排除光标"能力，协议表定稿后再加要改包头/通道表 | **S3a 开始前** |
| 2.3 intra-refresh | 编码器 trait 必须从一开始就有"刷新模式"，否则各后端实现要重写 | **S3a 开始前** |
| 2.8 时间层 | 包头 flags 位分配一旦冻结，后加只能占 reserved | **S3a 开始前** |
| 2.5 解码队列 | 解码线程结构定了再改要重写解码管线 | **S3a 开始前** |
| 2.7 分辨率切换 | 编码器接口需支持"并行实例/热重配"，事后加要重构工厂 | **S3b 开始前** |
| 2.10 双路径 | 传输层 socket/路径抽象事后加成本高 | **S4 开始前** |
| 2.14 许可证 | 依赖选型决定构建方式，返工要重做 CI 与打包 | **S1 期间** |

### 6.3 阶段顺序调整建议

1. **S2 增加"接口冻结"子阶段**（0.5 阶段）：先把协议包头、stream id、编码器 trait、解码队列结构、时间码格式定稿，再写实现。否则 S3a 会边写边改。
2. **S2 拆成 S2a / S2b、S3 拆成 S3a / S3b**：
   - **S2a = 媒体会话协议冻结**：打洞直连 + 版本协商 + 配对防爆破 + 冻结状态机；**S2b = 账号服务与同账号互信**；**多账号授权**（`grant_token` 等）只冻结字段，落地放 S5。
   - **S3a = 主流档位 · 正式验收**：1080p60、H.264 硬编、光标分离、时间码、解码队列；**按档位记录 P99（参考 30ms）与准时率（≥99%），未达参考值不判失败但须填限制来源**。
   - **S3b = 高规格档位 · 能力协商与实验性**：4K、120/144fps、4:4:4、10-bit、intra-refresh、时间层；逐项探测、逐项实测，结果标注"实测值 / 实验性"，**不作为 S3 准入条件**，也不设软件上限。
3. **S4 提前"剪贴板通道"**（与输入同属交互通道，共用加密与限流基础设施）；剪贴板 UI 与平台实现可放 S5。
4. **S5 = 调优 + 多账号授权落地**：QP map、无缝切换、静态识别、HUD 打磨、弱网自适应；多账号授权与权限设置页只在 S5 落地 UI 与流程，**不新增协议结构**（字段已在 S2a / S2b 冻结）。

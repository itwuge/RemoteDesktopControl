# 10 · 里程碑与验收

> 目标：把「能编译」升级为「下载下来装上去能跑」。
> 每个阶段都有**可观察的验收动作**，验收不通过不进入下一阶段；阶段完成或有阻塞立即汇报。

---

## 1. 阶段总览

| 阶段 | 目标 | 核心产出 | 验收方式 |
|---|---|---|---|
| S1 | 全平台空壳可构建出安装包（**构建矩阵，不构成对外支持承诺**） | 仓库骨架（13 crate）+ Cargo/Flutter 工程 + CI 矩阵 + 基准骨架 | Windows/Linux/Android 可安装并启动（Windows 10/11 x64 为 v1 唯一对外支持平台，其余仅构建验证）；macOS 未公证 dmg 右键打开可启动；iOS 仅 xcarchive/源码自签，不要求安装；各端显示版本号 |
| S2 | 信令 + 打洞，两台桌面机 P2P 直连 | `rdc-signal`（信令部分）+ `rdc-connect` + `rdc-cli` + **免密认证** + **协议冻结（媒体会话协议 / 信令信封 / 错误码）** | 两台机器跑 CLI，输出「直连成功 + 路径类型 + RTT」；信任设备免配对码直连；协议三件套冻结入库 |
| S2b | 账号服务与多账号授权 | `rdc-signal` 内账号模块（同一二进制）+ 同账号发现 + 多账号授权协议 | 同账号设备自动互信；离线授权校验通过；账号/授权协议字段定稿 |
| S3a | 采集→编码→传输→解码→上屏主干（**1080p~1440p 60fps 4:2:0**） | `rdc-capture` + `rdc-codec` + `rdc-transport` + 渲染 + **时间码测量** | 按「档位 × 网络 × 平台」记录管线/G2G P99 与 p95（参考基线见 §1.1） |
| S3b | 4K / 高刷 / 4:4:4 / 10-bit（**能力允许 + 实验性**） | 能力探测 + 降档路径 + HUD 标注 | 能力探测正确 + 降档透明 + 不崩（见 §4.1） |
| S4 | 键鼠/触摸注入 + **剪贴板 + 文件传输** | `rdc-input` + 交互通道 | 实际操作被控端；文本双向；文件传完并校验一致 |
| S5 | 画质与延迟调优、码率自适应、**多设备与屏幕墙**、**多账号共享控制与权限设置页** | 质量阶梯 + 中继 + HUD + 设备列表 + 预览墙 + `13-权限设置页设计.md` 的 7 个区块 | 弱网降级不卡死；9 路预览可同时观看；指标可查；授权/接管/吊销全流程可演示 |

**阶段边界**：上一阶段验收项全部通过才开工下一阶段；但**中继开关 UI** 因属于 S1 的设置页骨架，提前放到 S1 的空壳里（仅开关与配置，不建立连接）。

### 1.1 硬件能力参考基线（验收分档记录，不一刀切）

> 口径：**软件侧不设人为上限**——所有档位都可协商、可探测、可降档；能否达到由硬件与网络决定。下表是**参考基线**，验收记录实测值，未达参考值不判失败。

| 档位 | 常见硬件实际上限 | 软件理论能力 | 参考码率区间 | 参考管线 P99 | 参考 G2G P99 |
|---|---|---|---|---|---|
| 1080p60 4:2:0 8-bit | ✅ 消费级全平台（含 macOS VideoToolbox、移动端硬编） | 支持 | 8~20 Mbps | 20~30 ms | 30~40 ms |
| 1080p120 4:2:0 8-bit | ✅ 需 120Hz 屏 + 桌面硬编 | 支持（移动端按机型） | 20~40 Mbps | 22~32 ms | 28~40 ms |
| 1440p60 4:2:0 10-bit | ✅ NVENC / AMF / QSV 多数可用 | 支持 | 30~60 Mbps | 25~35 ms | 35~45 ms |
| 1440p144 | ⚠️ 编码吞吐 + 线材受限，部分硬件可用 | 支持（能力探测） | 60~120 Mbps | 30~45 ms | 40~55 ms |
| 4K60 4:2:0 8/10-bit | ✅ NVENC / 部分 AMF / QSV | 支持 | 40~120 Mbps | 30~45 ms | 40~55 ms |
| 4K60 4:4:4 8-bit | ⚠️ 仅部分 NVIDIA，对端解码不确定 | 支持（能力探测） | 80~180 Mbps | 40~55 ms | 50~65 ms |
| 4K60 4:4:4 10-bit | ❌ 消费级卡多为不可用（待实测确认） | 可协商，不保证可达 | 120~250 Mbps | 45~60 ms | 55~75 ms |
| 4K120 4:2:0 10-bit | ⚠️ 编码吞吐 / 解码 / 线材均紧张 | 可协商，不保证可达 | 150~250 Mbps | 50~70 ms | 60~80 ms |
| 4K120 4:4:4 10-bit | ❌ 无消费级硬件路径（待实测） | 可协商，不保证任何硬件可达 | 300~1500 Mbps | ≥70 ms（待实测） | ≥80 ms（待实测） |

- ✅ 常见硬件实际上限可覆盖；⚠️ 部分硬件可达、需逐设备实测；❌ 常见硬件实际上限不可用。
- "软件理论能力"是协议与实现允许协商到的上限，**不代表任何硬件必然达到**。
- 超出上表的组合（如 4K144 4:4:4、4K240）：协议不阻断，按"能力探测 + 降档"处理，不列入验收档位。
- 标"待实测"的项由 6 周 spike 回填，回填前不作为任何门槛。
- **移动端解码上限**：Android/iOS 的常见硬解上限为 **1080p60 / 4:2:0 / 8-bit**（部分旗舰可 4K60 4:2:0），4:4:4、10-bit、120fps 普遍不可用；实际以 `DecoderCaps` 探测为准，超出能力时不发流、主动降档并显示 `decoder_limit`。

#### 延迟：双口径

| 口径 | 定义 | 参考刻度 | 测量方法 |
|---|---|---|---|
| 管线 P99 | 画面时间码：被控端帧内时间戳 → 主控端解码提交上屏 | LAN 1080p60 **≤30ms（目标线，不放宽）**；同城 ≤45ms；跨省 ≤85ms | 时间码（`04 §6` 估偏移，HUD 标注"估计值"） |
| G2G P99 | 玻璃到玻璃：被控端屏幕像素变化 → 主控端显示器像素变化 | LAN 1080p60 ≤45ms；同城 ≤55ms；跨省 ≤90ms | 240fps 高速相机 |
| 管线 P99（高刷 + 原生视频层） | 120Hz+、零抖动缓冲、绕开 Flutter 合成器 | LAN ≤20ms | **尽力值（best-effort，不作为验收门槛）** |

> 全部刻度均"由硬件与网络决定"，验收按档位记录实测值；样本 **≥10 分钟**，**P99 与 p95 同时报出**。
>
> **例外**：LAN 1080p60 管线 P99 ≤30 ms 是 S7 口径的目标线（不放宽），不是可"记录即通过"的参考值；未达按未达标记录。当前实测（S7-8：pipeline p50 19.47 / p99 34.59，e2e p50 24 / p99 36）与 S7-9 复验条件见 `17-经验与坑.md` §口径裁定 4。

#### 验收方式：分档记录

1. 每个「档位 × 网络场景 × 平台」记录实测 P99 / p95 与"达标 / 未达标"。
2. 未达参考值**不判失败**，但必须写明**限制来源**：硬件编码器 / 对端解码器 / 网络带宽 / 用户偏好 / 策略。
3. 只有下列情况判失败：协商结果与 UI / 码流不一致、崩溃、花屏 >1 帧、黑屏 >200ms、降档后无法恢复。

| 仍为失败判据的项 | 判据 | 方法 |
|---|---|---|
| 协商一致性 | 采集输出、会话协商、解码输出三处分辨率 / 色度 / 位深 / 帧率一致，UI 显示与 SPS 一致 | 断言 + SPS 解析（不一致即失败） |
| 黑屏（切换 / 降级） | ≤ 200ms | 录屏逐帧比对 + 日志 `switch_epoch` 对齐 |
| 花屏 | ≤ 1 帧 | 录屏逐帧比对 |
| 降档可恢复 | 压力解除后回到原档，无需重连 | 长稳 + 日志 |
| 输入延迟 | 按键到注入 ≤ 16ms（LAN 合批 2ms 下） | 240fps 高速相机或注入侧打点 + 时间码画面反馈 |

**测量纪律**：管线延迟**一律来自时间码**、G2G **一律来自 240fps 高速相机**，禁止用"估算 / 抓包时间差"充当验收数据；每次验收必须附带原始 `csv`（每帧一行：`frame_id, capture_ts, encode_ms, send_ts, recv_ts, decode_ms, present_ts, e2e_ms`）。

## 2. S1 · 仓库骨架与 CI

### 2.1 目标与产出

| 产出 | 验收标准 |
|---|---|
| Rust workspace（13 个 crate 空壳，含 `rdc-runtime`） | `cargo check --workspace` 全绿；`cargo clippy` 无 error |
| Flutter 工程（5 平台宿主） | `flutter analyze` 无 error；`flutter build` 各平台成功 |
| FRB 桥接最小闭环 | App 启动调用 `core_version()`，首页显示版本号与平台名 |
| 设置页骨架 | 中继开关（默认关）+ 中继地址 + 三档降级策略 + 方向策略 + 文件带宽上限 |
| 基准骨架 | `cargo bench` 可跑（包解析/FEC/拥塞），基线文件入库 |
| 打包脚本 | `packaging/` 四平台脚本本地可跑通 |
| CI 矩阵 | 6 个 job 全绿（含 `compliance`），Release 产出分平台安装产物 + `NOTICE` / SBOM / 校验和 |

### 2.2 空壳应用的最小可验证行为

启动后必须能观察到（少一条都算 S1 未完成）：

1. 窗口标题为 `RDC`。
2. 首页显示：Rust 核心版本、构建平台、FRB 桥接状态（OK/失败）。
3. 点击「自检」调用 `rdc-cli doctor` 等价逻辑，输出 5 行环境检查结果。
4. 设置页可切换中继开关，**切换时只写配置，不发起任何网络请求**（用抓包确认无中继连接）。
5. 关闭再打开，设置持久化生效。

### 2.3 汇报节点

S1 的 CI 第一次全绿、且任一产物（建议 Windows 安装包）在真机装成功，立即汇报；不等到全平台安装承诺全部验证完。

## 3. S2 · 信令与打洞

### 3.1 可验证产出

| 检查项 | 通过标准 |
|---|---|
| 信令注册 | 两台机器 `register` → `register_ok`，服务端日志可见 peer_id |
| 呼叫/应答 | `call` → `incoming` → `accept`，配对码校验通过 |
| 候选交换 | 双方互换 host / srflx 候选，日志可见候选数量 ≥ 2 |
| IPv6 直连 | 同网段 IPv6 下必走直连，耗时 < 3s |
| UDP 打洞 | 跨 NAT（同运营商不同网络）成功，`rdc-cli` 输出 `path=udp-punch` |
| TCP 打洞 | 强制 `--disable-udp` 时走 TCP 打洞，`path=tcp-punch` |
| 失败码 | 打洞失败返回明确错误码，**不静默切中继** |
| 中继（手动） | 设置页开启中继 + 配置地址后，失败时按策略走中继，`path=relay` |
| 重连 | kill 一端进程后重启，指数退避重连并保留会话 ID |
| 免密登录 | 首次配对后断开重连**不再需要配对码**；挑战-应答验签通过；验签失败拒绝且**不回落到配对码流程** |
| 信任策略 | 三档策略各验证一次；吊销设备后必须重新配对；有效期到期转回"每次确认" |
| 协议冻结 | **仅冻结「媒体会话协议 + 信令信封 + 错误码」**：包头字段、`stream` 表、编码器 trait、时间码格式、版本协商字段（含 `reserved` 与 capabilities 位图）、挑战-应答格式，写入 `crates/rdc-protocol`；账号 / 授权相关字段不在此冻结，随 S2b 定稿 |

### 3.2 CLI Demo 形态（阶段验收的实物）

```
$ rdc-cli pair --server 1.2.3.4:21116
配对码: 482913   (有效期 120s)

$ rdc-cli connect --code 482913
[1/4] 注册成功  peer=ab12…  rtt=18ms
[2/4] 候选交换   host×2  srflx×1
[3/4] IPv6 直连  失败 (no route)
[4/4] UDP 打洞  成功  path=udp-punch  rtt=42ms
会话建立完成，按 Ctrl+C 退出
```

### 3.3 汇报节点

两台**真实不同网络**的机器跑通直连即汇报（不接受同机双进程冒充）。若只在同网段成功、跨 NAT 失败，也立即汇报卡点（附候选与 NAT 类型）。

### 3.4 S2b · 账号服务与多账号授权（从原 S2 移出）

> S2 只冻结「媒体会话协议 + 信令信封 + 错误码」；账号服务、同账号发现、多账号授权协议与离线授权校验移到 S2b，与 S5 的多账号 UI 同阶段验收。

| 检查项 | 通过标准 |
|---|---|
| 账号服务 | `rdc-signal` 同一二进制内提供：注册/登录（Argon2id）、access+refresh token、公钥上报、同账号设备列表（含 `list_version`）；**不存媒体与内容**（表结构可查） |
| 同账号自动互信 | 两台设备登录同一账号 → 各自上报公钥 → 连接时双向验签通过、**无需配对码**；单台改为"每次确认"后恢复确认 |
| 离线可用 | 停掉账号服务后，**已缓存的信任关系与已有直连不受影响**；同账号设备降级为"每次确认"，不阻断连接 |
| 账号边界 | 抓包与库表核对：账号服务收发的字段仅限邮箱/设备名/平台/公钥/在线时间；无画面、文件、剪贴板、连接历史 |
| 多账号授权协议 | `grant_token` / `binding_token` 的字段与签名格式、`call/incoming/accept/reject/kick` 新增字段、`takeover_*`/`role_change` 消息、并发模式枚举定稿（协作仅留枚举位，收到即拒绝） |
| 离线授权校验 | 断网且账号服务停机时，已缓存授权的设备仍被接受；篡改令牌、过期令牌、`revoked_epoch` 命中均被拒绝 |
| 授权协议冻结 | 上述 grant / binding / takeover 字段与签名格式入库，作为 S5 权限页的协议依据 |

**汇报节点**：同账号两设备免配对码互信成功，且账号服务停机不阻断已有连接，即汇报。

## 4. S3a / S3b · 采集与编码与上屏

| 子阶段 | 范围 | 验收性质 |
|---|---|---|
| **S3a** | 1080p~1440p 60fps 4:2:0 为主干 | **正式验收**（按 §1.1 分档记录管线 / G2G P99 与 p95） |
| **S3b** | 4K / 高刷 / 4:4:4 / 10-bit | **能力允许 + 实验性**：能力探测正确 + 降档透明 + 不崩 |

### 4.1 可验证产出

| 检查项 | 通过标准 |
|---|---|
| 采集 | 三桌面平台稳定出帧；`rdc-cli capture --probe` 输出分辨率/格式/帧率；**光标已排除**（帧内无光标） |
| 编码 | HEVC 硬编优先 → H.264 硬编；日志打印实际后端与色度/位深；能力按 **profile + 分辨率 + 帧率 + 码率** 组合探测，不把色度/位深/帧率当独立开关 |
| 传输 | 1080p60 在 LAN 丢包 < 0.5%，无持续 NACK 风暴；分片按微秒间隔铺开（抓包看间隔） |
| 解码上屏 | 画面连续无花屏；LAN 1080p60 管线 P99 与 G2G P99 按 §1.1 分档记录（参考 30 / 45 ms），p95 同时报出 |
| 帧率 | 1080p60 / 1440p60 实际渲染 ≥ 58fps（记录）；4K / 高刷 / 4:4:4 / 10-bit 归 S3b，只做能力探测与降档 |
| **S3b 能力探测** | 协商前探测编码器与解码器的 profile / 色度 / 位深 / 帧率 / 码率上限；不支持时透明降档并在 HUD 标注原因；探测结果与协商结果一致 |
| 在线重配 | 改码率/帧率 2s 内生效；改分辨率黑屏 ≤ 200ms（intra-refresh 起点） |
| 解码队列 | 深度固定 2，覆盖最旧；`decode_overwrite_count` 可观测 |
| 时间码 | 能导出每帧 `csv`，字段齐全（见 §1.1） |

**辅助观测项（记录，不判失败）**

| 观测项 | 参考 | 口径 |

## 7. GitHub Actions 构建矩阵（方案）

> 本节只是**方案**，当前阶段不落地 workflow 文件。落地时按本节逐条实现。

### 7.1 Job 矩阵

| Job | Runner（**固定版本**） | 目标三元组 | 产物 |
|---|---|---|---|
| `build-windows` | `windows-2022` | `x86_64-pc-windows-msvc` | `RDC-Setup-x.y.z.exe`（NSIS） |
| `build-macos` | `macos-14` | `aarch64-apple-darwin` + `x86_64-apple-darwin`（universal） | `RDC-x.y.z.dmg`（ad-hoc 签名） |
| `build-linux` | `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | `RDC-x.y.z-x86_64.AppImage` + `rdc_x.y.z_amd64.deb` |
| `build-android` | `ubuntu-22.04` | `aarch64-linux-android`（+ `armv7-linux-androideabi` 可选） | `RDC-x.y.z-arm64.apk`（固定 keystore 签名） |
| `build-ios` | `macos-14` | `aarch64-apple-ios`（静态库） | `RDC-x.y.z.ipa`（**Apple 开发者证书签名**，可 TestFlight）；未签名 `xcarchive` 仅作 CI 中间产物 |
| `compliance` | `ubuntu-22.04` | — | `NOTICE.txt`、SBOM、`ffmpeg -buildconf` 校验报告 |
| `release` | `ubuntu-22.04` | — | 汇总产物 + `sha256` + `NOTICE/SBOM` + Release 发布 |

**托管 runner 的职责边界**：只做 lint / 单测 / 交叉编译 / 打包 / 合规校验。**GPU 编码、长稳、真实网络、TCC 权限验收不在托管 runner 上执行**，统一放在自建硬件实验室（人、机、弱网仪、240fps 相机），结果以报告入库。

**为什么 Ubuntu 22.04 而不是 latest**：AppImage 依赖较老的 glibc 与 `libfuse2`；用 22.04 可保证在更多发行版上运行（在 24.04 构建会在老系统上报 `GLIBC_2.38 not found`）。

### 7.2 每个 job 的标准步骤（顺序固定）

```
1. checkout
2. 安装 Rust 工具链（rustup，版本取 rust-toolchain.toml，**不使用 stable 浮动**）
3. 恢复 Rust 缓存（Swatinem/rust-cache，key 含 target 三元组）
4. 安装 Flutter（subosito/flutter-action，**锁定稳定版号**）+ 恢复 pub 缓存
5. 安装平台原生依赖（见 §7.4）
6. flutter pub get
7. flutter_rust_bridge_codegen generate
8. `git diff --exit-code`（**FRB 生成一致性**：Rust 侧签名变更必须与 Dart 生成物同 PR）
9. flutter build <platform> --release
10. 打包（packaging/ 下对应脚本；Android 用固定 keystore，iOS 用 Apple 开发者证书）
11. 合规校验：`cargo-deny` / license allow-list / `ffmpeg -buildconf` / NOTICE / SBOM
12. 计算 sha256、上传 artifact
```

### 7.3 缓存策略（决定 CI 时长）

| 缓存 | 键 | 说明 |
|---|---|---|
| Cargo registry | `${{ runner.os }}-cargo-registry-${{ hashFiles('Cargo.lock') }}` | 依赖下载占大头 |
| Cargo target | 含 `target` 三元组 + `Cargo.lock` hash | 跨 job 不复用，避免污染 |
| Flutter SDK | `flutter-<version>-<os>` | 避免每次 1.9GB 下载 |
| pub 缓存 | `pubspec.lock` hash | |
| Gradle | `~/.gradle/caches` | Android 构建加速 |
| CocoaPods / SPM | `~/Library/Caches/CocoaPods` | 若走 SPM 则用 SwiftPM 缓存 |

**目标**：全绿矩阵总墙钟时间 **≤ 90 分钟（缓存命中）**；**冷启动 90~150 分钟属预期**，不承诺 40 分钟。macOS / iOS job 受 Apple 分钟计费限制，按 tag 与每日定时触发，不随每次 push 全量跑。

### 7.4 各平台原生依赖与交叉编译

| 平台 | 必装 | 说明 |
|---|---|---|
| Windows | VS 2022 Build Tools（C++ 工作负载）、NSIS、LLVM（若需 bindgen） | `windows-2022` 已带 VS；NSIS 需 `choco install nsis`；需带 VC++ runtime（或静态 CRT） |
| macOS | Xcode（`macos-14` 预装的**固定版本**）、`create-dmg`、`codesign`（系统自带） | ad-hoc 签名：`codesign --force --deep --sign - RDC.app` |
| Linux | `libfuse2`、`libgtk-3-dev`、`libx11-dev`、`libxcb`、`libdrm-dev`、`libva-dev`、`appimagetool`、`dpkg-deb` | PipeWire 头文件：`libpipewire-0.3-dev`；glibc 基线固定 22.04 |
| Android | JDK 17、Android SDK/NDK（`ndkVersion` **固定**）、`cargo-ndk` | NDK 版本必须与 Flutter 的 `ndkVersion` 对齐，否则链接失败；`applicationId` 固定 |
| iOS | Xcode + `xcodebuild`、Apple 开发者证书与 Provisioning Profile | **正规签名 + 导出**：`flutter build ipa`；未签名 xcarchive 仅作中间产物 |

**版本固定（写入 `.tool-versions` 与 workflow，禁止 latest 浮动）**

| 组件 | 固定值 | 说明 |
|---|---|---|
| windows runner | `windows-2022` | 不用 `windows-latest` |
| macOS runner | `macos-14` | Xcode 版本随镜像固定并记录 |
| Linux runner | `ubuntu-22.04` | glibc 基线 |
| Flutter | `3.x` 具体稳定版号 | 写入 workflow，禁用自动升级 |
| Xcode | 随 `macos-14` 的具体版本 | 记录到 BUILD-INFO |
| Rust | `rust-toolchain.toml` 指定版本 | 各 target 同一版本 |
| Android NDK | `27.x` 具体版本 | 与 Flutter `ndkVersion` 一致 |
| flutter_rust_bridge | 固定版本 | 生成物一致性由 `git diff --exit-code` 保证 |

### 7.5 构建产物清单（Release 页）

```
RDC-Setup-1.0.0.exe            + .sha256
RDC-1.0.0-universal.dmg        + .sha256
RDC-1.0.0-x86_64.AppImage      + .sha256
rdc_1.0.0_amd64.deb            + .sha256
RDC-1.0.0-arm64.apk            + .sha256
RDC-1.0.0.ipa                  + .sha256   （Apple 开发者证书签名，可 TestFlight）

```

> 未签名 `xcarchive` 只作 CI 中间产物，**不进 Release 页**。

### 7.6 签名与密钥策略

| 项 | 方案 | 用户侧表现 / 备注 |
|---|---|---|
| **iOS** | **Apple 开发者证书签名**：`flutter build ipa` 正规签名 + 导出。所需 secrets：`IOS_CERT_P12`(base64)、`IOS_CERT_PASSWORD`、`IOS_PROVISIONING_PROFILE`(base64)、`APPLE_TEAM_ID`；仅上传 TestFlight 时需要 `APPSTORE_API_KEY_ID` / `APPSTORE_API_ISSUER_ID` / `APPSTORE_API_PRIVATE_KEY` | 未签名 `xcarchive` 仅作为 CI 中间产物；无证书时不产出可分发的 ipa |
| **Android** | **固定 keystore**：`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`；**固定 `applicationId`**；禁止 CI 临时 keystore，禁止无 secret 时降级 debug 签名 | 丢失 / 更换后果：签名变更导致**无法覆盖升级**，用户必须**卸载重装（本地数据丢失）**，且**无法上架商店**；轮换须走 Play App Signing 或密钥迁移方案 |
| **macOS** | **ad-hoc 签名**（`codesign -s -`）；不公证 | Gatekeeper 会拦截：**右键 → 打开**，或 `xattr -d com.apple.quarantine /Applications/xxx.app`；**这不是"顺畅安装"**；将来公证需 Developer ID + `notarytool` + Hardened Runtime |
| **Windows** | 无代码签名证书时**不签**，SmartScreen 会警告（需「仍要运行」）；后续接 **OV / EV 证书或云签名**（如 Azure Trusted Signing） | 无警告安装需证书与 CI 集成，成本另计；不影响安装流程本身 |

**禁止**：把任何私钥 / 证书明文写进 workflow；用 `secrets` 注入，且日志脱敏；日志中不得打印 keystore / p12 / API key 内容。

#### 安装包签名与升级覆盖连续性（硬要求）

| 要求 | 说明 |
|---|---|
| 签名身份跨版本稳定 | 同一平台、同一 `applicationId` / `bundleId` 的签名身份必须**跨所有版本保持稳定** |
| 覆盖安装 | 升级包必须能覆盖安装，并**保留用户数据与设备身份密钥**（设备密钥丢失即失去已配对关系） |
| 签名变更 = 破坏性变更 | 必须**主版本号升级** + 发布说明明确告知 + 提供迁移步骤；不得静默变更 |
| 校验入 CI | `compliance` job 校验 keystore / 证书存在性与签名身份指纹，与上一版本比对，不一致即失败 |

### 7.7 CI 稳定性要求

- 缓存未命中时允许时长翻倍，但不得失败。
- 任一步失败必须上传日志 artifact（含 `cargo`、`flutter`、`xcodebuild` 输出尾部 2000 行）。
- 允许 flaky 重试**仅限**下载类步骤（`flutter pub get`、依赖下载），编译失败不允许重试掩盖问题。
- `release` job 只在 tag 推送时触发；PR 只跑构建不发布。

## 8. 风险与卡点（提前登记，避免闷头重试）

| 风险 | 影响 | 应对 | 触发时的处理 |
|---|---|---|---|
| macOS 交叉编译 universal 二进制 | 两个 target 需 `lipo` 合并，FRB 生成物路径可能冲突 | 先用 `aarch64` 单架构出 dmg，universal 作为后续优化 | 若 1 天内打不通，先交付 arm64 dmg 并汇报 |
| Android NDK 与 Flutter 版本不匹配 | `libflutter.so` 与 `librdc.so` ABI 冲突 | 锁定 Flutter 稳定版 + 固定 NDK `27.x` | 汇报具体报错，不盲目升/降版本 |
| Linux AppImage 在 24.04 runner 上构建 | 依赖 glibc 过新，产物在 22.04 上跑不起来 | 固定 `ubuntu-22.04` | 已规避 |
| iOS 签名与 Provisioning | 需要 Apple 账号、证书、Profile；CI 首次配置易失败 | S1 即配置 secrets 并跑通 `flutter build ipa` 签名导出；xcarchive 仅作中间产物 | 证书 / Profile 缺失时汇报，不产出"伪 ipa" |
| Android keystore 丢失 / 变更 | 无法覆盖升级、用户需卸载重装、无法上架商店 | keystore 入 Secrets + 离线备份（双人保管）；固定 `applicationId` | 一旦变更按破坏性变更处理（主版本升级 + 明确告知） |
| HEVC / H.264 专利许可 | 闭源商业分发可能侵权 / 需付费 | 优先硬编规避；商业分发前完成专利尽调与预算（见 §11） | 未完成尽调前不做商业化分发 |
| VideoToolbox 在 CI 无 GPU | 编码器初始化失败 | S1 不做编码，仅空壳；S3 起 CI 只做编译不做运行 | CI 不跑需要 GPU 的集成测试 |
| 中继带宽成本 | 用户误开导致费用 | 默认关 + 开启二次确认 + 实时流量显示 | 已在设计里约束（见 05 文档） |
| 打洞失败率 | 部分对称 NAT 无法直连 | 明确错误码 + 引导手动开中继 | 不静默降级（用户已拍板） |

**汇报纪律**：任一风险触发且 30 分钟内无明确推进路径，立即汇报卡点，附完整报错与已尝试的方案。

## 11. 许可与专利合规

> 发布前闸门：**版权许可（LGPL/GPL）与专利许可（HEVC/H.264 池）分开评估**，缺一不可。

### 11.1 FFmpeg：LGPL 动态链接（硬约束）

| 要求 | 具体做法 | CI 校验 |
|---|---|---|
| 构建参数 | `--disable-gpl --disable-nonfree`；不启用 `--enable-libx264` / `--enable-libx265` | `ffmpeg -buildconf` 实际参数入库并 diff，出现 gpl / nonfree 即失败 |
| 链接方式 | **动态链接**：`.so` / `.dylib` / `.dll` 独立分发 | 检查产物符号与依赖（`ldd` / `otool -L` / `dumpbin`） |
| 用户可替换 | 允许用户替换库文件；随包提供 LGPL-2.1 全文 | 包内 `NOTICE.txt` + `licenses/` |
| 源码提供 | 随包提供源码，或提供书面 offer（写明有效期与获取方式） | `ffmpeg-buildconf.txt` + 源码获取说明 |

**禁止静态链接**：Android 尤其危险——`libavcodec.a` 静态进 `librdc.so` 即不满足"可替换"。要求 `.so` 独立打包或 FFmpeg 跑独立进程；**iOS 不链接 FFmpeg**。

### 11.2 编码器许可边界

| 后端 | 许可 | 允许性 |
|---|---|---|
| NVENC / AMF / QSV / VideoToolbox / VAAPI | 厂商驱动 API（专有 / MIT / 系统框架） | **允许**；优先使用，同时规避软件编码器的 GPL 与专利双重风险 |
| x264 / x265 | GPL-2.0+（或商业双许可） | **禁止**：不得通过任何 feature / 第三方 crate / 打包脚本间接引入；`--disable-gpl` + 产物符号扫描双重校验 |
| `Software` 后端 | — | **明确限定为 OpenH264**；注明 Cisco 专利许可**只覆盖其官方二进制**，自行编译需另行评估专利 |
| HEVC / H.264 专利池 | 专利许可（Access Advance / Via LA / H.264 池） | **版权许可 ≠ 专利许可**；闭源商业分发前必须完成尽调与预算 |

**默认策略**：**优先走硬件编码**（NVENC / AMF / QSV / VideoToolbox / VAAPI），规避软件编码器的 GPL 与专利双重风险；软件编码只保留 OpenH264 作为受限兜底。

**商业分发前置条件**：完成 HEVC / H.264 专利尽调与预算，并准备替代路径（AV1 优先；H.264 仅限特定场景）。

### 11.3 Release 合规产物

| 产物 | 内容 |
|---|---|
| `NOTICE.txt` | LGPL 文本 + Flutter / Dart / Rust / OpenH264 / 打包工具等第三方 NOTICE |
| `sbom.cdx.json` / `sbom.spdx.json` | CycloneDX 与 SPDX 各一份，覆盖直接与传递依赖 |
| `ffmpeg-buildconf.txt` | `ffmpeg -buildconf` 实际参数 + FFmpeg 源码获取说明 |
| `CHECKSUMS.txt` | 全部产物 sha256 |

> 缺任一产物 → `compliance` job 失败，不发布。

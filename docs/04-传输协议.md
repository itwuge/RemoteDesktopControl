# 04 · 传输协议

> 自研 UDP 传输层。目标是"可控的端到端时延 + 清晰的降级依据"，而不是做通用传输协议。
> 中继只做转发，报文格式与加密完全一致。

---

## 1. 报文结构

### 1.1 UDP 包头（32 字节，固定）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `magic0` = `R` | 快速识别 |
| 1 | 1 | `magic1` = `D` | 与信令报文区分（信令以 `{` 开头） |
| 2 | 1 | `version` | 传输协议版本 |
| 3 | 1 | `flags` | bit0 关键帧/可解码起点、bit1 重传、bit2 FEC 校验包、bit3 中继标记、**bit4~5 `temporal_id`（0~3）**、bit6 双路径副本、bit7 保留 |
| 4 | 4 | `session_id` | 会话标识（u32） |
| 8 | 1 | `stream` | 0 视频主码流 / 1 音频（预留）/ 2 输入 / 3 控制 / 4 统计 / **5 剪贴板** / **6 文件** / **7 视频子码流（屏幕墙）** |
| 9 | 1 | `priority` | 0 最高（输入）~ 5 最低（统计）：0 输入 / 1 剪贴板 / 2 控制 / 3 视频 / 4 文件 / 5 统计 |
| 10 | 2 | `payload_len` | 明文载荷长度（不含头部与 AEAD tag） |
| 12 | 4 | `seq` | 该 stream 的单调递增序号（u32，回绕安全） |
| 16 | 8 | `ts_us` | 采集/发送时间戳（微秒，主机单调时钟） |
| 24 | 2 | `fec_group` | FEC 组号（无 FEC 时为 0xFFFF） |
| 26 | 2 | `fec_index` | 组内序号（K 内为数据包，K..K+M 为校验包） |
| 28 | 2 | `frame_id` | 帧号（u16，按帧递增） |
| 30 | 2 | `reserved` | 对齐保留，必须置 0 |

**载荷之后紧接 AEAD tag（16 字节）**。头部整体作为 AAD，因此序号与时间戳不可被篡改；载荷加密保证内容不可读。

### 1.2 分片规则

- 单包总长（含头 + tag）不超过 **1400 字节**，避免 IP 分片；
- **单包明文载荷上限** = `1400 - 32 - 16 = 1352` 字节（本节所称"载荷上限"均指此值）；
- **媒体帧分片**：视频帧的载荷前还要拼 `FragmentHeader`，因此单个媒体分片的**数据**上限 = `1352 - FragmentHeader 长度`。
  - 该长度目前存在两个说法：**8 字节**（本工作树 `crates/rdc-transport/src/reasm.rs:16` 的 `FRAGMENT_HEADER_LEN = 8`，对应分片数据 1344）与 **13 字节**（另一条线实现，对应分片数据 1339）。两者只能有一个对，**状态：待代码核对**，见 `17-经验与坑.md` §口径裁定 1 与待办 T-3。
  - 核对结论落定前，本节不写死具体数值；编码与实现一律以核对后的代码常量为准，不以本文档或 D23 为依据。
- 文件、剪贴板、控制等不拼该分片头的 stream 仍按 1352 字节切片；
- 分片序号与帧号一起用于重组，重组窗口 = 4 帧，超时即整帧丢弃并计入统计。

## 2. 通道划分与优先级

| stream | 内容 | 典型带宽 | 优先级 | 丢包策略 |
|---|---|---|---|---|
| 2 | 输入事件（鼠标/键盘/触摸） | < 50 kbps | **P0**，插队发送 | 不丢弃；必要时重传 1 次 |
| 5 | 剪贴板（文本/图片） | 文本 ≤ 1 MB、图片 ≤ 10 MB/条；瞬时限流 2 MB/s | **P1** | 不可丢；块重传，超时整条重来 |
| 3 | 控制（握手、编码重配、权限位） | < 100 kbps | P2 | 重传直到成功或会话结束 |
| 0 | 视频主码流 | 按档位参考区间（8~1500 Mbps，见 `06-采集与编码.md` §2.8）；不设软件上限 | P3 | 可丢；靠 FEC + NACK |
| 7 | 视频子码流（屏幕墙） | 0.2~0.4 Mbps/路 | P3 | 可丢；长 GOP，不请求关键帧 |
| 1 | 音频（预留） | 64~256 kbps | P3 | 可丢少量，不打乱视频节奏 |
| 6 | 文件传输 | 默认 ≤ 可用带宽 15%，空载可借用至 30% | P4（最低，可暂停） | 不可丢；块重传 3 次 |
| 4 | 统计/心跳 | < 10 kbps | P5 | 可丢 |

**Pacer 规则**

1. 每个 1ms tick 计算可发送字节数（令牌桶，容量 = 2ms 码率）；
2. 输入/控制包**不占用**令牌桶配额，直接发出（上限 200 包/秒，防滥用）；
3. 视频按令牌桶节拍铺开，禁止瞬时突发；
4. 队列长度超过 20ms 的视频数据 → 主动丢最旧的 P 帧并上报拥塞。

### 2.1 剪贴板通道（stream 5）

| 项 | 规则 |
|---|---|
| 独立子密钥 | 由会话主密钥经 HKDF 派生 `k_clipboard`，与其他通道隔离（见 `07-安全设计.md`） |
| 带宽与限流 | 单条 ≤ 10 MB（图片），文本 ≤ 1 MB；独立令牌桶 2 MB/s、突发 512 KB；每秒最多 4 条，超出合并为"最新一条" |
| 不占视频带宽 | 令牌桶独立结算，不从视频码率预算里扣；拥塞时剪贴板降为 P1 但不暂停 |
| 分块 | 载荷 > 64 KB 时按 64 KB 分块，附带整条哈希；任一块失败整条重来（不做部分粘贴） |
| 去重 | 带内容哈希，接收端已存在则只回 ack，不重复落盘 |

### 2.2 文件传输通道（stream 6）

| 项 | 规则 |
|---|---|
| 分块 | **4 MB/块**；块头含 `file_id + block_index + offset + BLAKE3(block)` |
| 校验 | 逐块 BLAKE3；整文件再校验根哈希（块哈希列表的 BLAKE3） |
| 断点续传 | 通过控制通道交换 `manifest`（相对路径、大小、mtime、块数、每块哈希）；恢复时按 `offset` 续传，已确认块跳过 |
| 重传 | 失败块最多重传 **3 次**；仍失败整文件标记失败并给出可续传入口 |
| 带宽上限 | 默认 **≤ 可用带宽 15%**；链路空闲（视频 `send_queue_ms` < 5 且丢包 < 0.5% 持续 3s）可临时借用至 **30%**；用户可调区间 10%~50%；仅使用"探测到的空闲带宽"，不进入视频拥塞控制器的配额计算 |
| 暂停规则 | 视频 `send_queue_ms > 20`、视频码率连续 2s 低于目标 70%、或质量阶梯发生降级 → 文件通道**立即暂停**；恢复需视频稳定 3s |
| 反向影响 | 文件传输**不得触发画面降级**（文件流量不计入视频丢包/延迟统计样本） |
| 中继 | 与直连一致：中继只转发密文；中继模式下带宽上限收紧到票据 `bandwidth_cap` 的 20% |
| 多路会话 | 每路会话独立限额；同一设备多个会话时按"每路 15%"计算，避免合计超载 |

**文件通道状态机**：`Idle → Hashing → Offering（等接收确认）→ Transferring ⇄ Paused → Verifying → Done/Failed/Cancelled`。所有状态迁移只在 `rdc-ctl` 线程内完成。

### 2.3 视频子码流（stream 7）与多路会话

| 项 | 规则 |
|---|---|
| 用途 | 屏幕墙预览：每路 **480p、5~10fps、长 GOP（≤ 10s）、低码率（0.2~0.4 Mbps）** |
| 切换 | 点击进入单屏 → 控制通道发 `switch_to_main`，切换到 stream 0 主码流；退出时切回子码流。**子码流走独立编码实例**，切换不重建解码器（参数变化时才重建） |
| 编码器不足 | 超出 `max_instances` 时**降为 JPEG 快照模式**（快照不算编码流、不占实例），HUD 标注 `wall_snapshot=true`；**禁止"单实例双输出"或抽帧复用同一实例** |
| 带宽预算 | 9 路 3×3 ≈ **1.8~3.6 Mbps**；与主会话共享链路时，屏幕墙总预算上限 = 可用带宽 20% |
| 解码预算 | 墙路数 ≤ `DecoderCaps.max_sessions`；超出降路数或转快照 |
| 会话标识 | 每路用独立 `session_id`，同一连接内按 `stream` 区分主/子码流 |

### 2.4 版本协商、保留字段与能力位图

**目的**：保证旧客户端能连新服务端，且新增通道/字段不需要改包头长度（对应 `11-优化项与优先级.md` #15）。

| 项 | 规则 |
|---|---|
| `version`（包头偏移 2） | 主版本**不变**时向后兼容：新增字段一律走 `reserved` 或扩展 TLV，不重排既有偏移 |
| 版本不兼容 | 主版本差异 → 握手阶段拒绝并返回 `PROTOCOL_VERSION_UNSUPPORTED`，**不静默降级到旧协议**（避免"看起来连上但功能缺失"） |
| `reserved`（偏移 30，2 字节） | 发送方**必须置 0**；接收方**必须忽略**其非零值（为未来语义预留），不得因非零而丢包 |
| 升级路径 | 需要新语义时，先在能力位图里声明，再逐步启用；对端不支持则退回旧行为 |
| 能力位图 | 握手阶段交换 `capabilities`（u64）：bit0 HEVC / bit1 4:4:4 / bit2 10-bit / bit3 intra-refresh / bit4 temporal layers / bit5 QP map+ SCC / bit6 双路径 / bit7 子码流 / bit8 剪贴板 / bit9 文件传输 / **bit10 多会话 / bit11 屏幕墙 / bit12 账号同源互信** / 其余保留 |
| 协商结果 | 只启用**双方都为 1** 的位；结果缓存在会话内，会话中不得翻转为对方未声明的能力 |
| 未知 stream | 收到未协商启用的 `stream` → 整包丢弃并计数 `unknown_stream_drops`，**不报错、不断连**（保证旧端不被新功能打断） |
| 字段预留 | 新增 `flags` 位时先占位声明，未声明前对端按 0 处理 |

**与账号无关的声明（重要）**：

- 端到端加密与版本协商**完全不依赖账号服务**：`capabilities` 的 bit12 只表示"同账号互信可用"，即使账号服务不存在，握手与媒体加密也照常进行。
- 账号 token **不进入** UDP 头部、不参与 AEAD、不参与密钥派生；账号只影响"是否免密直连"，不影响"能否加密通信"。
- 因此：**账号服务故障 → 连接能力不受损，只是少一个免确认的便利**；抓包可见的媒体包与未登录时完全同构。

### 2.5 TCP/TLS 媒体承载（降级路径）

旧版只写"TCP 打洞"而没有定义 TCP 上的媒体协议，是缺口。补齐如下：

| 项 | 规则 |
|---|---|
| 传输层 | **TLS 1.3 over TCP**；证书使用会话临时自签证书，双方用 Ed25519 身份公钥做 pin（`peer_id` 校验），**不依赖账号 CA**，与 UDP 路径同一套身份信任 |
| 复用 | 单条 TLS 连接多路复用，按包头 `stream` 字段分路；TCP 不做 IP 分片，由应用层分片 |
| 帧格式 | 每帧先发 **8 字节帧头**：`frame_id(u16) + shard_count(u16) + total_len(u32)`；随后按 ≤ 4 KB 分片顺序发送；接收端按 `frame_id` 重组，超时整帧丢弃 |
| 队头阻塞 | 无法消除（TCP 有序），只能缓解：输入/控制/剪贴板单独成队并在每个写窗口**优先写**（减小其被视频大包阻塞的时间）；视频允许整帧丢弃，不重传 |
| 拥塞控制 | 沿用 §4 的 GCC，但反馈源改为"TCP 交付速率 + 发送队列占用"；**FEC 关闭**（TCP 自身重传）、**NACK 关闭** |
| 码率 | 该路径目标码率上限 = `min(协商档位, 20 Mbps)`，并计入 §4 的拥塞目标；超出按降级顺序降档 |
| 延迟预期 | 比同条件 UDP 高 20~60ms（重传与队头阻塞），UI 标注 `path=tcp` 与"延迟较高" |
| 启用条件 | 仅当 IPv6 与 UDP 打洞全部失败、且用户允许该路径时启用；用户关闭则直接失败或走中继 |

## 3. FEC 与 NACK

### 3.1 FEC（仅视频通道）

| 项 | 设计 |
|---|---|
| 算法 | GF(256) 上的系统化 Reed-Solomon（K 个数据包 + M 个校验包） |
| 组大小 K | 8 / 16 / 32（默认 16，低延迟优先选小值） |
| 冗余 M | 自适应：2（12.5%）、4（25%）、6（37.5%） |
| 触发 | 丢包率 > 3% 升一档；> 8% 升两档；连续 10s < 1% 降一档 |
| 组边界 | 按帧对齐：一帧跨组时拆成多个组，避免"一帧丢一个包就整帧丢" |
| 代价 | 25% 冗余 ≈ 码率 +25%，必须与拥塞控制联动（总码率含冗余） |

### 3.2 NACK

| 项 | 设计 |
|---|---|
| 触发 | 接收端在重组窗口内发现缺口 |
| 时机 | 立即发（不等超时），每个缺口最多请求 2 次 |
| 抑制 | RTT > 80ms 或丢包 > 15% 时关闭 NACK（重传只会加剧拥塞） |
| 缓存 | 发送端保留最近 **250ms** 的已发包（按码率估算内存，20Mbps ≈ 625KB） |
| 优先级 | 重传包优先级高于新视频数据（flags.bit1 标记） |

**FEC 与 NACK 的关系**：FEC 治突发、NACK 治稀疏；两者同时开启，FEC 负责"不需要等待"的恢复，NACK 负责"FEC 补不回来"的兜底。

## 4. 拥塞控制

采用"延迟梯度为主、丢包为辅"的类 GCC 方案，参数面向远控负载调优。

### 4.1 反馈回路

- 接收端每 20ms 回传一次 `TransportFeedback`：到达序号、到达时间、累计丢包、抖动；
- 发送端计算：
  - `arrival_delta` 与 `send_delta` 的比值 → 排队延迟趋势 `m(i)`；
  - 线性回归估计的过载阈值 `threshold`；超过则判定 overuse；
  - 丢包率按 1s 滑窗统计。

### 4.2 参数表

| 参数 | 默认 | 说明 |
|---|---|---|
| 初始码率 | 局域网 20 Mbps / 公网 6 Mbps | 按 RTT 与首帧探测决定 |
| 最小码率 | 1 Mbps | 低于此值不再降，转降分辨率 |
| 最大码率 | **无软件上限**：由协商档位（`06` §2.8 参考区间）与链路能力决定；LAN 模式由用户设定 |
| 增长 | 每 1s +8%，或探测簇成功后 ×1.5 | 缓慢增，避免震荡 |
| 丢包回退 | 丢包 > 5% → ×0.85；> 10% → ×0.7 | 立即生效 |
| overuse 回退 | ×0.85（每次反馈最多一次） | 防连续踩踏 |
| 探测 | 每 5s 发 1 个探测簇（20ms 内多发 20%） | 快速回收空闲带宽 |
| 滞回 | 回升需连续 5s 稳定 | 避免"降-升-降"抖动 |

### 4.3 LAN 模式

当满足 `RTT < 1ms` 且 `丢包 < 0.1%` 持续 3s：
- 关闭拥塞控制的降码率逻辑，目标码率由用户设定（**不设 200 Mbps 软件上限**，实际可跑到链路与编码器的极限）；
- 仍然保留 pacer 与 FEC 低档，防止交换机瞬时打爆；
- 一旦 RTT > 3ms 或出现丢包，5s 内退回普通模式。

## 5. 传输层线程与缓冲

传输层只在 tokio 多线程 runtime 内运行，**不创建任何 OS 线程**；采集与编码的阻塞调用永远不进入这里。

### 5.1 任务划分

| 任务 | 数量 | 优先级 | 驱动方式 | 职责 |
|---|---|---|---|---|
| `rdc-tx` | 1 | P1 高 | 1ms 定时 tick + 新包到达 | 取环 B / 插队队列 → FEC 编码 → 加密 → pacer 匀速发送 |
| `rdc-rx` | 1 | P2 普通 | socket readable | 收包 → 解密 → 重组 → 抖动缓冲 / NACK 生成 |
| `rdc-fb` | 1 | P3 低 | 20ms 定时 | 回传 `TransportFeedback`（到达序号/时间/丢包/抖动） |
| NACK 定时器 | 1 | P1 高 | 250ms 重传窗口到期 | 清理缓存、重传调度（最多 2 次） |
| 重连任务 | 1 | P2 普通 | 指数退避定时 | 路径重建（见 `05-连接与降级策略.md`） |

**为什么 tx 用 1ms tick 而不是"有包就发"**：有包即发会产生毫秒级突发，正是 bufferbloat 的来源。固定 tick 让发送节奏可预测，也让 pacer 的令牌桶有确定的结算点。

### 5.2 队列与上限

| 队列 | 位置 | 容量 | 满时策略 | 观测字段 |
|---|---|---|---|---|
| 视频发送队列 | `rdc-tx` 内 | 20ms 码率对应字节数 | 丢弃最旧 P 帧，保留 I | `send_queue_ms` |
| 输入插队队列 | `rdc-tx` 内 | 256 个事件 | **不丢弃**；生产者不阻塞（溢出计数） | `input_overflow` |
| 控制消息队列 | `rdc-tx` 内 | 64 条 | 短时阻塞 ≤ 5ms，超时返回 `Busy` | `ctrl_queue_full` |
| NACK 重传缓存 | `rdc-tx` 内 | 最近 250ms 已发包 | 环形覆盖 | 内存 ≈ 625KB @20Mbps |
| 重组窗口 | `rdc-rx` 内 | 4 帧 | 超时整帧丢弃并计数 | `reasm_timeout` |
| 抖动缓冲 | `rdc-rx` 内 | 1~3 帧自适应 | 丢弃超过 deadline 的帧 | `late_frames` / `jitter_ms` |
| 发送端到达反馈窗口 | `rdc-fb` 内 | 固定 1s 滑窗 | 环形覆盖 | `loss_percent` |

**共同规则**：全部有界；**没有一条队列允许无限增长**；任何丢弃必须原子加一，并进入 §9 的观测字段。

### 5.3 与编解码线程的边界

1. `rdc-transport` 从环 B **只取已编码的字节**，永远不碰 GPU 资源与编码器上下文。
2. 环 B 由编码线程写入、`rdc-tx` 读取，**严格 SPSC**；`rdc-tx` 不得回写环 B（重传走自己的缓存，不回灌编码队列）。
3. NACK 触发的关键帧请求（`request_keyframe`）通过控制消息队列转给 `rdc-ctl`，再由它调用编码器——**不在网络任务里直接调用编码器**（避免跨线程调用硬件上下文）。
4. 时间戳只在采集侧生成一次，传输与解码不得改写（保证端到端延迟可测）。

### 5.4 拥塞反馈的线程安全

- `CongestionController` 的状态**只被 `rdc-tx` 单线程读写**；`rdc-rx` 通过无锁队列把反馈样本交给 tx，不直接改控制器状态。
- 码率变更通过原子量 `target_bitrate_atomic` 通知编码线程，编码线程在下一帧编码前读取一次；**不回调、不加锁**。
- 目标码率变化必须限幅：单次调整不超过当前值的 ±20%，避免编码器参数抖动。

## 6. 时钟同步与呈现节奏

1. **发送端时间戳**：`ts_us` 使用主机单调时钟（与墙钟解耦）；
2. **偏移估计**：接收端用"最小 RTT 过滤 + 中位数"估计 `offset = recv_clock - send_clock`，每 5s 更新；
3. **帧到期时间** `deadline = ts_us + offset + jitter_delay`；
4. **呈现**：Flutter 侧按显示器刷新节拍，取 `deadline` 最近的帧；错过则丢弃并计 `late_frames`；
5. **抖动缓冲**：初始 1 帧，按 95 分位抖动自适应（上限 3 帧），稳定 10s 后回落 1 帧。

> 不做"追帧"：宁可丢帧，也不让延迟累积。

## 7. 断线与重连

| 项 | 设计 |
|---|---|
| 掉线判定 | 3s 心跳缺失 / 9s 无任何包 |
| 退避 | 0.5s → 1s → 2s → 4s → 8s → 15s（上限），每次 ±20% 抖动 |
| 上限 | 8 次；超限进入 `Failed` 并提示用户 |
| 会话保留 | 保留 `session_id`、媒体密钥、编码协商结果、权限位 |
| 路径重建 | 重新执行连接阶梯（IPv6 → UDP → TCP）；中继仍需用户已开启 |
| 解码器 | 不销毁；重连后请求关键帧即可恢复 |
| 状态提示 | UI 显示"重连中（第 n 次，x 秒后重试）" |

## 8. 中继路径下的差异

| 项 | 影响 |
|---|---|
| 加密 | 完全不变，中继只转发密文；中继能看到头部元数据（序号、时间戳、大小） |
| RTT | 增加约 `2 × 到中继的距离`；拥塞控制的目标码率自动下调 |
| FEC | 保留（中继丢包与直连丢包不同，按实测调整） |
| 通道优先级 | 中继按 `priority` 字段做队列调度，输入优先 |
| 带宽配额 | 中继票据中的 `bandwidth_cap` 生效，超出即丢包并回传配额告警 |
| 关闭时 | 不建立任何中继 socket / 不发送任何中继报文（不是"发了被拒"，而是根本不连） |

## 9. 观测指标（每个会话持续采集）

| 指标 | 用途 |
|---|---|
| `rtt_ms` / `rtt_p95` | 路径质量、重连判断 |
| `loss_percent` / `burst_len` | FEC 档位与码率回退 |
| `send_queue_ms` | 拥塞判断（> 20ms 即视为排队） |
| `jitter_ms` | 抖动缓冲深度 |
| `late_frames` / `dropped_frames` | 呈现质量 |
| `fec_recovered` / `nack_sent` / `nack_recovered` | 恢复效果 |
| `target_bitrate` / `actual_bitrate` | 码率控制是否跟得上 |
| `path` | `ipv6` / `udp` / `tcp` / `relay` |
| `relay_up_kbps` / `relay_down_kbps` | 中继流量（仅中继路径） |
| `e2e_latency_ms_p50 / p95 / p99` | 端到端延迟，由画面时间码客观测量（见 `10-里程碑与验收.md` §7） |
| `frames_on_time_ratio` | 准时上屏比例；按**档位 × 网络场景**记录，参考达标 ≥ 99%（非一刀切门槛） |
| `decode_overwrite_count` | 解码队列覆盖最旧帧次数（延迟是否在漂移） |
| `clip_sync_count / clip_bytes / clip_skipped` | 剪贴板同步次数、流量、被跳过（敏感格式/超限） |
| `file_throughput_kbps / file_paused_ms / file_retransmit_blocks` | 文件通道吞吐、暂停时长、重传块数 |
| `wall_streams / wall_bitrate_kbps / wall_snapshot` | 屏幕墙路数、总码率、是否降为快照 |
| `encoder_instances / decoder_sessions` | 并发编码/解码实例数（多路会话与屏幕墙资源核对；**不再有"共享实例"标记**） |
| `limit_source` | 当前档位的限制来源：`hw_encoder_limit` / `decoder_limit` / `network_limit` / `user_preference` / `policy_limit` |
| `protocol_version / negotiated_caps` | 协议版本与协商后的能力位图（排查兼容问题） |

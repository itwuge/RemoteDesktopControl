# 16 · 可观测性与诊断规范

> 状态：**待评审**（评审通过后才进入代码改造）
> 分支：`observability`（不得直接改 `master`，不得改 Windows 主线 / Linux 被控端 / Android 客户端正在改的文件）
> 适用范围：全部 Rust crate、`rdc-bridge` FFI 层、Flutter `app/`、Windows runner、打包与 CI
> 关联文档：`01-总体架构`、`02-模块设计`、`09-目录结构与命名规范`、`10-里程碑与验收`、`18-工程铁律`（编号待核对）
> 本文目标：把“出错后靠临时小程序试探”改成“默认有日志、错误有结构、单帧有因果链、环境一条命令可查、违规有门禁”。

---

## 0. 先给结论

1. **日志不是 `println` 的替代品，而是带字段的结构化事件。** 所有运行期代码只允许通过 `tracing` / `rdc-diag` 输出；`println!` / `eprintln!` 只允许出现在 CLI 的“用户可见报告”与 examples/benches，且必须白名单登记。
2. **错误对象必须保留原始来源。** 每层用 `thiserror`；Windows HRESULT / Win32 / AMF / FFmpeg 的数值码与系统文案必须同时保留；跨 FFI 必须带稳定错误码，不能只给一句话。
3. **`frame_id` 是排查一帧的身份证。** 从采集入队开始带 `frame_id`，经过队列、编码、发送、接收、解码、呈现；任何一段丢帧都能落到 `stage + reason`，并与现有 `RDC_FRAME_TRACE=1` 合流为一套输出。
4. **崩溃不静默。** Rust panic hook、Flutter `FlutterError.onError` / `PlatformDispatcher.onError`、日志环形缓冲、Windows engine stderr 重定向与可选 minidump 形成闭环。
5. **`rdc-cli doctor` 是环境台账入口。** 显卡/驱动/WDDM、AMF/NVENC/oneVPL/MFT、显示器开关状态、DDA 可采性、编码后端与回退原因，一条命令输出文本与 JSON。
6. **落盘有硬上限。** 固定目录、JSONL + 人读双份、单文件/总量上限、按天与按大小轮转、保留 7 天；任何日志路径失败都不得阻塞媒体线程。
7. **门禁必须能 fail。** `scripts/gate.ps1` 对 R-C / R-N / R-L / R-T / R-D 五域规则自动判定，支持只查改动文件与 `-Fix`（能自动修的只有 BOM），并有自测样本证明“脚本真的抓得到”。

## 1. 术语、边界与非目标

### 1.1 术语

| 术语 | 含义 |
|---|---|
| 事件（event） | 一条结构化日志记录，至少含 `event`、`level`、`module`、`thread`、`ts` |
| 字段（field） | 事件上的 key=value，例如 `frame_id=1024`、`elapsed_us=8300`、`hresult=0x887A0027` |
| 诊断码（diag code） | 稳定、可检索、可跨 FFI 的错误标识，形如 `RDC-CAP-003` |
| 帧因果链 | 同一 `frame_id` 在 `capture → queue → encode → send → recv → decode → present` 各段的记录 |
| 环形缓冲 | 内存中保留最近 N 条事件的定长队列，崩溃时 dump |
| 台账 | `doctor` 输出的环境事实集合，不是“猜”，而是“查到的值 + 查询失败原因” |

### 1.2 非目标

- 不改变任何协议字段、包头、编码参数、拥塞控制参数、线程数量与关键路径结构。
- 不把日志做成遥测上传；默认只落本机，不联网。
- 不为了“可观测”引入后台常驻线程之外的额外媒体线程；日志写入使用独立低优先级线程。
- 不记录画面像素、剪贴板正文、密钥、配对码、完整令牌。
- 不把 `tracing` 的 `debug/trace` 默认打开；默认只保留生命周期与异常。

### 1.3 行为中性红线

改造过程中，以下内容**禁止**变化：

- `rdc-protocol` 的线格式（`header.rs`、`message.rs`、`envelope`、能力位）。
- `rdc-codec::VideoConfig` 的默认码率/帧率/色度/GOP/低延迟参数。
- `rdc-transport` 的 pacing、FEC、NACK、拥塞控制阈值。
- `rdc-decode` 的解码队列深度、呈现路径与 GPU/CPU 选择。
- 任何 `unsafe` 块的调用顺序与 COM 生命周期。
- 日志关闭时的热路径：不得新增每帧堆分配、锁竞争或系统调用。

## 2. 分层日志

### 2.1 五级语义（强制）

| 级别 | 使用条件 | 默认是否输出 | 典型事件 |
|---|---|---|---|
| `error` | 操作失败且无法在当前层恢复；用户可感知或会话终止 | 是 | 编码器打开失败、DDA `DuplicateOutput` 返回非超时 HRESULT、解码器初始化失败 |
| `warn` | 已降级、已重试、已丢帧，但会话继续 | 是 | AMF 属性设置失败后继续、DDA 失效重建、队列满丢最旧帧、回退到软解 |
| `info` | 生命周期与状态迁移，低频 | 是 | 会话开始/结束、后端选择结果、窗口/显示器拓扑变化、doctor 完成 |
| `debug` | 排障时需要的事件级细节，可能每帧但默认关闭 | 否 | 每次 `DuplicateOutput` 结果、每次编码器属性设置、每帧入队/出队 |
| `trace` | 包级/字段级细节，短时间开启 | 否 | 每包发送/接收、每个分片、每个 NAL/属性值 |

**默认过滤器**：`info`。库 crate 不主动打印 `info` 级“每帧”事件；每帧事件只能是 `debug`/`trace`。

### 2.2 `RDC_LOG` 语法与模块别名

环境变量 `RDC_LOG` 采用 `tracing_subscriber::EnvFilter` 兼容语法：

```text
RDC_LOG=capture=debug,encode=trace,transport=info
RDC_LOG=off
RDC_LOG=rdc_bridge=debug,capture=debug
```

模块别名在 `rdc-diag` 内统一映射，禁止各 crate 自行解释：

| 别名 | 实际 target 前缀 | 覆盖范围 |
|---|---|---|
| `capture` | `rdc_capture` | 采集抽象与平台后端 |
| `encode` / `codec` | `rdc_codec` | 编码器选择、配置、出包 |
| `decode` | `rdc_decode` | 解码、队列、呈现 |
| `transport` / `net` | `rdc_transport` | 分包、FEC、NACK、pacer、UDP |
| `connect` | `rdc_connect` | 候选、打洞、QUIC、信令客户端 |
| `security` | `rdc_security` | 握手、AEAD、票据 |
| `input` | `rdc_input` | 注入、合并、映射 |
| `clipboard` | `rdc_clipboard` | 剪贴板同步 |
| `file` | `rdc_filetransfer` | 文件传输 |
| `core` | `rdc_core` | 会话编排、授权、审计 |
| `bridge` | `rdc_bridge` | FFI 与本地管线 |
| `app` | `rdc_app` / Dart 日志 | Flutter 侧日志门面 |
| `signal` / `relay` | `rdc_signal` / `rdc_relay` | 服务端二进制 |

规则：

1. `RDC_LOG` 只由**进程入口**读取一次；库 crate 不得读取该变量做分支。
2. `RDC_LOG` 为空时使用默认 `info`；`RDC_LOG=off` 时所有 RDC target 关闭，但 panic hook 仍然落盘。
3. 未识别的别名按原样作为 target 前缀使用，不静默丢弃；初始化时用 `warn` 打印一次“未识别别名”。
4. `RDC_FRAME_TRACE=1` 是逐帧埋点的唯一开关，等价于启用 `bridge=debug` + 帧记录写出；不得再引入第二个帧埋点开关。

### 2.3 结构化字段字典（强制）

| 字段 | 类型 | 何时必填 | 说明 |
|---|---|---|---|
| `event` | string | 所有事件 | 点分命名，如 `capture.duplicate.failed`、`codec.attr.set_failed`、`frame.present` |
| `module` | string | 所有事件 | 别名表里的短名，便于人读 |
| `target` | string | 由 formatter 自动填 | `tracing` 的 target（crate/module path） |
| `thread` | string | 所有事件 | `std::thread::current().name()`；token 线程填 `rdc-tokio` |
| `task` | string | 异步任务事件 | 如 `tx`、`rx`、`nack`、`reconnect` |
| `session_id` | u64/string | 会话内事件 | 进程内唯一；不得使用账号、设备名、IP 直接拼接 |
| `frame_id` | u64 | 帧相关事件 | 采集开始递增，贯穿到呈现 |
| `stage` | string | 帧相关事件 | `capture` / `queue` / `encode` / `send` / `recv` / `decode` / `present` |
| `elapsed_us` | u64 | 耗时事件 | 微秒；同段内使用同一单调时钟 |
| `code` | string | 所有 `error` / `warn` 降级事件 | 稳定诊断码，如 `RDC-CAP-003` |
| `hresult` | string | Windows 平台失败 | 十六进制，如 `0x887A0027`；同时带 `system_message` |
| `platform_code` | i64/string | AMF/FFmpeg/Win32 | 原始数值，不得只留文案 |
| `backend` | string | 编解码事件 | `nvenc` / `amf` / `onevpl` / `mft` / `ffmpeg` / `mf-decoder` |
| `reason` | string | 丢帧/回退事件 | 枚举值见 §4.3 |
| `bytes` | u64 | 传输/文件事件 | 本段字节数，不是累计值 |
| `dropped` | u64 | 队列/统计事件 | 本次或窗口内丢帧数，需注明口径 |

错误日志的最小集合：`event` + `code` + `message` + `stage` + `module`；Windows 失败再加 `hresult` + `system_message`。

### 2.4 事件命名

- 使用 `领域.对象.动作_结果`，全部小写，动词过去式或 `failed`：`capture.duplicate.failed`、`codec.configure.ok`、`frame.queue.drop`、`frame.present.ok`。
- 禁止自由文本作为事件名；自由文本只进 `message`。
- 同一事件在不同后端保持一致，后端差异放 `backend` 字段。

### 2.5 输出格式

每进程每会话写两份：

1. **JSONL**：机器读，分析脚本与崩溃 dump 使用。
2. **人读**：同一事件的可读行，便于用户/测试直接看。

人读示例：

```text
2026-11-08 10:21:33.482 WARN  capture  capture.duplicate.no_frame  thread=rdc-capture frame_id=1817 display=0 noframe=306 age_ms=5000 hresult=0x887A0027 system_message="The application did not respond to the request." code=RDC-CAP-006
2026-11-08 10:21:33.501 INFO  codec    codec.backend.selected        thread=rdc-control-encode backend=amf fallback=nvenc:not_found,onevpl:not_found,mft:no_hw_mft
2026-11-08 10:21:33.512 ERROR decode   frame.present.failed          thread=rdc-pipeline frame_id=1817 present_us=1412 hresult=0x80070005 code=RDC-DEC-004
```

JSONL 示例：

```json
{"ts":"2026-11-08T10:21:33.482+08:00","level":"WARN","target":"rdc_capture::platform::windows","module":"capture","event":"capture.duplicate.no_frame","thread":"rdc-capture","frame_id":1817,"display":0,"noframe":306,"age_ms":5000,"hresult":"0x887A0027","system_message":"The application did not respond to the request.","code":"RDC-CAP-006","session_id":7}
```

### 2.6 初始化与依赖

新增 crate `crates/rdc-diag`，层级 L1（纯基础设施，不依赖任何业务 crate），职责：

```text
crates/rdc-diag/src/
├── lib.rs              # init / LogGuard / 再导出
├── filter.rs           # RDC_LOG 别名解析与 EnvFilter 构造
├── record.rs           # 人读 + JSONL formatter，字段规范
├── ring.rs             # 定长环形缓冲（崩溃 dump）
├── panic_hook.rs       # Rust panic hook + 回环 dump + 可选 minidump
├── frame_trace.rs      # FrameRecord / 写出器 / 旧 CSV 兼容
├── error.rs            # DiagCode 常量表、PlatformError、RdcErrorJson
├── redact.rs           # 敏感字段过滤
└── platform/
    └── windows.rs      # HRESULT / Win32 / AMF 数值与系统文案
```

依赖纪律：

- `rdc-diag` 只依赖 `tracing`、`tracing-subscriber`、`tracing-appender`、`serde`、`serde_json`、`thiserror`；Windows 平台辅助用 `windows`（仅 `cfg(windows)`）。
- 所有产生运行期日志的 crate 依赖 `tracing` 或 `rdc-diag`；纯类型 crate（`rdc-protocol`）不强制。
- 只有进程入口（`rdc-cli`、`rdc-bridge` 初始化、`rdc-signal`、`rdc-relay`、Windows runner）调用 `rdc_diag::init()`；库 crate 不得初始化全局 subscriber。

### 2.7 注释与分区样式（沿用项目既定规范）

所有新增/修改文件必须：

1. 文件头注释：`//!` 或 Dart 的 `// =====...`，写清层级、用途、调用方、边界。
2. 函数注释含 `# Arguments`、`# Returns`、`# Errors`（doc comment 会被 IDE 提示）。
3. 关键逻辑逐行注释，尤其是 `unsafe`、错误映射、字段含义。
4. 组件分区使用 `// =====** 组件名 =====**`；控制器/模型对应关系使用 `// =========** 组件名 =========`。
5. 枚举/常量块前写“为什么是这些值”，不要只列值。

### 2.8 性能与零开销

- `tracing` 宏只有在级别启用时才格式化字段；但**字段表达式本身仍会求值**。昂贵字段（如 `format!`、锁、系统 API）必须包在 `enabled!` 守卫内：

```rust
if tracing::enabled!(target: "rdc_capture", tracing::Level::DEBUG) {
    tracing::debug!(event = "capture.detail", frame_id, hresult = %format_hresult(hr), "...");
}
```

- 每帧路径只允许在 `debug`/`trace` 下写日志；`info`/`warn` 必须做速率限制（同一事件 1 秒/5 秒一次，带 `suppressed` 计数）。
- 日志关闭时不新增：每帧 `Arc` 克隆、`Mutex`、`Vec` 分配、系统调用。
- 日志写线程使用有界队列；满时丢日志并计数，禁止反压媒体线程。

## 3. 错误不丢信息

### 3.1 分层 `thiserror`

现状盘点（全部保留并增强，不推倒重来）：

| crate | 错误类型 | 现状 | 必改点 |
|---|---|---|---|
| `rdc-protocol` | `ProtocolError` / `ErrorCode` | 已有 `thiserror` | 增加稳定诊断码方法；线格式不动 |
| `rdc-runtime` | 无统一错误 | 线程创建返回 `io::Error` | 增加 `RuntimeError`（线程/池/令牌） |
| `rdc-security` | `SecurityError` | 已有 | 增加诊断码与 `source`；不泄露密钥 |
| `rdc-connect` | `ConnectError` | 已有 | 打洞/QUIC 错误保留底层来源 |
| `rdc-transport` | `TransportError` | 已有 | IO/协议错误保留数值码与来源 |
| `rdc-capture` | `CaptureError` | 仅 `Internal(String)` | 增加 `Platform`（HRESULT/Win32）与 `NoFrame` 诊断 |
| `rdc-codec` | `CodecError` | 字符串化严重 | 增加 `Platform`（HRESULT/AMF rc），配置失败保留期望/实际 |
| `rdc-decode` | `DecodeError` | 字符串化严重 | 增加 `Platform`；呈现失败带 HRESULT |
| `rdc-input` | `InputError` | 已有 | Win32/XTest 错误保留数值 |
| `rdc-clipboard` | `ClipboardError` | 已有 | Win32 错误保留数值；不记录正文 |
| `rdc-filetransfer` | `FileTransferError` | 已有 | IO 错误保留 `ErrorKind` 与路径哈希 |
| `rdc-core` | `RdcError` | 结构体，字段少 | 增加 `diag_code`、`details`、`platform`、`to_json()` |
| `rdc-bridge` | `Result<T, String>` | **大量丢结构** | 统一改为 `RdcErrorJson`（JSON 文本），Dart 解析为结构 |
| `rdc-signal` / `rdc-relay` | 局部错误枚举 | 已有 | 入口初始化日志；错误码 |

**强制**：每个错误枚举必须提供：

```rust
impl MyError {
    /// 稳定诊断码：新增变体必须追加新码，禁止复用旧码。
    pub fn diag_code(&self) -> &'static str { ... }

    /// 是否允许上层立即重试；决定 UI 是否显示“重试”。
    pub fn retryable(&self) -> bool { ... }

    /// 面向用户的一句话建议；不得包含内部路径、HRESULT 原文。
    pub fn user_hint(&self) -> Option<&'static str> { ... }
}
```

### 3.2 平台错误结构

新增 `rdc_diag::PlatformError`：

```rust
// =====** PlatformError =====**

/// 平台 API 失败事实：数值码、系统文案、调用点。
///
/// 为什么保留原文：HRESULT/Win32/AMF 的系统文案随系统语言变化，
/// 只存文案会导致跨机器不可比对；只存数值又缺少可读性，因此两者都存。
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct PlatformError {
    /// 平台家族：`hresult` / `win32` / `amf` / `ffmpeg` / `x11`。
    pub kind: String,
    /// 原始数值码（HRESULT 用 i32，Win32 用 u32，AMF 用 i32）。
    pub code: i64,
    /// 十六进制表示（如 `0x887A0027`）；无十六进制语义时与十进制相同。
    pub code_hex: String,
    /// `FormatMessageW` / `amf_error_text` / `av_strerror` 的系统或库文案。
    pub system_message: String,
    /// 调用点：`DXGI.DuplicateOutput`、`MFT.SetOutputType`、`AMF.Open`。
    pub operation: String,
}
```

Windows 构造规则：

- HRESULT：`kind="hresult"`，`code` 保留 i32，`code_hex` 用 `format!("0x{:08X}", code as u32)`，`system_message` 用 `FormatMessageW(FORMAT_MESSAGE_FROM_SYSTEM)`；**不得**只 `format!("{err}")`。
- Win32：`kind="win32"`，`code` 用 `GetLastError()`，`code_hex` 用 `0x{:08X}`，`system_message` 用 `FormatMessageW`。
- AMF：`kind="amf"`，`code` 用 shim 返回的 `rc`（不能只取 `error_text()`），`system_message` 取 shim 的 `last_error`。
- FFmpeg：`kind="ffmpeg"`，`code` 用 `AVERROR` 数值，`system_message` 用 `av_strerror`。
- X11：`kind="x11"`，`code` 用 X11 错误码/请求码，`system_message` 用扩展名 + 请求名。

### 3.3 禁止模式（全部由门禁 R-C-2/R-C-3 拦截）

| 禁止写法 | 为什么 | 正确写法 |
|---|---|---|
| `let _ = io_result;` | 丢弃错误，现场消失 | `if let Err(err) = ... { warn!(code=..., ...) }` 或 `?` |
| `result.ok();` | 把 `Err` 变 `None`，无日志 | 显式 `match`，错误路径写 `warn/error` |
| `unwrap_or_default()` 在 IO/编解码/网络路径 | 用空值掩盖失败 | 显式错误分支；只有“确实可空”的 Option 才可用 |
| `anyhow!("...")`（无 `source`） | 抹平层级与数值码 | `#[from]` / `#[source]` + 本层枚举 |
| `map_err(\|_\| ...)` | 丢原始错误 | `map_err(\|e\| MyError::from(e))` 或保留 `source` |
| `format!("{e}")` 处理 HRESULT/Win32 | 只留文案，无 `0x...` 数值 | `PlatformError::from_hresult(operation, e)` |
| FFI 返回 `Err("一句话".into())` | Dart 无法按码分支 | `RdcErrorJson`，含 `code`/`diag_code`/`details` |

### 3.4 跨 FFI 错误载荷

`rdc-bridge` 现有公开函数大量返回 `Result<T, String>`。为了不改 FRB 生成代码的错误类型机制，**保持返回类型为 `String`，但内容改为固定 JSON 文本**（可被 Dart 解析为结构，不是自由文案）：

```json
{
  "v": 1,
  "code": "CodecUnsupported",
  "diag_code": "RDC-COD-001",
  "message": "AMF 打开失败: rc=4 (AMF_RESULT_FAIL)",
  "user_hint": "显卡驱动不支持当前编码配置，请更新驱动或切换后端",
  "retryable": false,
  "details": {"backend": "amf", "stage": "open", "input_mode": "2"},
  "platform": {"kind": "amf", "code": 4, "code_hex": "0x00000004", "system_message": "AMF_RESULT_FAIL", "operation": "AMF.Open"}
}
```

Dart 侧新增 `RdcError.fromJson`，`RustGateway` 捕获异常后先解析；解析失败才退回原始字符串并记录 `RDC-BRG-004`。

**行为中性说明**：这是 FFI 载荷格式变化，不是协议变化；Dart 侧需要同步适配，但调用签名与线程模型不变。若评审要求保留旧字符串，可临时在 JSON 前加 `rdc-error:v1:` 前缀做兼容，但新代码仍按结构解析。

## 4. 一帧的因果链

### 4.1 `frame_id` 生命周期

| 段 | 产生/传递点 | 要求 |
|---|---|---|
| capture | `rdc-capture::platform::windows::capture_loop_dxgi` 的 `frame_id` | 会话内单调递增；GDI/Linux 后端同样维护 |
| queue | `FrameQueue::push` / `QueuedFrame` | 保留 `frame.meta.frame_id` 与 `enqueue_qpc` |
| encode | `FrameTiming` | 新增 `frame_id`、`session_id`；提交时写入 |
| send | `rdc-transport` | 不改协议；用 `(session_id, pts_ns)` 侧表映射到 `frame_id`，映射缺失时标 `frame_id=0` + `reason=no_mapping` |
| recv | `rdc-transport` | 同上，接收侧侧表在解码出帧时消费 |
| decode | `DecodedFrame.ts_us` → `pending_decode` | 以 `pts_ns` 关联回 `FrameTiming`；新增 `frame_id` 字段或侧表 |
| present | `present_gpu` / `present_cpu` | 记录 `frame_id`、`present_us`、结果 |

**不改协议**：不在包头新增 `frame_id`。远程链路的关联是“本进程侧表 + `pts_ns`”最佳努力；本地管线（`rdc-bridge/control_service.rs`）必须 100% 连续。文档与日志中必须如实标注 `frame_id=0, reason=no_mapping`，不得伪造成连续。

### 4.2 `FrameRecord` 结构

```rust
// =====** FrameRecord =====**

/// 一帧在某个阶段的记录；每条记录独立可读，按 frame_id 聚合即因果链。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct FrameRecord {
    /// 会话内唯一。
    pub session_id: u64,
    /// 采集帧号；0 表示未关联。
    pub frame_id: u64,
    /// 阶段：capture/queue/encode/send/recv/decode/present。
    pub stage: String,
    /// 结果：ok/drop/error。
    pub outcome: String,
    /// 丢帧/失败原因；ok 时为空。
    pub reason: String,
    /// 本段耗时（微秒）；入队类记录为 0。
    pub elapsed_us: u64,
    /// 本段开始时的单调时钟（微秒）。
    pub ts_qpc_us: u64,
    /// 可选旁证：包序号、码流字节、后端名。
    pub detail: serde_json::Value,
}
```

### 4.3 阶段与丢帧原因枚举

| 阶段 | reason | 含义 | 判定方法 |
|---|---|---|---|
| capture | `no_frame` | DDA `WAIT_TIMEOUT`，桌面无变化 | `Acquired::NoFrame` |
| capture | `access_lost` | DDA 失效，重建中 | `is_access_lost` |
| capture | `pool_exhausted` | 采集池满 | `add_pool_exhausted` |
| capture | `platform_error` | HRESULT/Win32 失败 | `PlatformError` |
| queue | `queue_full` | 编码队列满，丢最旧 | `FrameQueue::push` 的 `pop_front` |
| queue | `closed` | 会话停止 | `QueuePop::Closed` |
| encode | `submit_failed` | `encoder.push` 返回错误 | `CodecError` |
| encode | `stall` | 200 ms 无包输出 | `STALL_ERROR_US` |
| send | `queue_full` | 发送队列满 | transport drop 计数 |
| send | `socket_error` | UDP 发送失败 | `io::Error` |
| recv | `loss` | 分片丢失且 NACK 未恢复 | 重组丢弃 |
| recv | `late` | 超过 jitter 窗口 | 队列丢弃 |
| decode | `feed_failed` | 送包失败 | `DecodeError` |
| decode | `no_output` | 解码器无输出 | `feed_each` 返回 0 帧 |
| present | `no_texture` | 无可用纹理 | `decoded.texture == None` |
| present | `present_failed` | 呈现 API 失败 | `PresentFailure` |

### 4.4 与 `RDC_FRAME_TRACE` 合流

现状：`crates/rdc-bridge/src/control_service.rs::open_frame_trace()` 在 `RDC_FRAME_TRACE=1` 时写 `frames-detail.csv`；`open_log()` 写 `frames.csv`。**保留文件名作为兼容视图，但实现只留一套**：

- `rdc_diag::frame_trace::FrameTrace` 是唯一写出器。
- 每个 `FrameRecord` 同时产出：
  - JSONL：`frames-<session_id>.jsonl`（主数据，字段完整）。
  - CSV：`frames-detail.csv`（兼容既有分析脚本，列与现有表头一致；新增列追加在末尾）。
- `open_frame_trace()` / `open_log()` 删除或改为薄封装，禁止两套独立文件写入。
- `RDC_FRAME_TRACE=1` 时 `FrameTrace` 启用；日志级别自动提升 `rdc_bridge=debug`，但不把每帧写进人读日志（人读只写异常与每秒汇总）。

### 4.5 一帧丢失的判定配方

| 问题 | 查询 |
|---|---|
| 这一帧丢在采集？ | 查 `frame_id=1817`，若只有 `capture` 或没有 `queue` 记录，看 `capture` 的 `reason`/`hresult` |
| 丢在队列？ | `queue` 记录 `outcome=drop, reason=queue_full`；对比 `enqueue` 与 `dequeue` 的 `ts_qpc_us` |
| 丢在编码？ | `encode` 记录 `reason=submit_failed/stall`，附 `CodecError` 诊断码 |
| 丢在网络？ | `send` 有记录、`recv` 无记录：查 transport 的 `seq`/`loss`/`nack` 汇总 |
| 丢在解码？ | `recv` 有、`decode` 无：查 `feed_failed` 或 `no_output` |
| 丢在呈现？ | `decode` 有、`present` 无或 `present_failed`：查 HRESULT |

### 4.6 现有埋点迁移点

| 文件/符号 | 现状 | 改造 |
|---|---|---|
| `control_service.rs::open_frame_trace` | 独立 CSV | 改为 `rdc_diag::frame_trace` 薄封装 |
| `control_service.rs::open_log` | 独立 `frames.csv` | 由 `FrameTrace` 汇总写出 |
| `control_service.rs::FrameTiming` | 无 `frame_id` | 增加 `frame_id`/`session_id` |
| `control_service.rs::run_pipeline` | 每段计时已有 | 每段结束时写 `FrameRecord`（`RDC_FRAME_TRACE` 才写） |
| `rdc-capture::platform::windows::capture_loop_dxgi` | `eprintln!` 5s 诊断 | 改为 `warn!`，带 `noframe`、`last_hresult`、`last_frame_age_ms` |
| `rdc-transport::reasm` / `jitter` | 丢弃计数 | 增加 `reason` 与 `frame_id` 侧表 |

## 5. 崩溃不静默

### 5.1 Rust panic hook

必须安装（`rdc_diag::init` 内）：

- 记录：`thread`、`panic message`、`location`（文件:行）、`Backtrace::force_capture()`、最近 N 条环形缓冲。
- 落盘：`crash/panic-<ts>-<pid>.log`，包含人读 header + JSONL ring dump。
- 调用链：先写文件，再调用 `previous_hook`，保证 `panic=abort` 前完成 flush。
- 防死锁：hook 内不获取全局日志写线程锁；ring 使用独立 `Mutex`，写文件用 `OpenOptions::append` + `sync_all`。
- `spawn_named` 用 `catch_unwind` 包住线程体，捕获后写 `ThreadPanic` 与线程名，转为统计计数；不得让 panic 静默结束线程。

### 5.2 日志环形缓冲

- 默认容量：4096 条 / 2 MiB，先到者为准；可用 `RDC_LOG_RING` 覆盖（如 `RDC_LOG_RING=8192`）。
- 内容：`info` 及以上事件；`debug`/`trace` 不进入 ring，避免冲掉关键上下文。
- 线程安全：单 `Mutex<VecDeque<RingEntry>>`，写入 O(1)；满时丢最旧并计数。
- dump 时机：Rust panic、Flutter fatal、Windows native crash（若启用 dump）。
- dump 文件同样受总量上限约束，保留最近 3 份 / 30 天。

### 5.3 Flutter 侧

`app/lib/main.dart` 启动时必须安装：

```dart
// =====** 全局错误捕获 =====**

// 1) Framework 错误（build/layout/paint）
FlutterError.onError = (FlutterErrorDetails details) {
  FlutterError.presentError(details);
  RdcLogger.error('flutter', 'framework_error', error: details.exception, stackTrace: details.stack);
  RdcLogger.dumpRing('flutter_framework_error');
};

// 2) Engine/平台错误（白色屏幕常见来源）
PlatformDispatcher.instance.onError = (Object error, StackTrace stack) {
  RdcLogger.error('flutter', 'platform_error', error: error, stackTrace: stack);
  RdcLogger.dumpRing('flutter_platform_error');
  return true;
};

// 3) 异步未捕获错误
runZonedGuarded(() { runApp(...); }, (error, stack) {
  RdcLogger.error('flutter', 'zone_error', error: error, stackTrace: stack);
  RdcLogger.dumpRing('flutter_zone_error');
});
```

补充：

- 首帧看门狗：`runApp` 后 5 秒内无首帧，写 `error`（含 `RDC_RENDERER`、GPU 名、`startup.log` 路径），不能只白屏。
- Dart 日志同样五级（`trace/debug/info/warn/error`），字段 `module`、`event`、`code`、`frame_id`；默认 `info`，`RDC_LOG` 过滤。
- Dart 日志通过新增 FFI `rdc_log_event(level, tag, event, message, code, frame_id)` 写入同一 JSONL；FFI 不可用时写本地 `dart-errors.log`，不得静默丢弃。

### 5.4 Windows runner

现状：`app/windows/runner/main.cpp` 只在有控制台/调试器时 `AttachConsole`；release 下 engine stderr 无处可去，白屏时“一句错都没有”。

改造：

1. `AppendStartupLog` 保持并扩展：记录 `renderer`、`gpu`、`remote_session`、`exe_path`、`build_version`。
2. 无控制台时，把 `stdout` / `stderr` 重定向到 `%LOCALAPPDATA%\RDC\logs\engine-<pid>.log`；退出时 flush。
3. 安装 `SetUnhandledExceptionFilter`：仅在 `RDC_CRASH_DUMP=1` 时写 minidump；否则至少写 `native-crash-<ts>.log`（异常码、模块、线程）。
4. `RDC_RENDERER` 选择结果必须落 startup.log；若 `impeller` 被选且首帧超时，自动记录并建议 `RDC_RENDERER=skia`，不自动切换（避免行为变化）。

### 5.5 Windows 本地崩溃 dump 结论

**结论：默认关闭，显式 `RDC_CRASH_DUMP=1` 才启用本地 minidump。**

理由：

- minidump 可能包含屏幕像素、剪贴板/文件内容、密钥材料，默认开启有隐私风险。
- 单个 normal dump 可达数百 MB，与本规范“不得塞满用户盘”冲突。
- 文本 panic + ring dump + engine stderr 已覆盖绝大多数 Rust/Flutter 问题；native 崩溃（D3D 驱动、engine）需要 dump 时才让用户主动开启。

启用时：

- 使用 `MiniDumpWriteDump`，类型 `MiniDumpNormal | MiniDumpWithThreadInfo`，不写全内存。
- 路径：`%LOCALAPPDATA%\RDC\logs\crash\`，每进程最多 1 个，保留最近 3 个 / 30 天。
- `doctor` 输出 `crash_dump=enabled/disabled` 与 dump 目录。

### 5.6 符号

- Release 构建当前 `strip = "symbols"`；为保留可读回溯，CI 在打包时额外归档 `.pdb`（Windows）与未 strip 的符号文件到 `dist/symbols/`，**不装进用户安装包**。
- `panic` 文本仍能给出地址；符号归档用于离线 `llvm-symbolizer` / `cdb` 还原。
- 若评审认为符号归档增加交付复杂度，可先只保留 `Backtrace` 文本并记录 `build_id`，后续再补符号。

| 硬件编码器 AMF | `amfrt64.dll` + `AMFInit` + 编码器 ID 枚举 | `rdc-codec/src/platform/windows/amf.rs::probe_caps` | `rc` + `error_text` |
| NVENC | `nvEncodeAPI64.dll` + `NvEncodeAPIGetMaxSupportedVersion` + session 探测 | `rdc-codec/src/platform/windows/nvenc.rs`（新增/现有） | DLL 缺失/版本/rc |
| oneVPL | `libvpl.dll` / `vpl.dll` + `MFXLoad` + `MFXCreateSession` | `rdc-codec/src/platform/windows/onevpl.rs`（新增） | 库缺失/版本/rc |
| MFT | `MFTEnumEx(MFT_CATEGORY_VIDEO_ENCODER, MFT_ENUM_FLAG_HARDWARE)` + 友好名 + `GetAttributes` | `rdc-codec/src/platform/windows/mf.rs::probe` | 无硬件 MFT/枚举 HRESULT |
| 显示器开关状态 | `EnumDisplayDevices` + `DISPLAY_DEVICE_ATTACHED_TO_DESKTOP`/`ACTIVE` + `QueryDisplayConfig` | `rdc-capture/src/platform/windows.rs::probe_displays` | 每屏 `attached/active` + HRESULT |
| DDA 可采 | `IDXGIOutput1::DuplicateOutput`（每输出一次，立即 Release） | `rdc-capture/src/platform/windows.rs::probe_dda` | 每输出 `dda_ok` + `dda_error` |
| 编码后端顺序与回退 | `rdc-codec::backend::select` 的探测结果 | `rdc-core::doctor` 聚合 | `order` / `selected` / `fallback_reason` |
| 日志/崩溃配置 | `rdc_diag::config_snapshot()` | `rdc-core::doctor` | 目录、ring、dump 状态 |

### 6.4 与现有 `doctor_report`

- `rdc-core::doctor::run_doctor()` 保留前 5 条基础检查（版本、平台、协议、运行时、FFI），**追加**新检查，不改原有顺序，避免 Flutter 首页布局变化。
- `rdc-bridge::doctor_report()` 继续返回 `Vec<String>`，但每行带诊断码；新增 `doctor_json()` 返回 JSON 文本供 UI 复制。
- `rdc-cli doctor` 是唯一同时输出文本 + JSON 的入口；Flutter 首页只展示摘要，不直接做平台探测。

### 6.5 反面例子如何被台账覆盖

| 踩过的坑 | 台账字段 | 防再犯 |
|---|---|---|
| `frames=0 noframe=306` 无 HRESULT | `displays[].dda_error` / `dda.duplicate_hresult` | 每次 `DuplicateOutput` 失败都保留 HRESULT + 系统文案 |
| Flutter 白屏、engine stderr 无错 | `logs.engine` / `startup.log` / 首帧看门狗 | runner 重定向 stderr；5 秒无首帧写 error |
| AMF `rc=4` 被当成成功 | `encoders.available[].platform.code` | 属性设置后立即校验 `rc`，失败即 `warn/error` |
| `CODECAPI_AVLowLatencyMode` VT 类型错误被拒无人察觉 | `encoders.available[].detail` + 配置日志 | 设置前记录期望 `VT_UI4`，设置后校验 HRESULT，失败保留数值 |

## 7. 落盘纪律

### 7.1 固定目录

| 平台 | 根目录 | 说明 |
|---|---|---|
| Windows | `%LOCALAPPDATA%\RDC\logs` | 不用 `%APPDATA%`（漫游目录不应放日志）；`startup.log` 迁到此 |
| Linux | `$XDG_STATE_HOME/rdc/logs`，缺省 `~/.local/state/rdc/logs` | 不用仓库内 `logs/` |
| macOS | `~/Library/Logs/RDC` | 系统日志惯例 |
| Android | 应用私有 `files/logs` | 不写外部存储 |
| 开发/测试 | `RDC_LOG_DIR` 覆盖 | 默认不落到仓库 `target/` 或系统盘 |

`RDC_CONTROL_LOG_DIR` 保留为兼容别名，读取时写一条 `warn` 提示迁移到 `RDC_LOG_DIR`。

目录树：

```text
<LOG_ROOT>/
├── rdc-<service>-<YYYYMMDD>-<pid>.jsonl      # 主结构化日志
├── rdc-<service>-<YYYYMMDD>-<pid>.log        # 人读日志
├── frames-<session_id>.jsonl                 # 逐帧 JSONL（RDC_FRAME_TRACE=1）
├── frames-detail.csv                         # 逐帧 CSV 兼容视图
├── doctor-<YYYYMMDD-HHMMSS>.json              # 环境台账
├── engine-<pid>.log                          # Windows runner 的 engine stderr/stdout
├── dart-errors.log                           # FFI 不可用时的 Dart 兜底
├── panic-<YYYYMMDD-HHMMSS>-<pid>.log          # Rust panic + ring dump
└── crash/
    ├── native-<YYYYMMDD-HHMMSS>-<pid>.log     # 无 minidump 时的异常摘要
    └── rdc-<pid>-<ts>.dmp                    # RDC_CRASH_DUMP=1 时的 minidump
```

### 7.2 上限与轮转

| 类别 | 单文件上限 | 总量上限 | 轮转 | 保留 |
|---|---|---|---|---|
| JSONL / 人读 | 16 MiB | 256 MiB | 按天 + 按大小 | 7 天 / 10 个会话 |
| 逐帧 JSONL / CSV | 64 MiB | 128 MiB | 每次会话新文件 | 3 天 / 2 个会话 |
| panic / native 日志 | 8 MiB | 32 MiB | 每次崩溃新文件 | 3 份 / 30 天 |
| minidump | 每个 1 个 | 3 个 / 300 MiB | 每进程一次 | 3 份 / 30 天 |
| doctor JSON | 1 MiB | 64 MiB | 每次运行 | 30 份 / 30 天 |

- 超限时先删最旧；删除失败则停止新增并写一条 `warn`（不能无限重试）。
- 启动时执行一次清理；长会话每小时检查一次。
- 日志写入失败（磁盘满、权限）→ 降级为仅 ring + stderr，并在 UI/doctor 显示 `logs.degraded=true`；**不得 panic、不得阻塞媒体线程**。

### 7.3 敏感字段

禁止记录：

- 密钥、私钥、配对码、令牌、`Authorization`、完整 ticket。
- 剪贴板正文；只记录长度与 SHA-256 前 8 位。
- 文件内容；只记录大小、分片数、SHA-256 前 8 位、路径哈希。
- 画面像素、缩略图、OCR 文本。
- 完整对端 IP 默认打码（`192.168.*.*` → `192.168.x.x`）；`--verbose` 才保留完整地址。

`rdc_diag::redact` 提供统一函数；新增字段必须过一遍 `SENSITIVE_KEYS` 列表，否则 code review 直接拒。

## 8. 强制门禁（R-C / R-N / R-L / R-T / R-D）

> 本节是硬约束，不是建议。`scripts/gate.ps1` 命中即非零退出；CI job 必须阻断合并。
> 规则编号采用跨项目经验库的五个域：R-C 代码规范、R-N 注释规范、R-L 调试日志规范、R-T 团队规范、R-D 指挥规范。
> 本仓库的 `gate.config.json` 通过 `ruleIds` 做“语义键 → 编号”映射；经验库编号若变化，只改配置，不改判定逻辑。

### 8.1 编号、可移植性与配置

门禁脚本不是本仓库专用工具，而是可复制到任何新项目的模板：

| 项 | 约定 |
|---|---|
| 脚本本体 | `scripts/gate.ps1`，不写死任何项目路径、crate 名、模块名、白名单 |
| 外部配置 | 仓库根 `gate.config.json`（可选）；启动时按 `-ConfigFile` → `<root>/gate.config.json` → `<root>/tools/gate.config.json` 查找 |
| 无配置运行 | 使用内置中性默认值，并逐行打印默认假设（扫描范围、crate 目录、日志依赖、磁盘阈值） |
| 模板副本 | `tools/gate-template/`：脚本 + 配置样例 + 使用说明；内容中立，不含本项目专有信息 |
| 跨项目副本 | `C:\Users\Administrator\Desktop\工程经验库\门禁模板\`（只写该目录，不改经验库其他文档） |
| 规则编号 | 以经验库《铁律》为准；`ruleIds` 可重映射，冲突时经验库优先并记录到 §8.8 |
| 分模块运行 | `-Changed` / `-Paths` / `-Rules`，只查改动文件也能跑 |
| 自动修复 | `-Fix` 仅补 UTF-8 BOM；语义修复必须人工 |
| 退出码 | `0` 无违规；`1` 有违规；`2` 脚本错误或自测失败 |

### 8.3 各规则判定细节

#### R-C-2 吞错误

命中模式（排除注释、字符串内、`#[cfg(test)]` 后代码）：

```text
let _ = <expr>;
<expr>.ok();
<expr>.unwrap_or_default();      // 仅在 IO/编解码/网络 crate
```

白名单（脚本内显式登记，输出“已豁免 N 条”）：

| 路径/模式 | 理由 |
|---|---|
| `crates/rdc-runtime/src/pool.rs` 的 `Drop` | 归还缓冲失败不影响进程正确性，且已在统计中计数 |
| `crates/rdc-runtime/src/thread.rs` 的 `let _ = ...` | 线程优先级设置失败已降级并记录 |
| `crates/rdc-cli/**` | CLI 面向用户的退出码/输出，不把诊断当业务错误 |
| `examples/**`、`benches/**`、`tests/**`、`build.rs` | 非产品运行路径 |
| 行内注释 `// gate-allow R-C-2: <reason>` | 必须在 PR 中说明理由，评审可拒绝 |

#### R-C-3 错误无上下文

命中模式：

```text
anyhow!(...)
map_err(|_| ...)
format!("{e}") / format!("{}", e) 且文件位于 src/platform/** 或 crates/rdc-bridge/**
<windows error>.to_string() 且未同时出现 .code() / 0x 格式化
```

白名单：

| 路径/模式 | 理由 |
|---|---|
| `rdc-cli` 的最终错误展示 | 只用于终端一句话，同时已写 tracing |
| 纯 UTF-8/JSON 解析错误且上游已保留 `serde_json::Error` | 已有 source，不重复包装 |

#### R-C-5 无界队列/通道

命中模式：

```text
unbounded
VecDeque::new() 赋给字段名含 queue/pending/backlog/reasm/jitter/history
Vec::new() 赋给字段名含 queue/buffer/backlog，且不是 with_capacity
```

允许：

- `Vec::new()` 用于非流式局部集合（需 `// gate-allow R-C-5: local-only`）。
- `VecDeque::with_capacity(n)` 且 `n` 有常量上限。
- 流式队列字段声明在同一行注明上限，如 `queue: VecDeque<T>, // capacity: 8`；运行期仍须在 push 处强制截断（满时丢最旧并计数/告警），注释本身不构成实现。

#### R-C-14 版本号一致性

读取并比对：

1. 根 `Cargo.toml` 的 `[workspace.package] version`。
2. `app/pubspec.yaml` 的 `version:` 主版本（`0.1.0+1` → `0.1.0`）。
3. `packaging/windows/rdc_installer.nsi` 的 `!ifndef VERSION` 回退值。
4. `packaging/**/BUILD_INFO.txt` 中的 `version=`（若存在）。
5. `dist/**` 安装包文件名 `RDC-<version>-...`：仅 `-Build`（出包）时检查。`dist/` 是本机未跟踪产物，普通扫描/CI 报告任务不应把历史残留包计入基线。
6. 版本递增：以 `-BaseRef`（默认 `master`）为基线；若本次变更含 `team.sourceGlobs` 覆盖的源码且版本未变，判违规（改配置/文档/脚本不触发）。`-SkipVersionBump` 仅用于纯文档提交，CI 不允许。

输出示例：

```text
RDC-0.1.0-windows-x64-setup.exe: R-C-14 安装包版本 0.1.0 与 Cargo.toml 0.2.0 不一致
packaging/windows/rdc_installer.nsi:13: R-C-14 NSIS 回退版本 0.1.0 与 Cargo.toml 0.2.0 不一致
```

#### R-C-1 BOM

- 读取字节；若存在 `0xEF 0xBB 0xBF` 则跳过。
- 解码为 UTF-8 后，若含 `[^\x00-\x7F]` 且无 BOM → 违规。
- `-Fix`：在文件头写入 UTF-8 BOM，保留原字节；修复后重新检查并输出“已修复 N 个文件”。
- 必须覆盖中文注释、中文 UI 字符串、任意 `.cpp/.h`。

#### R-C-15 构建落盘

- 目标目录解析顺序：`-TargetDir` 参数 → `$env:CARGO_TARGET_DIR` → `$Root\target`。
- 若目标目录所在盘符等于 `$env:SystemDrive`（Windows）→ 违规；非 Windows 检查是否为根分区。
- `-Build` 时读取目标盘可用空间；低于 `-MinFreeGB`（默认 10）→ 违规并阻止构建。
- 当前仓库若已存在 `C:\...\target` 且未设置 `CARGO_TARGET_DIR`，同样判违规（历史产物也占系统盘）。
- 推荐命令：

```powershell
$env:CARGO_TARGET_DIR = 'E:\rdc-target-obs'
```

#### R-N-1 文件头注释

- 在文件前 `note.headerScanLines`（默认 25）行内查找 `note.headerRegex`。
- 头注释至少说明：文件用途、所属层级、被谁调用/边界。
- Dart/C++ 同样适用；`app/lib/src/rust/**` 等生成代码由配置排除。

#### R-N-2 公开函数文档

- Rust：`pub fn` / `pub async fn` 上方必须紧邻 `///` 注释。
- `note.requireParamSections=true` 时，带参数的公开函数还必须包含 `# Arguments` / `# Parameters` / `# 参数` 段。
- 豁免：`#[cfg(test)]`、生成代码、`examples/**`。

#### R-N-4 组件分区标记

- 仅对 `note.uiGlobs`（默认 `view/`、`widget/`、`page/`、`component/`）匹配的视图文件生效。
- 文件行数 ≥ `note.minLinesForSection`（默认 200）时，必须至少有一个组件分区标记：`// =====** 组件名 =====**` 或 `# =====** 组件名 =====**`。
- 标记中的名字命中 `note.placeholderNames`（如 `组件名`、`Component`、`TODO`）→ 违规。

#### R-N-5 控制分区标记

- 仅对 `note.controlGlobs`（默认 `controller/`、`model/`）匹配的控制层文件生效。
- 文件行数 ≥ `note.minLinesForControlMarker`（默认 400）时，还必须至少有一个控制分区标记：`// =========** 组件名 =========`。
- 控制分区用于 controller/model 等长文件，避免“只有组件分区、没有控制分区”。

#### R-N-7 注释与代码同批更新

**仅人工。** 机器只能确认“有没有标记”，不能确认“标记是否还描述当前代码”。评审检查：新增/删除模块时是否同步增删分区；分区标题是否仍准确。

#### R-L-1 日志旁路

- Rust：`println!` / `eprintln!` / `print!` / `eprint!`。
- Dart：`print(` / `debugPrint(` / `debugPrintStack(`。
- C++：`std::cout` / `std::cerr` / `printf(` / `fprintf(` / `OutputDebugString`。
- 诊断日志必须走统一日志层（`tracing` / `rdc-diag`）。

白名单（配置 `logging.allowedPrintGlobs` 与 `whitelist`，每条必须写理由）：

| 路径 | 理由 |
|---|---|
| `crates/rdc-cli/**` | 面向用户的命令输出，不是诊断日志 |
| `crates/rdc-codec/shim/**`、`crates/rdc-decode/shim/**` | spike/shim 工具把测量结果打到 stdout |
| `crates/rdc-linux-e2e/src/bin/**` | 一次性回环验证二进制，不是产品路径 |
| `examples/**`、`benches/**`、`tests/**`、`build.rs` | 非产品运行路径 |
| `app/windows/runner/**` 的启动日志 | 在 Flutter/engine 初始化之前，无统一层可用 |

#### R-L-4 统一日志接入

- `crates/*/Cargo.toml` 必须依赖 `rust.requiredLogDeps`（默认 `tracing`）。
- 新建 crate 未接入统一日志层 → 违规。
- 纯类型 crate（`rust.pureCrates`）可豁免，但必须在配置里登记理由。

#### R-L-9 只打日志不返回错误

- `if let Err(e) = ... { tracing::warn!(...); }` 且分支结束后继续执行、没有 `return Err(...)` / `?` / `bail!` → 违规。
- 允许：显式降级且有注释说明；此时用 `// gate-allow R-L-9: <reason>`。

#### R-T-2 合并冲突

- 扫描 `team.sourceGlobs`，命中 `<<<<<<<` / `=======` / `>>>>>>>` 即违规。
- 必须在提交前解决，不允许“先合并、后修复”。

#### R-T-4 改动记录

- 仅在 `-Changed` 模式且配置了 `team.changeRecordGlobs` 时生效。
- 有源码改动但没有任何记录文件变更 → 违规。
- 本项目已拍板为硬约束：记录文件为 `docs/20-变更记录.md`，不填即违规，见 §8.11。
- 未配置记录文件的新项目输出“not configured”，不判失败（保持模板中立）。

#### R-T-8 同文件多线修改

**仅人工。** 机器无法可靠判断“同一文件是否被两条线改”。由 worktree/分支归属登记表 + 负责人人工核对；发现冲突以编排规则处理，不靠脚本。

#### R-D-9 版本号递增

- 以 `-BaseRef`（默认 `master`）为基线，比较 `version.cargoManifest` 的版本。
- 本次变更包含非文档/非脚本文件且版本未变 → 违规。
- `-SkipVersionBump` 仅用于纯文档提交，CI 不允许。

#### R-D-9 冒烟记录

- 仅在 `-Build` 模式检查。
- `command.smokeRecordGlobs` 下必须存在至少一份冒烟记录；否则阻止打包/发布。

#### R-T-5 里程碑上报

**仅人工。** 按约定在里程碑节点向负责人报告：文档完成、crate 改造完成、`doctor` 可用、需要拍板的取舍。脚本不判定“是否报告了”。

### 8.5 分模块运行

- `-Changed`：`git diff --name-only <BaseRef>...HEAD` + 工作区未提交改动；只对改动文件跑文件级规则（R-C-2/R-C-3/R-C-5/R-C-1/R-N-*、R-L-1/R-L-9、R-T-2）；R-T-4 与 R-D-9 版本递增按“改动集合”判定；R-L-4 只检查被改动触及的 crate。
- `-Paths`：同 `-Changed`，作用域限定为给定路径。
- `-SkipGlobal`：跳过仓库级/环境级规则（R-C-14 跨文件一致性、R-C-15 构建落盘、R-D-9 冒烟记录）；**不跳过 R-T-4 与 R-L-4**，因为它们判定的是“本次改动”而不是存量。
- 全量（无 `-Changed`/`-Paths`）：文件级 + 仓库级规则全部执行，并触发基线“只降不升”判定。
- `-Rules R-C-2,R-L-1`：只跑指定规则，便于分模块验证。
- R-C-14 版本递增依赖 git 基线；无 git 或 `-SkipVersionBump` 时只做一致性检查。
- R-C-15 始终检查，因为它决定构建落盘；`-Build` 额外检查可用空间。
- R-D-9 版本递增在 `-Changed`/全量下比较基线分支；R-D-9 冒烟记录只在 `-Build` 下检查。

### 8.7 基线治理：只许降不许升

1. **主门禁只卡改动文件**：CI `gate-changed` 跑 `-Changed -SkipGlobal`，改动引入的新违规立即失败。
2. **全量报告不阻塞合并**：CI `gate-baseline-report` 跑全量，输出 `logs/gate-baseline-<ts>.txt` 作为 artifact；存量红以 `continue-on-error: true` 处理，不因存量阻塞合并。
3. **快照入库**：`logs/gate-baseline.json`（以及历史 `logs/gate-baseline-*.txt`）进入 git；配置项 `baseline.allowedCount` 记录“当前基线数”（当前为 442）。
4. **只许降不许升**：全量运行时，若当前违规总数 > `baseline.allowedCount`，或 > 上一次快照的 `total`，输出 `GATE-B` 违规并 `exit 1`。存量可以慢慢还，但不许继续欠。
5. **更新流程**：`-UpdateBaseline` 写快照前先做同样的“不得上升”比较，超标即拒绝；写出成功后提示把 `baseline.allowedCount` 手动改成新值（只允许等于或更低）。
6. **存量豁免不等于允许新增**：禁止为了让门禁变绿而：
   - 把规则改成 warning 或关掉；
   - 给业务代码加无理由 `// gate-allow`；
   - 删除断言/测试；
   - 把日志改成空实现；
   - 把 `allowedCount` 往上改。
   允许的“绿”只来自：真实修复、脚本自身误报修正（需附误报理由与回归样本）。

## 10. 验证方案与判据

### 10.1 每 crate 的固定门禁

```powershell
$env:CARGO_TARGET_DIR = 'E:\rdc-target-obs'
cargo build -p <crate>
cargo clippy -p <crate> --all-targets -- -D warnings
cargo test -p <crate>
```

- 任一失败不得进入下一个 crate。
- `rdc-cli`、`rdc-bridge` 额外跑 Windows 冒烟。
- 每轮结束删除 `E:\rdc-target-obs\debug\incremental` 与临时测试产物，报告释放量。

### 10.2 功能判据

| 编号 | 判据 | 方法 |
|---|---|---|
| OBS-1 | 默认日志 10 分钟空闲 < 1 MiB；无逐帧刷屏 | 启动 app 静置 10 分钟，统计文件大小 |
| OBS-2 | `RDC_LOG=capture=debug` 只提升 capture，其它模块仍 info | 运行并检查 JSONL 的 `module` 分布 |
| OBS-3 | `RDC_LOG=off` 时无 RDC 日志，但 panic 仍落盘 | 关闭后触发测试 panic（子进程） |
| OBS-4 | 任意错误日志都有 `code`；Windows 失败都有 `hresult` + `system_message` | 脚本扫描 JSONL 字段 |
| OBS-5 | 一帧从 capture 到 present 可按 `frame_id` 聚合；丢帧有 `stage + reason` | `RDC_FRAME_TRACE=1` 跑 30 秒，脚本聚合 |
| OBS-6 | `RDC_FRAME_TRACE=1` 只产生一套逐帧文件（JSONL + 兼容 CSV），无第二套 | 检查目录 |
| OBS-7 | Rust panic 产生 `panic-*.log` 且含线程名/回溯/最近 N 行 | 子进程测试 |
| OBS-8 | Flutter 白屏样本产生 `engine-*.log` 或首帧看门狗 error | 强制 `RDC_RENDERER=impeller` 复现 |
| OBS-9 | `doctor --json` schema v1 可解析；每项失败带 code | `ConvertFrom-Json` + 字段断言 |
| OBS-10 | DDA 失败必带 HRESULT；AMF rc 失败必带数值 | 构造/真实失败样本 |
| OBS-11 | 日志总量超限时删最旧，不超上限 | 生成 300 MiB 假日志后运行清理 |
| OBS-12 | 日志目录不可写时 app 仍启动，doctor 显示降级 | 只读目录/磁盘满模拟 |
| OBS-13 | 日志关闭时热路径无可测量开销（< 1% 差异） | `cargo bench` 基线对比 |
| OBS-14 | `gate.ps1 -SelfTest` 每条规则都命中并 exit 0；构造违规时 exit 1 | 脚本自测 |

## D1 Windows 插件符号链接 / Flutter 插件方案

- **问题**：本机未开启 Windows 开发者模式（无管理员权限），`flutter pub get` 无法为
  path 插件创建符号链接，因此无法使用 flutter_rust_bridge 官方 `integrate` 生成的
  `rust_builder` 插件（cargokit）。
- **可选方案**：
  1. 开启 Windows 开发者模式（需管理员权限），恢复 cargokit 插件方案；
  2. 维持当前方案：不引入插件，由 CMake 钩子与打包脚本显式构建/复制动态库。
- **影响**：方案 1 开发体验最好，但需要系统设置变更；方案 2 已在 S1 打通，跨平台布局需
  各平台脚本分别维护（Windows/Linux CMake 钩子，macOS/iOS/Android 打包脚本）。
- **建议**：长期采用方案 1（官方插件），短期保留方案 2 保证 CI 与本地均可构建。
- **临时处理**：方案 2，已通过 `cargo build` + `flutter build windows` 验证。
- **是否阻塞**：不阻塞 S1；S2 起如引入第三方 Flutter 插件（托盘、剪贴板）会遇到同一限制。

## D18 S3a 编码 p99 未达标（实测 18.3ms vs 门槛 8ms）

- **结论**：AMD `AMDh264Encoder` 单会话 1080p 端到端编码时延约 21ms，MF 异步 MFT 的
  `NeedInput` 只在上一帧输出被取走后才下发，因此单会话下 push 调用被串行化。
- **实测**：p50/p99 由 20.1/29.4ms 优化到 13.9/18.3ms（NV12 转换查表 + 4 路并行、
  输出改为下一次 push 非阻塞取回），仍高于 8ms 门槛。
- **临时处理**：如实上报差距，不下调门槛。
- **建议**：S3b 评估「多编码会话轮转」或 GPU 侧 NV12 转换，以把 push 成本压到
  「转换 + 提交」的 3ms 量级；另需确认多会话硬件并发能力。
- **是否阻塞**：阻塞 S3a 编码门槛验收，不阻塞采集（掉帧率 0.000%）。

## D19 码率与码控不收敛（实测 15.4Mbps vs 目标 8.0Mbps）

- **结论**：`CODECAPI_AVEncCommonRateControlMode` 设 CBR(1) 后实测只有 0.096Mbps
  （几乎不发数据），设回驱动默认（0）则实测 8~15Mbps 且随时延波动。
  S3c-C3 追加：`AVEncCommonMaxBitRate`(目标×1.25)、`AVEncCommonMeanBitRate`(目标)、
  `AVEncCommonQualityVsSpeed` 均 `SetValue` 成功，但 s3b3 实测仍 15.04~15.96Mbps
  （+88.0~+99.4%）；同一份码控在 s3b4 链路里因 pacer 限速才恰好 8.13Mbps。
- **临时处理**：保留驱动默认，避免出现「码率塌陷」；码率目标在报告中如实标注未达成。
- **建议**：S5 改用质量档 + 上限约束（PeakConstrainedVBR），或按链路预算动态调整。
- **是否阻塞**：不阻塞 S3a 功能链路，阻塞带宽预算验收。

## D20 采集帧率上限受显示器刷新率约束（实测 57.9fps vs 60）

- **结论**：DXGI Desktop Duplication 只在桌面更新时出帧，本机显示器为 1920x1080@59Hz，
  物理上无法产出 60 帧/秒；`AcquireNextFrame` 超时 53 次，均记为「无更新」而非丢帧。
- **临时处理**：掉帧率口径按「交付帧 / 期望帧」计算，实测 0.000%（门槛 <1%）。
- **建议**：验收环境改用 60Hz 及以上显示器，或在报告中同时给出「按显示器刷新率的达成率」。
- **是否阻塞**：不阻塞掉帧率门槛，但影响「1080p60」这一字面口径的证明力。

## D22 MF MP4 直通封装对时间戳的要求

- **结论**：MPEG-4 文件 sink 要求 H.264 为 Annex-B（3/4 字节起始码），且必须显式
  `BeginWriting()`，否则首个 `WriteSample` 返回 `MF_E_INVALIDREQUEST`。
- **临时处理**：已按 Annex-B 透传并补 `BeginWriting`；样本时长按相邻 PTS 差值给出。
- **建议**：S3b 传输层若改为 fMP4，需重新确认时间戳基数（避免出现 10000000/177353 这类
  由稀疏 PTS 推导出的异常帧率声明）。
- **是否阻塞**：不阻塞（解码验证 563 帧全部解出、0 失败）。

## D23 媒体分片头属载荷层扩展，未进冻结包头

- **结论**：`rdc-transport::FragmentHeader`（8 字节：shard_index/shard_count/total_len）拼在
  载荷最前面，包头固定 32 字节没有它的字段；单包载荷因此只能用 `1352 - 8 = 1344` 字节。
- **临时处理**：`s3b4` 按 1344 切分，`Reassembler` 按同一约定解析。
- **建议**：S5 前评估是否把分片信息并入包头（会破坏冻结格式），或正式写入协议文档的载荷层章节。
- **是否阻塞**：不阻塞。

- **是否阻塞**：阻塞跨机验收，不阻塞同机 S3b 验收。

## D26 解码输出走系统内存 NV12，未接 DXVA 直出纹理

- **结论**：`MfH264Decoder` 输出 `DecodedFrame{data: Vec<u8>, stride}`，每帧 CPU 侧
  Map/Unmap + 上传到 D3D11 纹理；未设置 `MFT_MESSAGE_SET_D3D_MANAGER`，因此拿不到 DXVA 纹理。
- **临时处理**：`present_nv12` 用 STAGING 纹理 + `CopyResource` + `VideoProcessorBlt` 上屏，
  实测呈现 p50 3.0 ms / p99 16.5 ms（1080p）。
- **建议**：接入 `ID3D11VideoDevice` 的 decoder 管理器，让解码器直接出 NV12 纹理，省掉 CPU 往返。
- **是否阻塞**：不阻塞功能，阻塞 1080p60 性能。

## D29 端到端固定积压：in-box 解码器 17 帧管线（≈550 ms）

- **结论**：S3c 复测 e2e p50 551,447 us / p99 556,368 us（71 样本），`in_flight` 峰值与
  稳态均为 17 帧；按宿主 33.4 ms/帧计算 17 帧 ≈ 568 ms，与实测延迟吻合。

- **建议**：后续评估 ①自管输出样本 + 只保留最新（已做，但输入侧仍会被解码器吃满 17 帧）；
  ②改用硬件解码 MFT（本机不存在）；③接受 17 帧下限并据此重估 E1 门槛（须用户裁决，本轮不调）。

## D30 编码吞吐与分段耗时

- **结论（S3c-C3 实测，1080p / AMDh264Encoder / 目标 8 Mbps）**：
  - 分段：`build` 5.5→4.0 ms（其中 alloc 0.03 ms、CPU RGBA→NV12 4.0 ms），
    `wait`(NeedInput) 6.3~9.7 ms、`drain` 3~113 us、`ProcessInput` 1.5~1.7 ms。
  - push p50/p99：单实例 13.95/16.87 ms，双实例 14.32/18.01 ms（C2 末 16.8/20.5 ms）。
  - 关闭节拍取证：单帧仍 16.5 ms（≈60.6 fps），即 1080p 下编码器自身就是上限；
    60 fps 节拍跑 300 帧用 5.57 s（53.8 fps）属「编码器占满一个帧周期 + IDR 抖动」。
  - 链路 fps 的另一道闸：host 侧 pacer 按 8 Mbps 限速，而编码器实际产 15.96 Mbps
    （34 KB/帧），故 `s3b4` 宿主只跑到 29.6 fps、码率恰好 8.13 Mbps。
  - `s3b4` 控制端：接收 298 帧（24.74 fps），但 `presented=71`（12.04 s → 5.9 fps 上屏）。
    原因见 D29——解码器成批吐 4 帧，latest-wins 每批只上屏 1 帧（dropped_latest=210）。
    即 E2 同时被「输入 30 fps」与「成批 latest-wins」两道闸压低。
- **临时处理**：如实上报；未调门槛。
- **建议**：①编码零拷贝（采集纹理直接作 NV12 输入 + VideoProcessor 做 RGBA→NV12，
  见 D31）；②码控收敛（D19）后才能把 pacer 目标与编码器实际码率解耦。
- **是否阻塞**：阻塞 E2（≥56.05 fps）与 D18（push p99 ≤8 ms）。

## D31 编码零拷贝未落地（GPU NV12 转换 + 纹理输入）

- **结论**：当前编码输入仍是 CPU RGBA → CPU NV12（4.0 ms/帧）→ `MFCreateMemoryBuffer`
  + `Lock` 写入。AMDh264Encoder 走 `MFT_ENUM_FLAG_HARDWARE` 且接受 D3D11，理论上可
  用 `MFCreateDXGIDeviceManager` + `MFT_MESSAGE_SET_D3D_MANAGER` + `IMFDXGIBuffer`
  纹理输入，把转换交给 `ID3D11VideoProcessor::VideoProcessorBlt`。
- **为什么本轮未做**：①编码器与呈现/解码共用设备需要跨 crate 传 `ID3D11Device`；
  ②`rdc-codec` 的 `push` 只接受 CPU 池化缓冲，改成纹理输入要动 `VideoEncoder` 接口与
  三个调用方（s3a/s3b3/s3b4）；③即便零拷贝，单帧仍受 16.5 ms 编码器上限约束，
  收益只在 CPU 占用与 push p50（4 ms）。
- **建议**：S5 随采集侧 GPU 化一并做（采集纹理直接进编码器，中间不再回读）。
- **是否阻塞**：不阻塞功能，阻塞 push p99 ≤8 ms 目标。

## D32 码率仍不可控：MF_MT_AVG_BITRATE + CBR/PCVBR 全部无效（S3d-D4）

- **结论（S3d-D4 实测，`s3b3 --secs 5`，1080p60，目标 8 Mbps）**：
  - 驱动默认 + 输出类型 `MF_MT_AVG_BITRATE=8 Mbps` + `MeanBitRate`(VT_UI4)
    + `MaxBitRate`：实测 15.58~15.97 Mbps（+95%~+100%），属性被忽略。
  - `CODECAPI_AVEncCommonRateControlMode=CBR(1)`：0.08 Mbps；`PCVBR(2)`：0.08 Mbps。
    两个模式 SetValue 均返回成功，但输出塌成「只剩头」——驱动接受了模式却没接目标码率。
  - 调整下发顺序（先 Mean/Max 后 Mode）结果不变。
- **临时处理**：维持驱动默认码控；**发送预算改为跟随实测码率（S3d-D1）**，
  不再为凑 8 Mbps 牺牲帧率。16 Mbps 在回环可接受，真机部署需按带宽另议。
- **建议**：①换 AMD AMF 原生（AMF_VIDEO_ENCODER_RATE_CONTROL_METHOD）而不是 MF 包装；
  ②或接受「编码器不改码率、由发送侧按实测值整形」并把 8 Mbps 从配置语义里移除。
- **是否阻塞**：不阻塞 E1/E2；阻塞「8 Mbps 目标码率」这条产品约束。

## D33 解码器 17 帧下限已定性；替换（FFmpeg）评估数据不足

- **结论（S3d-D2 受控实验，`s3b4 exp`）**：
  - 连续送入：首次输出在送入第 11 帧后（墙钟 41.9 ms），峰值/末态 in_flight=10；
    119 帧送完仍余 10 帧在管线内。
  - 严格串行（送一帧等一帧）：首帧要等到第 18 帧、只出 4 帧，第 19 帧起 MFT 永久
    `MF_E_NOTACCEPTING`——这个解码器**不支持一进一出**。
  - 自有队列：端到端链路里首次拿到输出时 in_flight=10，我们从不预填 17 帧。
  - 即：17 帧（≈283 ms@60fps）是 in-box 解码器的 DPB/流水，不是我们的缓冲策略；
    改我们的队列消不掉。
- **替换评估（S3d-D3 spike，独立目录，未入主干）**：FFmpeg LGPL/d3d11va 在
  1080p60 8 Mbps 码流上，单线程软解 4.3 ms/帧、无 B 帧重排、默认多线程有 (N-1) 帧延迟；
  hwaccel 路径因 CLI 回读更慢。但「首帧输出延迟」没有进程内实测，
  **e2e 能否到 30 ms 数量级：数据不足，不确定**。
- **建议**：S5 先做 200 行进程内 FFmpeg spike（avcodec 逐帧计时 + d3d11va + 不回读），
  达标再换实现。代价：+60~300 MB 运行期 DLL、MSVC import lib、LGPL 动态链接合规。
- **是否阻塞**：阻塞 E1（p99 ≤30 ms）——只要继续用 in-box MFT 解码器。


## D34 FFmpeg 解码已进程内实测：软解达标在望，但判据口径含一帧固定偏移

- **S3e-E1 实测**（`rdc-cli s3b4 --secs 10`，1080p60 / UDP 回环 / 59Hz，600~601 样本）：
  - FFmpeg 软解（1 线程、`AV_CODEC_FLAG_LOW_DELAY`、bf=0）：e2e p50 30.4 ms / p99 37~46 ms，
    上屏 60.1 fps（102% × 59Hz），首帧输出在第 1 个 AU 后（5.8~8.7 ms），delay=0、in_flight=0，
    解码 1.7~2.0 ms/帧、NV12 整理 0.4 ms/帧，进程 CPU 26~29% 单核。
  - MF 同会话基线：p50 295.8 ms / p99 333.4 ms，上屏 58.5 fps；首帧要等 10 帧流水。
  - 结论：换解码器把 e2e 从 ~330 ms 降到 ~37 ms（8.8×），但**按现行判据仍 FAIL**（1.24~1.53×）。
- **卡点分解（p50，数据来自 e2e-samples.csv）**：传输（采集→完整 AU）8.1 ms /
  解码+整理 2.4 ms / 上屏 2.3 ms / **回读固定偏移 16.7 ms**。
  最后一项不是解码器：host 把 `ProcessOutput` 拿到的码流与「当前」采集时间戳配对，
  回读内容稳定落后 1 帧（600/600 样本一致，16.6~16.8 ms），e2e 口径因此系统性多算一帧。
  剔除该固定量后的物理 p99 ≈ 20.6~29.1 ms。
- **待裁决**：是否修 host 的输出/时间戳配对（会同时改变所有历史基线），
  或在判据里把该固定量单列。未修之前不把 FFmpeg 设为默认（MF 仍是默认与回退）。
- **FFmpeg d3d11va（零拷贝直出纹理）**：解码 0.86 ms/帧、无 NV12 整理，但每 10 s 内会出
  数次 ~900 ms 的 e2e 尖峰（p99 921 ms，两次复现，软解无此现象）；`extra_hw_frames=8`
  无效。需定位（表面池/驱动同步/输入视图缓存）后才能作为默认硬解路径。
- **依赖体积**：LGPL 共享构建 avcodec-63.dll 92 MB + avutil + swresample（合计 ~95 MB）。
  可自建 `--disable-everything --enable-decoder=h264 --enable-parser=h264` 精简到个位数 MB，
  属打包决策。许可证：LGPLv3 动态链接，随包需附 LICENSE.txt 与源码获取方式；
  构建脚本目前只把 DLL 与许可证拷到本机 target 目录，正式打包尚未接入。
- **是否阻塞**：阻塞 E1（p99 ≤30 ms）的最终判定；不阻塞「解码器可切换」能力（已落地，
  `RDC_DECODER=mf|ffmpeg`，FFmpeg 需 `--features ffmpeg` + `FFMPEG_DIR`）。

## D35 S3f 配对 bug 已修：那 16.7 ms 不在 e2e 里，两条路按原判据仍不达标

- **根因**：host 每轮 `push` 后立刻 `poll`，in-box 编码器下一次 `poll` 吐的是**上一帧**的包，
  但发送时用的 `captured_us` 是本轮刚送入那帧的采集时刻 → 包头时间戳比画面内容超前一帧。
  **e2e 公式本身没被污染**：`e2e_us` 用回读的 24 位时间码（画面内容）计算，那 16.7 ms 是
  编码器真实的 1 帧延迟，一直算在 p50/p99 里；错的只是 `expected`（解码帧 pts）与
  `readback_lag_us` 这两个校验字段。所以修配对不会让 e2e 变小。
- **修法**：host 记录「编码器 100ns 精度采样时间 → 采集时刻」队列，按包自带 `pts_ns/100` 回查；
  输出采样时间为 0 时退化为队首（仍比取本轮采集时刻更接近归属）。`host.json` 新增 `pair_misses`。
  注意采样时间在编码器内部按 100ns 截断，配对键必须同精度。
- **证据**（`logs/s3f-fix-ffmpeg-soft4/e2e-samples.csv`，601 样本）：`tcode == expected` 599/601，
  仅剩首帧 0/1 两处启动样本；回读滞后中位 **0 µs**（修前 600/600 恒差 16.6~16.8 ms、`+16.7 ms`）。
  MF 路径 554/571 一致，残差为首帧流水与 GOP 边界重排（µs~8 ms 量级），中位仍 0。
- **同判据重测**（p99 ≤30 ms、上屏 ≥56.05 fps；不改口径、不剔除固定量，三次 FFmpeg 软解 + 一次 MF）：

  | 路径 | e2e p50 | e2e p99 | 上屏 fps | 首帧输出 | 结论 |
  | --- | --- | --- | --- | --- | --- |
  | FFmpeg 软解 A | 30.6 ms | 35.8 ms | 60.09 | 6.6 ms | FAIL 1.19× |
  | FFmpeg 软解 B | 30.9 ms | 41.2 ms | 60.00 | 5.6 ms | FAIL 1.37× |
  | FFmpeg 软解 C | 32.4 ms | 39.8 ms | 60.17 | 11.5 ms | FAIL 1.33× |
  | MF in-box | 307.3 ms | 339.8 ms | 57.24 | 192.8 ms | FAIL 11.3× |

  分段（p50）：传输（采集→完整 AU，含编码器 1 帧延迟）25~27 ms / 解码+整理 6.1 ms / 上屏 2.4 ms；
  MF：传输 34.0 ms / 解码 0.04 ms（GPU 直出）/ 上屏 1.8 ms，其余 270 ms 停在解码器 17 帧流水。
- **结论**：两条路都不达标，**未把 FFmpeg 设为默认**（MF 仍是默认与回退）。主项已不在解码器，
  而在主机侧「采集→编码出包」的 1 帧（16.7 ms）+ 编码/传输 8~10 ms；要进 30 ms 必须动编码排队
  （如让编码输出与采集同轮、或换更低延迟编码器），属新工作项，本轮不调参凑数。
- **后续待办**：d3d11va 每 10 s 数次 ~900 ms 尖峰（D34 未解决）；精简 FFmpeg 构建
  （`--disable-everything --enable-decoder=h264` 可到个位数 MB，打包决策，只记不做）。

## D41 S5-1 屏幕墙子码流的编码实例选择与 docs/04 §2.3 冲突

- **选择**：屏幕墙子码流使用 **1 个共享的缩略图编码器**（进程内唯一 H.264 实例，

  编码输出，只做分片分发，**编码实例数不随观看者数增长**。

  1) 改为每路独立实例（实例数随观看者线性增长，与 S5-1 资源约束冲突）；
  2) 修订 docs/04 §2.3，允许“一个共享缩略编码器 + 多路分发”这一形态。
- **代价**：所有观看者共享同一组分辨率/帧率/质量参数，不能按观看者单独调；仍额外占

    “屏幕墙管线单独 3 s 测量边际成本 + 4 路由 3 路线性外推”，比并发差分更可解释。

    `logs/TESTPLAN-s5-1.md`。

- **会话对端仍是进程内回环桩**：`bye` 报文与回执真实走了 UDP 序列化，但两端在同一进程；
  真实网络的 bye / 断线检测待会话层接入（现无网络输入通道）。
- **角标 fps 依赖纹理消费者与画面变化**：锁屏静态桌面下编码帧约 5 fps、上屏 fps 为 0，
  需在解锁且有交互的场景复验 fps/延迟数字。
- **桌面截图待人工确认**：本环境无法自动截取 Windows 原生窗口，角标与断线横幅的视觉
  呈现只有构建与数据证据。

## S5-5（2026-11-07）实测与缺口

- **块 1 授权内核**：新增 `crates/rdc-core/src/s5/grant.rs`（`PermBits(u16)` 严格按 docs/07 §4、
  `GrantTemplate`、`issue_grant`/`verify_grant` 五步离线校验、`ReplayGuard`、`ControlArbiter`
  独占+接管、`KickTicket`/`SignedKick`、`GrantStore` 原子写与 epoch）。审计新增字段级条目。
  单测 G1–G7 全过；`cargo test -p rdc-core` 36 项。
- **块 2 权限页真数据**：`rdc-bridge` 新增 `permission_snapshot` 与 grant/trust 的增删改查、
  `remote_access_stop`/`remote_access_resume`；页面三区接真实存储，含审计尾部、空/错态与重试。
- **块 3 免密**：`passwordless::decide_for_record` 统一裁决；信任设备 `passwordless`、未信任
  `pairing_code`、账号服务不可达按本地信任回退。
- **块 4 验证**：`rdc-cli s5-5` 产出 `logs/s5-5-verify.json`（`all_pass=true`）、
  `logs/s5-5-audit.jsonl`（11 条）。关键数字：只观看注入 `viewer_readonly`、可操作重连后
  `grant_control`；接管 15 s 让位 + 本机 30 s 超时拒绝；**踢出下发→画面停止 32 ms**（本机回环，
  上限 3 s）；撤销信任后强制配对码。

**已知缺口 / 环境待办**：

- **锁屏点击级验证未做**：权限页的签发对话框、批准/拒绝、停止/恢复二次确认、踢出按钮均
  **未**在锁屏会话下验证，只做了内核与数据链路证据；解锁后须人工复验并补截图，当前不计入通过。
- **踢出计时为本机回环**：32 ms 来自同进程 30fps 渲染循环，非真实网络对端；
  网络会话接入后需复测「下发→对端画面停止」。
- **权限位模型双轨**：新内核 `PermBits(u16)`（docs/07 九位）与旧 `rdc_security::permission::PermissionSet`
  （u32 五位）并存，映射在桥接边界显式换算。是否统一、以及 docs/13 写「七位」与 docs/07 九位的
  冲突，需负责人拍板（本阶段不改 docs）。
- **身份种子明文落盘**：`%APPDATA%\RDC\identity.json` 存 Ed25519 种子，未做 OS 级加密
  （DPAPI/Keychain）；当前仅本机单用户场景可接受，正式版需加固。
- **授权令牌有效期上限固定 90 天**：与 docs/07 一致，但未提供「续签」入口；到期后需重新签发，
  UI 只提示到期时间。

## S6（2026-11-07）打包与交付缺口

- **无代码签名证书**：Windows exe 与 NSIS 安装包均未签名，SmartScreen 首次运行提示「未知发布者」。
  正式分发需 EV/OV 代码签名证书 + 时间戳服务；本轮只保证可装可启动。
- **非 Windows 采集/注入后端仍是空壳**：`rdc-capture`、`rdc-input` 的 macOS/Linux 实现含
  `todo!()`，构建可通过但建立会话即 panic；Android/iOS 走 `CaptureError::Unsupported`。
  CI 的 macos/linux/android job 只证明「能打包」，不证明可用；本机无对应 SDK 无法实测。
- **iOS 无签名且 Rust 静态库未接入**：`build_xcarchive.sh` 产出 `--no-codesign` 归档，
  Rust staticlib 尚未配置到 Xcode 链接参数，真机无法运行。
- **Android 只有 debug 签名**：无 keystore 时脚本明确降级为 debug APK，不可上架；
  且移动端没有采集/注入实现。
- **锁屏导致点击级验证缺失**：屏幕墙预览、控制页建链画面、权限页对话框仍未人工复验，
  本轮只验证了进程启动、版本可读、配置加载与退出清理。
- **VC++ 运行库版本随构建机**：app-local 部署取自 MSVC 14.44.35112 的 Redist，
  若目标机已装更高版本，仍优先使用随包 DLL；后续升级工具链需同步重取。
- **安装包依赖 makensis**：本机通过 winget 安装 NSIS 3 后才产出 setup.exe；
  缺工具时脚本只出便携 zip 并显式警告，CI 用 `choco install nsis`。

# 15 · 可行性评审（独立评审意见）

> 评审对象：`01`~`14` 共 14 份设计文档（另扫描了仓库现有 Go 原型与空壳脚手架，`_rdc_impl_stash` 未纳入评审）。
> 评审时间：2026-11-07。评审方式：文档通读 + 参数交叉核对 + 平台/SDK 约束核查。评审人未参与本设计。
> 局限说明：本次没有真机、没有 GPU 编码器实测，也没有实验室网络环境。凡涉及具体编码器"某分辨率+色度+位深+帧率"能否同时成立，均以公开的驱动/SDK 能力边界判断，并在文中标注"不确定"；这类不确定本身就是风险，不应被当作已解决。

## 1. 结论摘要（先给结论）

**一句话结论：架构方向成立，但"按当前文档全量开工"不可行；裁剪到 v1 边界后可行。**

1. **整体评级：有条件不可行（Conditional No-Go）。**
   流媒体主干（Windows 采集 → 硬编 → 自研 UDP/FEC → 硬解 → 外部纹理上屏）是成熟路径，可行；但文档把三个"实验性能力"当成了 v1 验收门槛：4K+4:4:4+10-bit+120/144fps 同时成立、LAN P99 ≤20ms、五平台"可安装成品"。这三项在当前约束下都不成立（详见 §3、§4）。以现文档直接进 S1，S3/S4 必然返工，且返工点在协议与渲染桥，不是局部修补。

2. **硬指标：只有"1080p60、4:2:0、8-bit、LAN"这一档是稳的。**
   现实可达（被测管线、非玻璃到玻璃）：LAN P99 25~35ms（1080p60）、30~45ms（1080p120）；同城 P99 35~50ms；跨省 P99 55~90ms。文档的 20/40/80ms 只有在 120Hz 以上、零抖动缓冲、绕开 Flutter 合成器、且只测"采集时间戳之后"的管线下才可能接近；它不是用户感知的端到端延迟。4K120 4:4:4 10-bit 在消费级硬件上不可行，且与文档自定的 200 Mbps 码率上限直接矛盾（该组合需要约 300 Mbps~1.5 Gbps）。

3. **平台边界：文档对"iOS/Android 不能做被控"的判断是正确的，但"五平台可安装成品"的承诺不成立。**
   iOS 只能产出未签名 ipa，标准 iOS 设备无法安装；macOS 不做公证会被 Gatekeeper 拦截；Windows 不签名会触发 SmartScreen；Android 若按文档用"CI 临时 keystore"，每次构建签名不同，用户无法覆盖升级。也就是说，CI 能产出"构建物"，但产不出文档承诺意义上的"成品"。

4. **文档一致性：不满足"可冻结协议"的标准。**
   交叉核对出 38 处实质矛盾，其中 18 处为高严重度，7 处会直接导致实现分叉：降级顺序、TCP 路径没有媒体协议、抖动缓冲单位（帧 vs 毫秒）、同实例双输出（主码流+子码流）、重连是否重建解码器、账号服务可自授权、授权"永久"与"不支持永久"。这些不是文字瑕疵，是协议/状态机层面的冲突。**S2 结束前必须先裁决并冻结，否则 S3 之后改动成本翻倍。**

5. **安全：三处硬伤。**
   ① 6 位配对码只作为 HKDF salt，主动中间人可离线枚举 10^6 次完成握手，文档"中间人无法完成握手"的结论不成立；② 信令走明文 UDP，`sig` 的 HMAC 密钥（token）在 `register_ok` 中明文下发，链路上可读即可伪造，HMAC 不提供所需保护；③ 账号服务持有授权签名私钥，被攻破后可为攻击者签发 grant（含 VIEW/CONTROL），攻击者作为主控端连接后在自己的客户端解密画面——文档"账号服务被攻破也不能解密任何媒体"的表述是错的。

6. **工期：文档"比原估算多 35~45%"不可审计，且偏低。**
   在没有给出原基线的前提下，这个百分比无法验证。按文档自身列出的范围逐项估算：核心工程 40~61 人月，加 QA/发布/硬件实验室后 52~80 人月；5~6 人团队约 11~16 个月，3~4 人约 18~25 个月。相对一个"只做 Windows 1080p60 远控"的朴素基线，增量是 1.8~2.5 倍，不是 35~45%。35~45% 只覆盖了 `11` 的优化项，没有覆盖 `14` 新增的 7 个设置页/主界面 IA、账号服务、多账号授权、签名与公证。

7. **CI：40 分钟目标不现实。**
   冷启动 90~150 分钟，命中缓存 45~75 分钟；iOS 无签名只能出 xcarchive 再手工封 ipa；macOS universal 需要两次构建再 lipo；Android 临时 keystore 会让升级链断裂；GitHub 托管 runner 无法跑 GPU/长稳/延迟验收，性能门槛只能在自建硬件实验室做。

8. **建议的 v1 重定义（明确表态，供决策）：**
   - 被控端：Windows 10/11 x64（唯一被控平台）。
   - 主控端：Windows、macOS（arm64/x64）、Linux x64、Android、iOS；移动端明确 1080p60 4:2:0。
   - 画质：1080p~1440p、60fps、4:2:0、8-bit 为正式支持；4K60 4:2:0 10-bit 为"能力允许"；4:4:4 与 120/144fps 降为"Windows+NVIDIA 实验性"，不进 v1 验收。
   - 延迟口径：LAN P99 ≤30ms（管线测量）、玻璃到玻璃 ≤45ms；同城 P99 ≤50ms；跨省 P99 ≤90ms。
   - 功能：设备列表、单会话、剪贴板（文本）、文件传输、权限页精简版；多账号授权、屏幕墙 16 路、双路径、音频全部后置。
   - 分发：Windows/Linux/Android 为"可安装"；macOS 为"未公证 dmg"；iOS 为"源码/自签"，不承诺安装。

9. **开工前的强制闸门（建议 6 周 spike，全部通过才进 S1 全量）：**
   Windows NVENC 4K60 4:2:0 10-bit 实测；同卡 4:4:4 8/10-bit 实测（含解码端）；Flutter 外部纹理 + HDR/10-bit 呈现路径实测；60Hz 与 120Hz 下时间码 P99 测量；对称 NAT/CGNAT 打洞成功率统计；macOS SCK+TCC 与 CI 构建；Android keystore 与 iOS 未签名产物验证。任一失败，先改范围再排期。

## 2. 逐模块评级

评级口径：**可行**＝有成熟实现路径、工作量可控；**有风险**＝存在平台/硬件/协议不确定性，必须先 spike 或改方案；**不可行**＝在当前约束下无法达到文档承诺，必须删改范围。

### 2.1 平台限制是否被绕过（专项核对）

## 3. 硬指标可达性

### 3.1 先把"延迟"的口径说清楚

文档混用了三个不同的量，但都叫"端到端延迟"：

- **管线延迟**：从"采集到一帧的时间戳"到"解码完成/提交上屏"，`10 §1.1` 与 `11 §2.12` 的时间码测的就是这个。
- **玻璃到玻璃（G2G）**：从屏幕像素变化，到主控端显示器像素变化。它额外包含采集等待（vblank 相位）、合成器排队、显示扫描与面板响应。
- **输入延迟**：按键事件到被控端注入，`10 §1.1` 用 240fps 相机测，这个口径是合理的。

`01 §5.1` 的预算表把"抖动缓冲 0~2ms、预算 3ms；呈现 0~1ms、预算 2ms；采集 1~2ms"当作连续时间加总，但**帧级管线的调度粒度是帧周期**，不是毫秒：

- 60Hz：1 帧 = 16.7ms；120Hz：8.3ms；144Hz：6.9ms。
- 采集 `AcquireNextFrame` 会阻塞到下一帧到达：平均等待半个帧周期，P99 接近一个帧周期（60Hz 下 8.3/16.7ms）。文档把它记成 1~2ms，等于把这段时间藏到了时间码起点之前。
- 抖动缓冲只要按"1 帧"设计，60Hz 下就是 16.7ms，不是 1~3ms。
- Flutter 外部纹理上屏要经过引擎合成与 vsync，至少再等 0~1 个帧周期；`01 §5.1` 记 0~1ms 不成立。

结论：**`01 §5.1` 的"典型 7~15ms、预算 20ms"在 60Hz 下算不通。** 20ms 只有在 120Hz 以上、零帧抖动缓冲、绕开 Flutter 合成器（原生视频层）、且只统计"采集时间戳之后"时才可能接近；它不是 G2G，也不是 60Hz 用户的实际体验。

### 3.2 带宽的物理下限

以 4:4:4 10-bit = 30 bit/像素、4:2:0 10-bit ≈ 15 bit/像素、4:2:0 8-bit = 12 bit/像素计：

| 组合 | 像素率（Mpx/s） | 原始码率 | 若压到 200 Mbps 所需压缩比 |
|---|---|---|---|
| 1080p60 4:2:0 8-bit | 124.4 | 1.49 Gbps | 7.5:1 |
| 1080p120 4:2:0 8-bit | 248.8 | 2.99 Gbps | 15:1 |
| 1440p120 4:2:0 10-bit | 442.4 | 6.64 Gbps | 33:1 |
| 4K60 4:2:0 10-bit | 497.7 | 7.46 Gbps | 37:1 |
| 4K60 4:4:4 10-bit | 497.7 | 14.93 Gbps | 75:1 |
| 4K120 4:2:0 10-bit | 995.3 | 14.93 Gbps | 75:1 |
| **4K120 4:4:4 10-bit** | **995.3** | **29.86 Gbps** | **149:1** |

屏幕内容（HEVC-SCC/调色板/无损块）在静态文字上可以做到 100:1 以上，但"高刷 + 4:4:4 + 10-bit + 低延迟"意味着不能靠长 GOP、不能靠多帧参考、不能靠大缓冲；动态内容（视频、滚动、游戏）的可用压缩比会掉到 30~60:1。**4K120 4:4:4 10-bit 的现实码率是 300 Mbps~1.5 Gbps，与 `04 §2.1` 的"每路 ≤200 Mbps"直接冲突。** 这不是"调参能解决"的问题，是上限被写死。

### 3.3 现实可达区间（我的判断）

"管线 P99"指时间码口径；"G2G P99"指玻璃到玻璃。均为理想千兆/万兆 LAN、单会话、硬编硬解、无中继。

| 档位 | 编解码可行性 | 现实码率 | LAN 管线 P99 | LAN G2G P99 | 判定 |
|---|---|---|---|---|---|
| 1080p60 4:2:0 8-bit | 可行 | 8~20 Mbps | 20~30 ms | 30~40 ms | **正式支持** |
| 1080p120 4:2:0 8-bit | 可行（120Hz 屏） | 20~40 Mbps | 22~32 ms | 28~40 ms | 正式支持（有条件） |
| 1440p60 4:2:0 10-bit | 可行 | 30~60 Mbps | 25~35 ms | 35~45 ms | 正式支持 |
| 4K60 4:2:0 8/10-bit | 可行（NVENC/部分 AMF/QSV） | 40~120 Mbps | 30~45 ms | 40~55 ms | 能力允许 |
| 4K60 4:4:4 8-bit | 仅部分 NVIDIA，解码端不确定 | 80~180 Mbps | 40~55 ms | 50~65 ms | 实验性 |
| 4K60 4:4:4 10-bit | **不确定，大概率不可行** | 120~250 Mbps | 45~60 ms | 55~75 ms | 从硬指标删除 |
| 4K120 4:2:0 10-bit | 编码吞吐/解码/线材都紧张 | 150~250 Mbps | 50~70 ms | 60~80 ms | 实验性 |
| 4K120 4:4:4 10-bit | **不可行** | 300~1500 Mbps | 70 ms+ | 80 ms+ | 删除 |
| 4K144 任意 4:4:4 | **不可行** | — | — | — | 删除 |

由此对硬指标给出明确判断：

- **LAN ≤20ms**：在 60Hz、4:2:0、1080p 下**不可达**（管线 P99 就已 20~30ms，G2G 30~40ms）。在 120Hz、零抖动缓冲、原生视频层下**边缘可达**（管线 12~18ms，G2G 18~24ms），但不能写成"全档位 P99"。
- **同城 ≤40ms**：1080p60 的 G2G P99 为 30~45ms，**只有一半场景能达标**；4K60 为 40~55ms，**不达标**。作为"典型值"可以，作为"P99 99% 准时"不行。
- **跨省 ≤80ms**：1080p60（RTT 25~45ms）G2G P99 55~85ms，**边缘**；4K60 70~100ms，**不达标**。若按管线口径，1080p60 可做到 45~65ms，能达标，但那就不是用户感知的端到端。
- **4K + 4:4:4 + 10-bit + 120/144fps 同时成立**：**不可行**。四个维度里任意三个组合都可能落到"部分硬件/部分内容"可用，四个全开没有消费级硬件路径，也没有 200 Mbps 内的码率路径。

### 3.4 文档中过强的假设（逐条）

1. **`01 §5.1`：抖动缓冲按毫秒计（1~3ms）。** 帧级缓冲的最小单位是帧周期，60Hz 就是 16.7ms。这一条直接推翻 20ms 预算。
2. **`01 §5.1`：呈现 0~1ms。** 忽略了合成器排队、vsync 等待、面板扫描与响应；Flutter 还要多一帧。真实是 0~33ms（60Hz）。
3. **`01 §5.1`：采集 1~2ms。** 这是"帧到手之后的拷贝开销"，不含等待下一帧的相位时间；时间码测量把这段隐藏了。
4. **`01 §5.1`：4K 编码 2~4ms（上限 6ms）。** 1080p 低延迟硬编可能是 3~6ms，4K 4:4:4 10-bit 通常是 6~12ms；这个数字没有分档位给出。
5. **`01 §5.1` + `10 §1.1`：时间码"不依赖两端时钟同步"。** 读远端嵌入的时间戳再和本地单调时钟比较，必须知道两端时钟偏移；`04 §6` 虽用最小 RTT 估偏移，但估计误差本身就有 1~5ms。`11 §2.12` 又承认"±1 帧（16.7ms）"，两者自相矛盾（C37）。
6. **`04 §2.1`：视频每路 ≤200 Mbps。** 对 4K120 4:4:4 10-bit 不够，物理下限见 §3.2。
7. **`05 §2.0`：4K 起、60fps 底线。** 在 20 Mbps 公网/弱网下，4K60 至少需要 40~120 Mbps；按这个"底线"，降级阶梯根本无法执行（降分辨率就违反底线，不降就花屏）。
8. **`06 §2.2`：4:4:4、10-bit、120/144 可以"逐项能力允许"。** 编码器的色度、位深、profile、level 是耦合的，不能把四个维度当独立开关逐项协商；必须按"具体 profile + 分辨率 + 帧率 + 码率"组合探测。
9. **`12 §2.1`/`04 §2.3`：观看者复用主码流编码实例、同实例输出主+子码流。** 单编码会话不支持两个独立输出；这是 API 层面不成立，不是调参问题（C31）。
10. **`12 §2.2`：消费卡 2~5 实例可支撑"4 路主码流 + 16 路预览"。** 单路 4K120 就能吃满一个 NVENC 引擎；实例数不是"路数"的线性资源。
11. **`10 §7.7`：CI 全流程 ≤40 分钟。** 见 §9，冷启动至少翻倍。
12. **`10 §1`/`08 §5`：五类产物"安装后能启动"。** iOS 未签名 ipa 不满足"安装"，Android 临时 keystore 不满足"升级"，macOS 未公证不满足"顺畅安装"。

**给硬指标的最终建议值（可直接写进验收）：**

| 指标 | 建议验收值 | 测量口径 |
|---|---|---|
| LAN 延迟 | 1080p60 管线 P99 ≤30ms；G2G P99 ≤45ms；120Hz 档管线 P99 ≤20ms | 时间码 + 高速相机双口径，样本 ≥10 分钟 |
| 同城 | 1080p60 G2G P99 ≤55ms | 同上 |
| 跨省 | 1080p60 G2G P99 ≤90ms | 同上 |
| 画质 | 1080p~1440p 60fps 4:2:0 8-bit 正式；4K60 4:2:0 10-bit 能力允许 | 能力探测 + 像素比对 |
| 色度/位深 | 4:4:4/10-bit 仅 Windows+NVIDIA 实验性，不进 v1 门槛 | 编解码双向实测 |
| 帧率 | 60fps 正式；120fps 仅 1080p/1440p 4:2:0；144fps 不做 | 逐档位验收 |

### 4.3 对"比原估算多 35~45%"的判断

**判断：这个说法不可审计，且按文档全量范围偏低。**

- 文档没有写出原估算的人月/日历，35~45% 没有分母，无法验证。
- 若"原估算"= 30 人月（一个只做 Windows 1080p60 远控的朴素基线），+35~45% = 40~44 人月。本文核心估算 40~61 人月，**下限刚好、上限超出 39%**；加上 QA/发布后 52~80 人月，**超出 18%~82%**。
- 更关键的是：35~45% 只对应 `11` 的 16 项优化。`14` 新增的 7 个设置页 + 主界面 shell/快速设置/引导/通知中心、`03 §4.6-4.7` 的账号服务与多账号授权、`10 §7` 的签名/公证/keystore，都不在那 16 项里。把这些算进去，相对朴素基线是 **1.8~2.5 倍**，不是 1.35~1.45 倍。
- 结论：**+35~45% 是"只算优化项"的数字，不是"全量交付"的数字。若拿它做排期，至少低估 25~60%。**

### 4.4 最可能延期或返工的环节（按概率排序）

1. **S2 协议冻结太晚（概率高）。** 打洞、TCP 路径、账号授权、接管状态机同时在 S2 改，S3 的传输/渲染按旧协议实现，必返工。建议 S2 只冻结"媒体会话 + 信令信封 + 错误码"，账号/授权拆到 S2b。
2. **4:4:4 + 10-bit + 120 的能力探测（概率高）。** 一旦实测不支持，`11 §1` 的硬指标、`06 §2.2` 的协商矩阵、`10` 的 S3 验收全部要改。
3. **Flutter 10-bit/HDR 呈现（概率高）。** 要么改原生视频层（架构变更），要么放弃 10-bit（指标降级）；两条路都不是"再调一下"。
4. **macOS TCC + CI 产物（概率高）。** ad-hoc 签名导致每次构建重新授权；CI 上无法验证 TCC；公证另需账号与流程。
5. **Wayland 无人值守（概率高）。** portal 逐次授权与被控端"开机即用"直接冲突；uinput 需要 root，发行版差异大。
6. **屏幕墙/观看者的编码实例（概率高）。** "同实例双输出"不成立，必须改资源模型；16 路解码上限也未评估。
7. **多账号授权安全评审（概率中高）。** 令牌、世代、接管、踢出、审计五套状态机，任何一处口径不一致都会在 S5 暴露。
8. **CI 打包与签名（概率中高）。** Android keystore、iOS 签名、macOS universal、Windows 签名，任何一个都能让"成品"延期数周。
9. **延迟测量口径争议（概率中）。** 管线 vs G2G 的选择会直接决定验收是否通过；建议先定口径再写代码。
10. **移动端解码能力（概率中）。** 4K/120/10-bit 在手机上普遍不支持，S3 的"五端一致"验收会失败。

### 6.2 文档里可能踩坑的表述

1. **`11 §2.14`：把"LGPL 配置 + 动态链接"当成合规的全部。** 还缺三件事：源码提供/书面 offer、允许替换库、不得静态链接。尤其 Android：如果 `libavcodec.a` 被静态链进 `librdc.so`，即便 FFmpeg 是 LGPL，也不满足"可替换"要求。文档只写了 iOS 例外，没有写 Android 的静态链接风险。
2. **`11 §2.14`：只提 FFmpeg，没有提 HEVC/H.264 专利。** LGPL 解决的是版权，不解决专利。HEVC 是本项目的核心编码，专利许可成本可能高于全部开源许可成本。
3. **`06 §2.4`：OpenH264 作为"兜底"。** 需要写清"仅 1080p、H.264、4:2:0；专利许可另行评估"，否则会被理解为"免费可商用"。
4. **`02 §1.1`：把"厂商 SDK"列为普通依赖。** NVENC SDK 的许可禁止在非 NVIDIA 硬件上模拟、限制再分发；这不是 `cargo` 依赖，不能按 crate 管理。要在架构里把它标成"平台专有后端 + 许可审查"。
5. **`14 §3.1`：关于页只写"许可与开源声明（LGPL）"。** 至少要包含：FFmpeg LGPL 文本与源码 offer、Flutter/Dart/Rust 的 MIT/BSD/Apache NOTICE、OpenH264 的 BSD 与专利声明、厂商 SDK 的商标/免责声明。不能只写一个 LGPL。
6. **`06 §2.1` 的 `Software` 后端。** 如果实现时为了图快接了 x264/x265，整个产品会被 GPL 污染；协议里应把 `Software` 明确为"OpenH264 only"，并在 CI 里做二进制符号/构建参数扫描。
7. **`10 §7` 的产物清单没有 NOTICE/SBOM。** Release 包应带 `NOTICE.txt`、`SBOM (CycloneDX/SPDX)`、FFmpeg 源码获取说明；否则 LGPL 合规不完整。
8. **`03 §4.6` 账号服务依赖未做许可审查。** 后端若引入 AGPL 组件（某些数据库/队列/管理面板），SaaS 场景也可能触发 copyleft；需要与客户端一起做 allow-list。
9. **字体/图标/示例素材。** Flutter 默认字体、第三方图标包、`14` 里引用的截图素材，都需要确认可商用；这类"小资产"最容易在发布前卡住。
10. **"闭源分发"与"App Store"的冲突。** 若未来上架 macOS/iOS，LGPL 静态链接与 Apple 的 DRM/签名限制可能冲突；文档已经避开 iOS 链 FFmpeg，方向正确，但要把"永不上架 App Store"写成明确约束，否则后续会反复。

### 6.3 结论

- **版权层面：按文档的 FFmpeg LGPL 动态链接 + iOS 不链 FFmpeg 的方案，闭源分发基本可行**，前提是补齐源码 offer、NOTICE、SBOM，并禁止 GPL/AGPL 传递依赖；Android 必须改成动态链接或独立进程。
- **专利层面：不可判定，且大概率需要付费。** HEVC/H.264 的专利池许可在文档中完全缺失；4:4:4 10-bit 与高帧率不改变专利池覆盖范围，但会增加"商业产品"属性。**在 S1 退出前必须做一次法务/专利尽职调查，否则"可闭源分发"的结论不成立。**
- **厂商 SDK：可以用，但不能当作普通开源依赖。** NVENC/AMF/QSV 的运行时随驱动分发没问题，SDK 本身不要再分发；这部分需要在 `02` 的依赖表里单独标注。

## 8. CI 现实性

### 8.1 文档的 CI 目标 vs 实际

`10 §7` 的目标是"5 个 job、全流程 ≤40 分钟、产出 5 类可安装产物"。这个目标在 GitHub 托管 runner 上**不成立**：

| 项目 | 文档目标 | 实际（冷启动） | 实际（命中缓存） | 卡点 |
|---|---|---|---|---|
| 5 平台矩阵总时长 | ≤40 min | **90~150 min** | 45~75 min | Flutter SDK 1.9GB、Xcode 工具链、NDK、Rust 多目标编译、CocoaPods |
| macOS job | 与 Linux 同量级 | 25~40 min/架构 | 15~25 min | arm64/x64 两次构建 + lipo + 签名 |
| iOS job | 产出 ipa | 20~35 min | 15~25 min | 无签名只能出 xcarchive；插件走 CocoaPods；SPM 不成熟 |
| Windows job | NSIS 安装包 | 20~30 min | 12~20 min | VS2022 workload、choco 装 NSIS、签名缺失 |
| Android job | APK | 15~25 min | 8~15 min | NDK、cargo-ndk、Gradle 缓存、ABI 拆分 |
| Linux job | AppImage | 10~20 min | 6~12 min | libfuse2、GTK/PipeWire 依赖、AppImage 打包 |
| 服务器 job | 未提 | 10~20 min | 5~10 min | 数据库迁移、容器构建 |

按 GitHub 计费：私有仓库 macOS 分钟按 10 倍计。上述矩阵单次运行约消耗 **100~200 计费分钟**；每月 2000 分钟免费额度只够 10~20 次完整构建。对"每次 push 都跑"的团队，这是成本问题，不是技术问题。

### 8.2 会实际卡住的点

1. **iOS 无签名 ≠ 可安装。**
   `flutter build ipa --no-codesign` 产出的是 `.xcarchive`，不是可安装 ipa；手工把 `Payload/*.app` 压成 zip 得到的"未签名 ipa"只能越狱/TrollStore 安装，不是文档说的"成品"。要真正可安装，必须有 Apple Developer 账号、证书、Provisioning Profile、设备 UDID 或 TestFlight/App Store 流程。**这是流程阻塞，不是 CI 脚本能绕过的。**
2. **Flutter iOS 插件与 SPM。**
   文档倾向"优先 SPM"，但当前 Flutter 插件生态仍以 CocoaPods 为主；`flutter_rust_bridge` 的 iOS 集成通常要 xcframework + 手写 podspec/脚本。CI 上第一次 `pod install` 很容易因 CDN/版本漂移失败。建议：**pin Flutter 版本、pin FRB 版本、把 Podfile.lock 入库、禁用 SPM 实验特性**。
3. **macOS universal 构建。**
   `flutter build macos --release` 只产出 runner 当前架构；GitHub 的 `macos-14/15` 是 arm64，`macos-13` 是 x64。universal 需要两次构建再 `lipo` 合并 App 二进制、Flutter engine framework、FRB dylib，并在合并后重新签名。合并顺序错、framework 符号链接丢失都会产出"能编译但不能启动"的包。**建议 v1 只发 arm64，x64 单独发；universal 作为 v1.1。**
4. **macOS 公证。**
   需要 Developer ID Application 证书、Hardened Runtime、entitlements、`notarytool` 与 Apple ID/API Key。文档明确"不做公证"，那么 Gatekeeper 会拦截，用户要右键打开；这可以接受，但**不能在 `10 §1` 写"安装后能启动"而不加限定**。另外 SCK/TCC 无法在 CI 验证，只能人工冒烟。
5. **Android keystore。**
   `08 §5` 写"CI 生成临时 keystore"。这是**分发级错误**：Android 用签名证书识别应用身份，签名一变就不能覆盖安装，用户必须卸载重装（数据丢失），也无法上架。必须把 keystore 以 base64 存 GitHub Secrets，密码单独存，固定 `applicationId`，并制定密钥轮换/丢失预案。若上 Google Play，还要启用 Play App Signing。
6. **Windows 安装包与签名。**
   Flutter Windows 依赖 VS2022 C++ workload 与 Windows SDK；NSIS 需要 choco 安装；还要带 VC++ runtime（或静态 CRT），否则干净机器启动失败。没有代码签名证书 → SmartScreen 警告；EV 证书还需要硬件令牌/云签名服务，CI 集成另算。**"可安装"可以做到，"无警告安装"做不到。**
7. **Linux AppImage。**
   Ubuntu 22.04 需要 `libfuse2` 才能运行 AppImage；Flutter Linux 需要 GTK3 开发包、`libva`、PipeWire 头文件；AppImage 打包要把 Flutter 的 `lib/`、data、icons 全部收进去，并处理 `ldd` 缺失库。glibc 基线要固定在 22.04，不能在高版本 runner 上构建后要求低版本发行版运行。Wayland 相关库不要硬绑。
8. **Rust 交叉编译。**
   iOS 目标要 macOS runner + Xcode SDK；Android 要 NDK + `cargo-ndk`；Windows 要 MSVC；macOS universal 要两个 target。`ring`/`aws-lc-rs` 需要 clang，`bindgen` 需要 libclang；任何一项版本不匹配都会在链接期失败。**建议在 S1 就把 5 个 target 的"空 crate 编译"跑通，不要等 S3。**
9. **FRB 代码生成漂移。**
   Rust 侧签名一变，Dart 生成代码必须同步；CI 要加 `flutter_rust_bridge_codegen generate` + `git diff --exit-code` 检查，否则会出现"本地能跑、CI 产物崩溃"。
10. **GPU/性能验收无法在托管 runner 做。**
    GitHub runner 没有 NVENC/AMF/QSV/VideoToolbox，也没有 120Hz 屏与弱网仪；`cargo bench` 在共享 runner 上噪声大，15% 相对阈值仍会 flaky。**性能门槛必须放到自建硬件实验室；CI 只做编译、单测、协议一致性、打包。**
11. **密钥与供应链。**
   Windows 证书、Apple 证书/公证、Android keystore、服务端签名密钥都要进 Secrets/Environment；需要审批与轮换。文档没有列出任何密钥清单。Release 还应产出校验和、SBOM、NOTICE、签名（minisign/GPG）；`10 §7` 都没有。
12. **runner 镜像漂移。**
   `windows-latest`/`macos-latest` 会变；Xcode 版本升级会破坏 Flutter/FRB。必须 pin `windows-2022`、`macos-14`、`ubuntu-22.04`，并记录 Xcode/Flutter/Rust/NDK 版本到 `.tool-versions`。

### 8.3 建议的 CI 结构（务实版）

```text
job 1  lint + unit       (ubuntu, 5 min)
job 2  rust cross-build  (matrix: win-msvc / linux-gnu / mac-aarch64 / mac-x86_64 / android-arm64 / ios-arm64)
job 3  flutter build     (matrix: windows / linux / mac-arm64 / android / ios)
job 4  package           (NSIS / AppImage / dmg / APK；iOS 只出 xcarchive)
job 5  compliance        (cargo-deny + license NOTICE + SBOM + buildconf 校验)
job 6  release           (tag + checksums + 上传 artifact；签名 job 单独手动触发)
```

- **不做**：GPU 性能、长稳、真实网络、TCC/权限验收 → 放自建实验室。
- **必做**：`--disable-gpl` 校验、NOTICE/SBOM、keystore/证书存在性检查、FRB 生成一致性、产物冒烟（Windows/Linux/Android 可启动）。
- **时间预期**：冷启动 90~150 分钟；稳定后 45~75 分钟。**不要承诺 40 分钟。**

## 10. 最终结论与行动建议

### 10.1 明确表态

| 问题 | 结论 |
|---|---|
| 整体方案能否按当前文档开工？ | **不能（No-Go）。** 不是"有风险但可以做"，而是范围、硬指标、安全模型、发布承诺四处都与约束冲突；直接开工会在 S3/S4 返工。 |
| 裁剪后能否做？ | **能（Go with conditions）。** 按 §7.1 裁剪、按 §10.2 过闸门后，是一个 6~8 人、12~18 个月的可行产品。 |
| 核心流媒体链路是否可行？ | **可行。** Windows 采集 + NVENC + UDP/FEC + 硬解 + 外部纹理是成熟路径；1080p60 4:2:0 有把握。 |
| 20ms LAN 是否可达？ | **60Hz 不可达；120Hz、零缓冲、原生视频层下边缘可达。** 必须按 G2G 口径重新定义，否则验收必吵。 |
| 4K 4:4:4 10-bit 120/144 是否可达？ | **不可达。** 消费级硬件、解码端、200 Mbps 码率上限三重约束；只能做"部分硬件 + 部分档位"的实验性支持。 |
| 五平台可安装成品是否可达？ | **Windows/Linux/Android 可达；macOS 只能未公证 dmg；iOS 不可达（无签名不可安装）。** |
| 工期 35~45% 增量是否合理？ | **不合理，且偏低。** 无基线、不可审计；全量范围实际是朴素基线的 1.8~2.5 倍；核心 40~61 人月，总计 52~80 人月。 |
| 文档能否直接冻结协议？ | **不能。** 38 处矛盾、18 处高严重度；必须逐条裁决后才能进 S3。 |
| 闭源分发是否合规？ | **版权层面基本可以（有条件）；专利层面未评估，大概率需付费。** |

### 10.2 开工前闸门：6 周 spike（建议直接立项）

| 周 | 任务 | 通过标准（Exit Criteria） |
|---|---|---|
| W1 | Windows 编码矩阵：NVENC / AMF / QSV，1080p60、4K60 4:2:0 8/10-bit | 三后端至少两后端稳定编码；记录初始化/首帧/稳态延迟 |
| W2 | 4:4:4 / 10-bit / 120 组合：编码 + 解码 + 像素比对 | 同一 GPU 上"编码成功 + 解码出图 + PSNR/像素误差达标"三项全过；否则判定不支持 |
| W3 | Flutter 外部纹理 PoC（Win/mac/Android）+ 原生视频层备选 | 8-bit 稳定 60fps；10-bit/HDR 能出正确颜色；测出合成器附加延迟 |
| W4 | 延迟测量台：60/120Hz、时间码 + 240fps 相机、LAN 千兆 | 两套口径同时产出 P99；差值可解释；确定验收口径 |
| W5 | NAT 矩阵：20+ 组网络（家宽/校园/CGNAT/双栈/仅 IPv6） | 直连成功率 ≥70%；失败可中继；TCP 路径去留决策 |
| W5 | 安全评审：信令机密性、PAKE、grant 信任边界 | 三处硬伤有明确修复方案；红队无法用伪造 grant 观看 |
| W6 | 发布试通：Windows NSIS、Android 固定 keystore、macOS TCC、iOS xcarchive | 三类产物可安装/可启动；keystore 可覆盖升级；iOS 产物有明确分发路径 |
| W6 | 许可/专利初筛 | `--disable-gpl` 校验通过；NOTICE/SBOM 能生成；专利问题有法务结论或预算 |

**闸门规则：** 任一项不通过，先改范围/指标，再排 S1；不允许"先开工，后面再解决"。尤其 4:4:4/10-bit、Flutter 10-bit、NAT 成功率三项，是决定项目定位的。

- **核心工程：40~61 人月。**

- **日历：6 名核心 + 1 QA，10~15 个月；4 名核心 + 1 QA，15~22 个月；3 名核心，20~28 个月（不建议）。**
- **相对"朴素 v1 基线"的增量：1.8~2.5 倍；`11 §6.1` 的 35~45% 只覆盖优化项，不能用于全量排期。**

### 10.5 不确定项（明确标注，不装作确定）

1. **NVENC 在具体 GPU 代际上能否同时开 HEVC 4:4:4 与 10-bit、4K120 吞吐多少** —— 公开资料不一致，必须以 W1/W2 实测为准。这条不确定直接决定 4:4:4 档位的存亡。
2. **AMF/QSV 的 4:4:4 编码支持范围** —— 文档自己写了"需实测"；我判断多数消费级 iGPU/dGPU 不支持，但不敢替厂商下结论。
3. **D3D11VA / MediaCodec / VideoToolbox 对 HEVC 4:4:4 10-bit 的解码支持** —— 桌面独显可能支持，移动端基本不支持；需要逐设备验证。
4. **Flutter 各平台外部纹理的 10-bit/HDR 路径** —— Windows/macOS 可能通过原生叠加层绕过，Android/iOS 很难；这是架构级未验证项。
5. **NVDEC/MediaCodec 的并发解码会话上限** —— 文档完全没提；屏幕墙 16 路是否可行，必须实测。
6. **macOS ad-hoc 签名下 TCC 授权的持久性** —— 不同 macOS 版本行为不同；CI 无法验证，只能人工。
7. **国内 CGNAT/对称 NAT 的实际占比与打洞成功率** —— 需要 20+ 组真实网络统计；任何"理论成功率"都不可信。
8. **HEVC/H.264 专利许可的实际费率与是否需要按软件产品付费** —— 需法务；本文只能指出"文档缺失"。
9. **GitHub 托管 macOS x64 runner 的可用寿命** —— `macos-13` 会退役；universal 方案要准备替代（自建 runner）。
10. **现有仓库状态** —— `crates/`、`app/`、`packaging/`、`.github/` 目前是空壳，根目录只有 Go 原型；S1 实际尚未开始。文档的完成度不等于实现完成度，排期时不要把"文档写完"当成"S1 已完成"。

### 10.6 一句话给决策者

**现在不是"要不要做"的问题，而是"先花 6 周证明三件事"：4:4:4/10-bit/120 到底能不能用、20ms 到底按哪个口径验收、iOS/Android/macOS 的"成品"到底怎么分发。这三件事任意一件没答案，S1 全量开工就是把返工写进预算。** 先做 spike、先裁范围、先冻结协议，再谈 35~45% 还是 80~150%。
